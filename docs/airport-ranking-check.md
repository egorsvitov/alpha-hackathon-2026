# Проверка нашего блока на новости о Домодедово

> Обновление 22.10.2026: потребитель мигрирован на B6 v0.1/v0.2. Прежние ограничения приёма ниже описывают исторический срез. Актуальные результаты: [миграция](b6-v02-consumer-migration.md). Предметное покрытие ранкера этим не расширено.

Проверка: 22.10.2026, вход — присланный `output-b6.json` с двумя EventBundle. Код приложения не изменён. LLM и внешние API не вызывались.

## Вывод

**Текущий блок не сможет надёжно выбрать компании для этой новости.** Есть независимые проблемы транспорта/схемы и покрытия ранкера. Исправления одной версии контракта недостаточно.

## 1. Настоящий путь загрузки

`ranking.b6.load_bundles()` отвергает файл: `JSON input must be an object`. Прислан JSON-массив двух bundle, а наш интерфейс принимает один объект в `.json` либо по объекту на строку `.jsonl`.

После отдельного чтения массива каждый bundle проверен существующим валидатором. У каждого четыре ошибки схемы: версия 0.2 вместо поддерживаемой 0.1, новое поле scenario и два timestamp без секунд. Измерений нет, поэтому value_role в этом примере не участвует. Успешного импорта не произошло.

## 2. Изолированная проверка собственно ранжирования

Чтобы не ограничиться известным отказом схемы, создан диагностический прогон ниже границы валидации. Исходные bundle **не преобразовывались**: версия, claims, даты, источники и scenario сохранены. StoredEvent построены явно только для диагностики; это не новый адаптер и не штатно принятые события.

Дата среза выбрана на секунду позже максимального updated_at/first_published_at: `2026-10-21T21:00:40.777231+00:00`. Время не вызывает искусственного отсева. Роль — cfo, настройки ранкера исходные, доверенный entity mapping не задавался. Платёжные связи в этой пробе не загружались.

| Профили | Количество | В ленте | Результат пар с двумя событиями |
|---|---:|---:|---|
| Готовые синтетические логистика/ИТ/торговля | 3 | 0 | 6 deferred |
| Дополнительные синтетические авиагрузоперевозки/авиационная инфраструктура | 2 | 0 | 4 deferred |
| Реальные компании с ОКВЭД 79 — туризм | 3 | 0 | 6 deferred |
| Реальные компании с ОКВЭД 49.41 — автогрузоперевозки | 3 | 0 | 6 deferred |
| Реальные компании с ОКВЭД 62 — ИТ | 3 | 0 | 6 deferred |
| **Всего** | **14** | **0** | **28 deferred, 0 scored** |

Для реальных профилей выбраны первые три неконфликтных ID каждой группы, не вся база. Синтетические авиационные профили дополнительно прошли schema/semantic-проверку CompanyProfile. Таблица не является экспертной разметкой важности: туризм и перевозки — проверка возможного покрытия, не утверждение, что каждой такой компании новость важна.

Все пары отложены с `no_candidate_signal_unknown_relevance`, а не признаны доказанно нерелевантными. Ошибочных будущих дат или withdrawn-исключений в диагностике нет.

## 3. Почему ранкер пропускает событие

- Из восьми существующих mapping rules ни одно не покрывает operational_incident. Правила знают ставку, топливо, зарплаты, сталь, торговые ограничения и валюту.
- Новости об аэропорте недостаточно тематически похожего профиля transport: нужен описанный механизм сопоставления. Автоматического семантического понимания отрасли в коде сейчас нет.
- Лексический fallback требует двух точных содержательных слов из названия ОКВЭД в тексте claim. Для проверенных профилей этого нет. Сам по себе этот fallback даёт только 10 базовых баллов, ниже обычного порога ленты 0.15, поэтому не является полноценным семантическим каналом.
- У Домодедово `entity_id=null`; нет доверенного сопоставления с ID компании. Канал прямой связи и переход к её платёжным соседям не срабатывают. Построение платёжного графа само по себе эту неизвестность не устранит.
- Два bundle оцениваются независимо. Связанный контекст статьи автоматически не собирается.
- Аналитик не спасает событие после отбора: в этой пробе до него нечего передавать. Кроме того, текущий генератор — fixture, не работающая рассуждающая LLM.

Наш API оценивает события **для переданного профиля**, а не возвращает сразу список подходящих компаний всей базы. В проверке он вызывался для 14 профилей. Отдельный поиск candidate companies по всей базе пока не реализован.

## 4. Что необходимо добавить

1. Согласовать транспорт массива/JSONL, принять v0.2 без потери полей и привести timestamps к согласованному RFC3339.
2. Добавить канал кандидатов для операционных событий: нормализованные сущности/отрасли/тип операции и согласованные связи с профилями. Для бейслайна это может быть явное правило авиационной релевантности; для широкой предметной области потребуется расширяемый семантический отбор, а не одно исключение под Домодедово.
3. Подтягивать соседние факты статьи для выбранного кандидата, чтобы агент видел и основное событие, и объяснение причин.
4. Передать кандидатов живому аналитику с профилем; явно различать прямую связь, отраслевую гипотезу и подтверждённую экспозицию компании.
5. Проверить позитивные и негативные примеры: авиаперевозчик с операциями через этот аэропорт, компания без подтверждённой связи с ним, обычный ИТ-бизнес. Целевые оценки должны быть заданы человеком, а не взяты из нынешнего результата ранкера.

Из исходной новости нельзя сделать вывод о закрытии аэропорта, отменах или задержках. Даже для авиационной компании релевантность не означает установленный ущерб: в тексте недостаточно информации о масштабах и длительности режима.

## Воспроизведение

```bash
uv run --frozen python -m scripts.check_airport_example \
  --input '/home/pavel/Загрузки/Telegram Desktop/output-b6.json' \
  --output data/processed/personalization/airport-example-check.json
```

Скрипт требует локальный CSV компаний; подробные результаты с реальными ID сохраняет только в игнорируемую директорию. Диагностическое создание StoredEvent не должно использоваться в production вместо строгого импорта.
