# План разработки нового ретривера

Дата: 24 октября 2026. Статус: план реализации для GPT-6.1 Sol.
Основание: обсуждение с командой, текущие форматы парсера и кластеризации,
описание интерфейса `llm.cluster_merge`, переданное автором модуля.
В рамках подготовки документа код нового ретривера не реализовывался.

## 1. Назначение и границы

Ретривер отбирает кандидатов для последующей LLM-аналитики в контексте компании.
Поисковое сходство задаёт порядок рассмотрения кандидатов, а не бизнес-важность.
Последняя определяется отдельным аналитическим модулем после ретривера.

```text
Публикации + готовые векторы + предварительные кластеры
                           ↓
Готовые интересы компании → поиск по эмбеддингам
                           ↓
Очередь по максимуму сходства с интересами
                           ↓
Кандидат из необработанного кластера?
     нет → обычный отбор
     да  → готовый результат / merge_cluster при необходимости
                           ↓
Новые векторы через внешний encoder → атомарная замена представлений
                           ↓
Продолжение отбора до k или явного ограничения
                           ↓
Пакет событий, источников и оснований → LLM-аналитик → итоговый рейтинг
```

В первую версию входят: загрузка входов, точный семантический поиск, очередь,
интеграция lazy merge, хранилище состояния, пакет аналитику и диагностика.

За пределами этой реализации: обучение моделей, генерация интересов, массовый
расчёт векторов, создание исходных кластеров, обработка CSV компаний и платежей,
реализация бизнес-аналитика и его итогового рейтинга, интерфейс пользователя.
BM25, RRF, reranker и квоты по интересам — последующие измеряемые улучшения;
в основной путь MVP их не включать.

## 2. Что уже имеется и что ещё нужно получить

| Компонент | Фактическое состояние | Действие |
|---|---|---|
| `news/core/model.py` | Семь полей сырой статьи | Использовать формат через собственный небольшой адаптер |
| Подготовленный корпус | Есть ID редакций, хеши, provenance | Поддержать импорт без зависимости от старых NLP-стадий |
| Кластеры эксперимента | Группы фрагментов/документов; возможны пересечения | Проверить членство, не объявлять группы установленными событиями |
| Векторы новостей и интересов | Есть локальные BGE-M3 артефакты | Использовать через входной контракт; массовый расчёт ведёт другой разработчик |
| `merge_cluster` | По описанию коллеги реализован; в текущем checkout отсутствует | Найти точный коммит, перенести минимальный модуль и проверить API/тесты |
| Старый `retriever/` | B6-путь плюс большой экспериментальный код | Переносить только необходимые независимые функции после проверки зависимостей |
| Новый цикл отбора и применение merge | Не реализованы в выделенном чистом модуле | Основная работа по этому плану |
| Вход аналитика | Старый B6-адаптер и экспериментальный raw-адаптер | Согласовать новый небольшой контракт; совместимость не предполагается |

Описание коллеги — спецификация ожидаемого поведения, а не результат аудита
его кода. До переноса сверить фактические поля, статусы и методы.

## 3. Ветка и состав переноса

1. Получить актуальные remote refs, зафиксировать SHA `origin/main` и коммита
   автора merge. Проверить, существует ли уже командная ветка `retriever`.
2. Создать `retriever` от согласованного `main`, предпочтительно в отдельном
   worktree. Если ветка уже создана командой — продолжать её без force/reset.
3. Сохранить текущую экспериментальную ветку и все её незакоммиченные файлы.
   Не выполнять checkout поверх чужих или незавершённых изменений.
4. Перенести `llm/cluster_merge/`: реализацию, минимальные зависимости, схемы,
   синтетические тесты, пример, документацию и необходимые лицензии.
5. Добавлять новый `retriever/` поэтапно. Не cherry-pick целиком коммит, который
   тянет старые NLP-стадии, отчёты и несвязанные зависимости.
6. Проверить импорт и запуск в чистом окружении Python 3.13+, без GPU и весов
   для обычного поиска и офлайн-тестов.

В Git: код, контракты, синтетические fixtures, документация, агрегатные отчёты.
Локально: новости, профили, платежи, векторы эксперимента, запросы/ответы API,
SQLite, кэши, ключи и веса. Не переносить их в коммит.

## 4. Контракты входа

### 4.1. Исходная редакция публикации

`ArticleRevision`:

- `revision_id` — неизменяемый ID точной редакции; для подготовленного корпуса
  можно использовать `document_id`;
- `article_id` — внешний ID статьи парсера, не идентификатор редакции;
- `text`, `text_sha256`, `title`, `title_origin`, `source`, `url`, `language`;
- `published_at`, `publication_precision`, исходное выражение даты;
- `observed_at` — фактическое время получения, если оно известно;
- `provenance` и статус извлечения/допустимости текста.

ID парсера зависит от URL и не меняется при правке текста. При изменении
содержимого нужна новая редакция. Пустой/непригодный текст не кодировать как
полноценную статью; причину исключения сохранять. Не отбрасывать длинные статьи
по экспериментальному правилу «больше 2000 символов»: политику фрагментов
передаёт поставщик векторов, все исходники остаются доступны merge.

### 4.2. Поисковый объект

`SearchItem`:

- `item_id`, `item_version`, `kind=article|event`;
- `embedding_text`, его хеш, ссылка на вектор;
- `encoder_fingerprint`, `dimension`, `dtype`, `normalization`;
- `source_revision_ids`, `derived_from` — ссылки на исходники и операцию merge;
- признаки доступности и временное происхождение;
- для результата merge: ID событийного объекта и условия его применения.

Один источник может обосновывать несколько разных событий. Поэтому не считать
совпадение `source_revision_ids` достаточным основанием для удаления результата.
Не хранить в глобальном объекте score, позицию триггера или компанию.

Если статья представлена несколькими векторами-фрагментами, все они указывают
на один `item_id`. Сначала брать лучший фрагмент на интерес, затем лучший
интерес на объект. Один документ не занимает несколько мест за счёт фрагментов.

### 4.3. Интересы компании

`CompanyInterestSet`:

- `company_id`, `profile_version`, `interest_set_version`;
- интересы: `interest_id`, самостоятельный текст и хеш, вектор/ссылка на него;
- `family=activity|graph|other`, происхождение, условие применимости;
- явно переданный статус активации темы и основание применимости;
- точный профиль encoder и версия политики подготовки текста.

Ретривер получает уже выбранные активные интересы; он не придумывает сферы,
не подтверждает условные темы и не интерпретирует платежи как поставки.
Не усреднять интересы. Для MVP все переданные активные интересы участвуют в
`max cosine`; граф включается отдельной конфигурацией запроса. Весовые схемы
и разнообразие сравнивать позднее при сохранении исходных оценок.

### 4.4. Снимок кластера

`ClusterSnapshot`: `cluster_id`, строковая `revision`, `member_revision_ids`,
канонический `membership_hash`, происхождение алгоритма группировки,
снимок корпуса и условия доступности. Список участников упорядочен
детерминированно. Число публикаций считается по уникальным редакциям, не фрагментам.

Кластер — предварительная группа. Дату публикации не назначать датой события.
Не подменять полный состав кластера найденными top-k публикациями.

### 4.5. Векторы

У матрицы есть отображение строк на версии объектов, хеши и точный fingerprint.
Совпадения размерности недостаточно. Проверять конечность значений, размерность,
L2-нормы, полноту ID и версии текстов. Несовпадение профиля — явная ошибка,
без автоматической смены модели или смешивания пространств.

Ожидаемый основной профиль — закреплённый BGE-M3, 1024 измерения. Конкретный
fingerprint принимает конфигурация снимка, а не случайная локальная модель.

## 5. Алгоритм поиска MVP

1. Открыть согласованный снимок активных объектов и интересов компании.
2. Применить заявленные ограничения доступности/временного окна. Не угадывать
   timezone и не выдумывать историческое время получения. Политику неизвестных
   дат фиксировать в запросе и трассе.
3. Для нормализованных векторов вычислить `Q @ D.T` блоками. Не требуется
   выделять всю матрицу интересы × весь корпус в памяти.
4. Для каждого объекта получить лучший score по фрагментам и интересам.
   Сохранить найденные интересы и исходные оценки, а не только максимум.
5. Сортировать по `(-score, item_id)`. Среднее по интересам не использовать.
6. Предоставить расширяемую очередь до исчерпания допустимых объектов. Не
   обрезать её необратимо до первых k до обработки повторов.
7. Для небольшого корпуса первая реализация — точный поиск. ANN/vector DB
   добавляются по измерению, за тем же интерфейсом.

Число k конфигурируется, пример для эксперимента — 50. Наличие k не является
обещанием k качественных событий. Универсальный порог cosine не задаётся без
разметки; режим без порога явно обозначается.

## 6. Ленивый merge в цикле отбора

Для очередного кандидата, который может попасть в пакет:

1. Проверить актуальность его версии и отсутствие уже выбранного того же
   канонического события. Обработанные поисковые события не отправлять
   повторно на merge из-за сохранённой ссылки на исходный кластер.
2. Одиночную публикацию без нуждающегося в обработке кластера добавить по
   обычным правилам бюджета.
3. Получить полный актуальный `ClusterSnapshot`. Если он уже разрешён для
   данного состава и профиля, применить/прочитать сохранённый результат.
4. Если операция идёт у другого исполнителя — использовать её ID. Ожидать
   только в пределах deadline запроса; второй LLM-запрос не создавать.
5. Если нужен новый merge — передать снимок и триггер в сервис коллеги.
6. Применять только `completed`. Частичный ответ не меняет активный индекс.
7. Подготовить векторы всех выходных `embedding_text` через внешний encoder.
8. Атомарно применить результат по правилам раздела 8.
9. Обновить очередь и предварительно выбранный набор; продолжать до k либо
   ограничения контекста, времени, вызовов или числа обновлений индекса.

На запрос хранить `seen_event_ids`, рассмотренные пары cluster/revision,
отложенные операции и лимит перестроений. Это исключает цикл на одной ошибке,
повторный merge `unchanged` и бесконечное повторение после split.

| Результат сервиса | Действие текущего запроса |
|---|---|
| `merged` | Один объект может наследовать score и место допущенного триггера |
| `split` | Все выходные объекты оценить по интересам заново, очередь перестроить |
| `unchanged` | Сохранить разрешённость этой revision, продолжить обычный поиск |
| Не завершён / ошибка / превышен лимит | Индекс не менять, сохранить причину и operation ID |

Наследование места при `merged` — явно выбранная эвристика только текущего
запроса. В трассе различать `selection_score` триггера и cosine нового объекта.
Следующий запрос оценивает новый вектор обычным способом. Не переносить
персональную позицию из кэша результата другой компании.

После split не все дочерние события обязаны попасть в выдачу. Если разделение
включает исходники с несколькими событиями, не дедуплицировать их только по
совпадающим источникам.

## 7. Пересекающиеся кластеры — обязательное решение до интеграции

Текущий эксперимент группировал фрагменты; в полном корпусе 155 документов
попадают более чем в одну группу. Однозначный `article → cluster_id` здесь неверен.

Для MVP принять явное ограничение: автоматически применять merge только для
кластеров с непересекающимся владением исходными редакциями в выбранном снимке.
Импортёр обязан выявлять неоднозначные членства.

- Не назначать первый встретившийся кластер произвольно.
- Не объединять пересекающиеся группы автоматически по транзитивному замыканию.
- Группы с пересечениями помечать `ambiguous_membership` и не изменять по ним
  поисковые представления. Их публикации доступны в явно диагностическом
  режиме raw fallback; по умолчанию такой fallback выключен.
- Перед контрольным экспериментом получить от автора кластеризации согласованный
  непересекающийся снимок либо отдельно реализовать многозначное владение с
  инвалидацией затронутых кластеров. Не объявлять проблему решённой импортом.

Ограничение касается исходных предварительных кластеров, а не запрета одному
источнику обосновывать несколько событий после корректного split.

## 8. Хранилище и атомарное применение

Архив редакций неизменяем. Активные поисковые представления — отдельный слой.
Для первой версии допустим SQLite с метаданными и vector BLOB в одной
транзакции; индекс-матрица в памяти обновляется по `index_generation`.
Другая реализация допустима за теми же портами, если сохраняет атомарность.

Порядок применения:

1. Вне блокировки получить сохранённый полный результат и закодировать все
   выходные тексты. Проверить их ID, состав источников, нормы и fingerprint.
2. Начать короткую транзакцию. Проверить revision, membership hash, версии
   исходников и ожидаемые активные представления.
3. При несовпадении сохранить `stale_application`, ничего не заменять.
4. Проверить `application_id`: уже применённый результат — успешный no-op.
5. Записать все новые объекты и векторы, ссылки на исходники, результат
   операции; выключить только заменяемые представления.
6. Зафиксировать состояние cluster/revision и увеличить `index_generation`.
7. Commit. Затем обновить матрицу/очередь по новому поколению индекса.

Не держать транзакцию во время API и GPU-кодирования. Сбой кодирования любого
выходного объекта оставляет весь старый состав активным. Потеря процесса после
commit не требует второго API-вызова. Новые членства кластера создают новую
revision: одной транзакцией инвалидировать прежнюю применимость и восстановить
поисковые оригиналы нужных редакций; готовые старые карточки остаются в архиве.

В первой версии работать по явно зафиксированному снимку корпуса. Историческую
корректность не заявлять при неизвестной доступности исходников/профиля.
Карточку с будущим источником не использовать для более раннего `as_of`.
Для иного допустимого набора источников нужен иной снимок состава, а не
повторное применение карточки, прочитанной из будущего.

## 9. API и ответственность разработчиков

Предлагаемые порты нового ретривера:

```python
class SearchStorePort:
    def snapshot(self, request): ...
    def iter_vector_blocks(self, snapshot, max_rows): ...  # (item_refs, matrix)
    def get_sources(self, revision_ids): ...
    def get_cluster_snapshot(self, cluster_id, snapshot): ...
    def apply_merge(self, expected, result, encoded_items): ...

class EmbeddingProviderPort:
    fingerprint: str
    dimension: int
    def encode_event_texts(self, texts): ...

class MergePort:
    def plan(self, snapshot, trigger_id, profile): ...
    def resolve(self, snapshot, trigger_id, profile, *, max_calls): ...

class RetrieverService:
    def retrieve(self, request, *, interests, store, merge, encoder): ...
```

`MergePort` — тонкий адаптер готового `MergeService`, а не вторая реализация
пакетирования, промптов, heartbeat, квоты и восстановления. Методы коллеги:
`plan_merge`, `merge_cluster`, `resume_merge`, `get_merge_result`; точные
сигнатуры сверить в полученном коммите.

| Ответственный | Что поставляет |
|---|---|
| Автор merge | Код сервиса, профиль, схемы результата, сохранение операции и запросов |
| Автор эмбеддингов/интересов | Векторы и метаданные, активные интересы компании, encoder для новых событий |
| Автор кластеризации | Составы и ревизии, происхождение, решение о пересечениях |
| Разработчик ретривера | Контракты/адаптеры, точный поиск, очередь, вызов merge, атомарное применение и пакет |
| Автор аналитика | Приём пакета, компания-контекст, анализ и итоговая значимость |

Вход `RetrievalRequest`: request ID, company/profile/interest-set versions,
снимок корпуса, as_of/временная политика, k, профиль merge и лимиты запроса.

Выход `RetrievalCandidateBatch.v1`: статус `ready|partial|empty`, количество
запрошенных/возвращённых кандидатов, причины неполноты, версия индекса и
конфигурации; уникальные события с текстами, источниками, интересами и scores;
merge operation IDs, тип применения, число публикаций и различных источников;
ссылки на исходники, ограничения и ссылка на trace. Названия здесь предложены,
схему зафиксировать с потребителем до реализации.

Профиль компании передаётся/ссылается отдельно; поисковые гипотезы и графовые
основания не превращаются в подтверждённые факты. Размер кластера отражает
распространённость публикаций, а не независимые подтверждения или важность.

Пример структуры реализации:

```text
retriever/
  models.py          # публичные контракты
  ports.py           # store, merge, encoder
  importers.py       # parser/prepared corpus/vector manifest
  search.py          # exact cosine и очередь
  selection.py       # цикл lazy merge и добор
  merge_adapter.py   # интеграция сервиса коллеги
  store.py           # reference SQLite backend
  output.py          # пакет аналитику и trace
  __main__.py        # import, validate, retrieve, inspect
  tests/fixtures/    # синтетические данные
```

## 10. Лимиты, сбои и передача аналитику

- По умолчанию офлайн-режим: ноль новых API-вызовов; сохранённые результаты
  можно читать. Live требует настроенного профиля, общего резервирования и
  явного `max_new_llm_calls`.
- Кроме k ограничить время запроса, число merge-операций/перестроений и
  размер полного пакета аналитику. Один merge может потребовать несколько API
  запросов: резервировать каждый через общий лимитер сервиса.
- Не создавать новый общий бюджет при открытии нового индекса. Адаптер квоты
  должен соответствовать реальному общему шлюзу команды.
- Не выполнять автоматический HTTP retry, JSON repair, смену модели или
  сброс резерва при неизвестном исходе. Следовать семантике сервиса коллеги.
- Для busy/failed/incomplete кластеров продолжать независимых кандидатов в
  пределах лимитов; возвращать `partial` с причинами и operation IDs, если
  нужный результат не собран. Не добивать k повторами ради количества.
- Raw fallback — отдельный диагностический флаг, по умолчанию выключен.
  Он не обещает устранения повторов и всегда отражается в результате.
- Бюджет аналитика учитывать по полному сериализованному входу. При известном
  tokenizer применять его; байтовую оценку явно помечать приближённой.
  Не обрезать молча тексты/основания. Неуместившийся объект пропустить с
  причиной и продолжить допустимый добор.
- После собственных или конкурентных изменений перепроверять активность
  предварительно отобранных версий. Финальный пакет соответствует указанному
  согласованному поколению индекса; число повторных сборок ограничено.

LLM-анализ и итоговая сортировка не вызываются внутри `retrieve`. Модуль
публикует кандидатов и контекст для отдельного этапа.

## 11. Переиспользование старого кода

Можно извлечь после проверки зависимостей:

- блоковый cosine/top-k и стабильную сортировку из `raw_search.py`;
- проверки векторов, exact-text ключи кэша и контрольные суммы;
- идеи trace и бюджетирования, синтетические тестовые сценарии.

Не переносить целиком: B6-модели, eligibility по claims/evidence, структурный
поиск по B6 taxonomy, E5/ONNX runtime, старую сборку company snapshots,
экспериментальные runner/report/analyst модули и reranker.

В старом коде встречаются фиксированные 384 измерения. В `raw_ports.py` и
`raw_search.py` ранее расходился порядок `(matrix, ids)` / `(ids, matrix)`.
В новом интерфейсе установить один порядок и проверить реальным адаптером.
Тесты новой ветки должны работать без импорта старых `llm/events`,
`llm/event_pipeline` и B6-адаптеров. Не создавать копию общего LLM-клиента.

## 12. Этапы разработки и приёмка

### Этап 1 — чистая ветка и сервис merge

Перенести готовый модуль коллеги, зафиксировать исходный коммит и зависимости.
Прогнать его тесты, проверить генерацию схем и dry plan без сети.

Приёмка: изолированный импорт и офлайн-пример; нет зависимостей от старых
NLP-стадий; ключи/базы/оригиналы отсутствуют в коммите.

### Этап 2 — контракты, импорт и поисковое хранилище

Зафиксировать схемы с владельцами входов и аналитика. Импортировать исходники,
векторы и кластеры с проверкой хешей, ID редакций и членства. Реализовать
reference store и синтетический корпус. Выдать отчёт по пересечениям.

Приёмка: правка исходника создаёт новую редакцию; отсутствующие векторы и
неподходящий fingerprint не проходят; неоднозначные кластеры не применяются;
оригиналы не теряются при повторном импорте и сбоях.

### Этап 3 — поиск без новых LLM-вызовов

Блоковый `max cosine`, сведение фрагментов, стабильная очередь, k и trace.
Одиночные новости и уже подготовленные событийные объекты проходят один путь.

Приёмка: результат совпадает с прямым матричным oracle на маленьком корпусе;
важный кандидат по одному интересу не теряется из-за среднего; ties стабильны;
пустые интересы/корпус, фрагменты и нехватка кандидатов имеют явные результаты.

### Этап 4 — lazy merge и атомарное применение

Подключить fake MergePort, затем адаптер реального сервиса. Реализовать все
ветви таблицы, кодирование выходов через DI, idempotent apply, generation
refresh и ограничения повторного рассмотрения.

Обязательные сценарии:

1. N одно-событийных публикаций схлопываются в один объект; добор идёт дальше
   исходной границы k, источники доступны.
2. Повторный запрос/другая компания используют готовый общий результат;
   персональные scores не переносятся между компаниями.
3. Split создаёт несколько событий; их новые scores меняют очередь, и слабые
   дочерние события могут не попасть в пакет.
4. Один исходник поддерживает два события: они не удаляются как дубликаты.
5. `unchanged` не вызывает LLM заново для каждого участника той же revision.
6. Incomplete, отказ, transport failure и исчерпание лимита не меняют индекс.
7. Ошибка encoder на одном дочернем объекте не применяет остальные частично.
8. Revision меняется во время API/encode: CAS отклоняет устаревшее применение.
9. Два запроса к одному кластеру не создают два независимых API-вызова и не
   применяют результат дважды.
10. Сбой после ответа/commit восстанавливается по сохранённым артефактам.
11. Пересечение кластеров не приводит к произвольному удалению публикаций.
12. Результат с будущими источниками не попадает в более ранний снимок.

### Этап 5 — пакет аналитику и командная интеграция

Добавить CLI, итоговую схему пакета, пример вызова из приложения и контрактный
тест с новым потребителем. Передать владельцу эмбеддингов спецификацию encoder
и индексного импорта. Зафиксировать поведение бюджетов/partial.

Приёмка: fake аналитик получает полные ссылки и основания; реальный старый
B6-адаптер не используется как будто он совместим автоматически. Ни одного
неучтённого вызова API в обязательном тестовом прогоне.

### Этап 6 — измерение и ручная оценка

На фиксированном разнообразном пуле компаний сравнить при одинаковом бюджете:
семантический отбор без обработки групп и тот же отбор с lazy merge. На реальных
кластерах live запускать после готовности точного профиля и общего лимитера;
сохранять запросы, ответы, usage, время и ошибки в локальных артефактах.

Измерять:

- полноту по известным полезным событиям, шум, покрытие интересов;
- повторы в пакете, число уникальных событий, ошибочные merge/split и потерю деталей;
- размер пакета и оценённый/фактический расход аналитического контекста;
- cold/warm задержку поиска отдельно от encode и LLM;
- новые API-вызовы, cache hits, pending/failed, RAM/VRAM при наличии encoder;
- время и причины прекращения добора, stale применения и перестроения.

Размечать объединённые результаты вариантов, трудные отрицательные примеры и
контрольные пропуски. Рецензент читает исходники и профиль компании. Метки
агента не называть независимым человеческим эталоном. Если нет полного эталона,
не заявлять абсолютную полноту; разделить разработку и проверку по семействам
событий. Порогов превосходства без измерений не назначать.

## 13. Готовность первой версии

Готовность означает: чистая командная ветка; самостоятельные контракты и
адаптеры; точный поиск; ленивый вызов готового merge; атомарные и повторяемые
изменения; ограниченный добор с объяснимыми partial; согласованный пакет
аналитику; офлайн-приёмка и воспроизводимая диагностика.

Это не означает доказанную полноту поиска, идеальную кластеризацию, корректность
всех LLM-выводов или завершённую персональную аналитику. Результаты оценки и
ограничения публикуются отдельно от технической приёмки.
