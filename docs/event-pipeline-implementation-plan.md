# План завершения llm/event_pipeline

Дата: 2026-10-23. Основание: ветка `news-pipeline-clean`, коммит `61b52a3`.
Документ задаёт работу следующему исполнителю. Изменения реализации в рамках подготовки плана не выполнялись.

## 1. Цель и границы первой версии

Получить воспроизводимый экспериментальный каталог конкретных событий из явно выбранного снимка новостного корпуса. Каждый результат должен объясняться исходными фрагментами и сохранёнными решениями обработки.

```text
prepared-news.v1 + выбор document_id
  → проверка снимка и неизменяемый план
  → точные блоки текста
  → минимальные упоминания событий
  → поиск похожих ранее рассмотренных упоминаний
  → проверка принадлежности существующим кластерам
  → кластеры + одиночные записи + неразрешённые соответствия
  → JSONL, аудит покрытия, расход, оценка
```

Пять сообщений об одном установленном заседании могут образовать один кластер. Сообщения о двух разных заседаниях, даже с одинаковой ставкой, должны остаться разными событиями. При недостаточных основаниях система сохраняет неопределённость.

Неизвестные дата события, участник, единица измерения или модальность не являются причиной отбрасывания упоминания с корректными ссылками на источник. Дата публикации не назначается датой события.

Персонализация для компании, банковский RAG, рекомендации, обогащение строгих событий, адаптер B6, автоматическое объединение/разделение готовых кластеров и повторная проверка старых решений — последующие этапы. Их не включать в приёмку этой версии.

Реализацию и обязательную приёмку проводить без реальных API-вызовов. Live-эксперимент — отдельная работа после офлайн-приёмки с согласованными профилями и общей квотой.

## 3. Общие правила реализации

1. Продолжать существующий модуль; не создавать второй параллельный пайплайн.
2. Предметные модели не наследуют `SourceClaim` и не проходят обязательную B4-нормализацию.
3. Переиспользовать архив, задания, попытки, транспорт, heartbeat и учёт через `runtime.py`. Не копировать их в новый общий пакет.
4. Не менять старые базы B1–B6 и их версии схем ради нового модуля.
5. Артефакты запусков хранить в исключённом из Git `data/processed/event_pipeline/`. Полные тексты, ручные выгрузки и сырые ответы не коммитить.
6. Каждая часть завершается проверяемым результатом и отдельным логическим коммитом. Не переходить к настройке качества, пока не закрыты ошибки корректности.

## 4. Порядок выполнения

### Шаг 1. Закрыть дефект объединения и рассинхронизацию схем

Файлы: `clustering.py`, `pipeline.py`, `models.py`, `checks.py`, `schemas/`, тесты.

Как делать:

1. Сначала добавить интеграционный тест: проверяющий возвращает `same`, но не указывает упоминание или исходные блоки одной из сторон. Сейчас такой ответ может привести к объединению.
2. Проверять ответ во временной структуре. Список, который допускается передать в `attachment`, публиковать только после всех проверок формата, полноты и ссылок относительно конкретной пары.
3. При ошибке сохранять сырой ответ, артефакт, причину и кандидатов. Новое упоминание оставлять отдельно со статусом `unassessed`; содержимое старого кластера не менять.
4. Повторить тест для неизвестных ID, ссылок на третий кластер, пропущенного кандидата, дубликата кандидата и пустого списка решений.
5. Согласовать модели со сгенерированными схемами. Источник схем — модели; проверка дрейфа должна входить в приёмку.

Результат: отклонённое решение физически не может изменить членство.

Приёмка: исходный воспроизводимый дефект закрыт новым тестом; `check` проходит; прежние сценарии допустимого объединения, включая числовой конфликт, продолжают работать.

### Шаг 2. Зафиксировать контракты и состояния запуска

Файлы: `models.py`, `pipeline.py`, `output.py`, `schemas/`.

Как делать:

1. Добавить собственные версии шести публичных контрактов: SourceBlock, EventMention, ExtractionAudit, MembershipDecision, EventCluster и RunManifest.
2. В RunManifest фиксировать корпус, выбранные редакции, конфигурацию, отдельные профили извлечения/проверки, версии реализации/промптов/схем, фазу, порядок и состояние полноты.
3. Для упоминания сохранять путь к документу и его хэшу, основания, диагностические сообщения и происхождение каждого принятого повтора. Полный исходный ответ остаётся отдельным артефактом.
4. Для решения сохранять новое упоминание, ID/версии/состав кандидатов на момент запроса, решения по кандидатам, основания, итог применения и ссылку на API-артефакт.
5. Разделить завершение обхода, полноту обработки и определённость результата. `uncertain` при успешно выполненной проверке — допустимый законченный результат. Ошибка API, неразобранный пакет, слишком большой контекст или пропущенная работа означают ограничение полноты.
6. Явный переход к кластеризации частичного извлечения разрешать только через `allow_partial`; записывать это решение в manifest.
7. После перехода закрепить хэш набора упоминаний и их порядок. Позднее добавление упоминаний требует нового запуска кластеризации.

Предлагаемые состояния:

| Объект | Состояния |
|---|---|
| Пакет извлечения | pending, succeeded, failed, deferred |
| Покрытие блока | with_mentions, excluded, processed_without_mentions, skipped, deferred |
| Проверка нового упоминания | not_required, assessed, uncertain, unassessed |
| Запуск | фаза обработки отдельно от processing_complete и ограничений полноты |

Названия можно согласовать с существующими полями, сохранив эти различия.

Приёмка: manifest, JSON Schema, CLI status и экспорт одинаково трактуют состояния. Ошибочный или отложенный пакет не выдаётся за полностью обработанный документ.

### Шаг 3. Довести вход, блоки и упаковку запросов

Файлы: `pipeline.plan_run`, `blocks.py`; существующий `llm/events/corpus/` переиспользовать.

Как делать:

1. Проверить manifest подготовленного корпуса, хэши выходных файлов и документов, валидность ArticleInput и полей provenance. Один article_id с несколькими редакциями требует выбора одной редакции.
2. Сохранять точность даты и происхождение заголовка. Технический Telegram-заголовок не использовать как доказательство события.
3. Формировать детерминированные блоки заголовка и абзацев с координатами `[start,end)` в Python Unicode. Проверять точное равенство среза исходному тексту.
4. Ограничить размер блока 2000 символами. Делить длинные абзацы по предложениям, затем пробелам; длинную неразрывную последовательность обрабатывать явно, с диагностикой.
5. Сохранять табличный текст и доступные заголовки; неоднозначную структуру отмечать, не восстанавливать таблицу по догадке.
6. Формировать до 8000 символов основных блоков, соседей с обеих сторон, содержательный заголовок и метаданные. Настройки сохранять в плане.
7. Проверять размер полного сериализованного запроса, включая промпт, схему, метаданные и контекст. Проверку ограничений модели выполнять подтверждённым способом; не считать число символов числом токенов.
8. Слишком большой пакет делить до отправки. Если один блок с необходимым контекстом не помещается, откладывать его без обрезания.
9. Порядок: известная дата публикации, document_id, позиция упоминания. Дату без времени хранить отдельным календарным ключом; неизвестные даты — последними. Для упоминания с основаниями в заголовке и тексте использовать явный порядок полей, а не сравнивать несопоставимые координаты.

Приёмка: Unicode, emoji, NBSP, таблицы, длинные абзацы, технические заголовки и даты без времени покрыты тестами. После сохранения и загрузки плана состав пакетов и порядок не меняются.

### Шаг 4. Завершить минимальное извлечение и аудит

Файлы: `extraction.py`, извлекающая часть `pipeline.py`, `runtime.py`, тесты.

Как делать:

1. Модель выбирает готовые block_ids; цитаты и координаты берёт код из SourceBlock. Обязателен непустой список существующих блоков, включая хотя бы один основной блок пакета.
2. gloss и подсказки участников, автора, действия, объекта, времени, значений, категории и модальности оставить необязательными. Ошибки этих полей сохранять в сыром ответе и диагностике, не уничтожая корректные основания.
3. Неверные обязательные ссылки отклоняют одну запись. Неразбираемый JSON и `finish_reason=length` отклоняют пакет; остальные пакеты могут продолжаться.
4. Принимать голый JSON или единственную полную Markdown-оболочку. Не добавлять автоматический repair.
5. Разрешить несколько событий в одном блоке. Нулевой результат помечать как результат извлечения, не как доказательство отсутствия событий.
6. Одинаковые записи из пересечений пакетов объединять только в пределах одной редакции и с объединением происхождения. Не перезаписывать сведения о первом пакете последним повтором. Не схлопывать разные сырые записи только потому, что их ошибочные необязательные поля были отброшены.
7. По каждому основному блоку формировать аудит покрытия; отдельно хранить причины отказов и исходные исключения.
8. Успешный ответ провайдера сохранять до разбора и применения результатов. После сбоя между этими стадиями повторно использовать артефакт.

Приёмка: упоминание без даты/единицы/участника сохраняется; одна плохая запись не удаляет хорошие; одинаковые тексты разных документов не объединяют события; повтор не теряет provenance; аудит объясняет судьбу всех блоков.

### Шаг 5. Зафиксировать поиск кандидатов

Файлы: `retrieval.py`, конфигурация и отчёт запуска, `pipeline.retrieve_candidates`.

Как делать:

1. Искать только по уже рассмотренным в текущем запуске упоминаниям, включая одиночные и неопределённые.
2. Первое представление — исходные блоки с контекстом; второе — gloss с доступными подсказками. Пересказ не заменяет исходные блоки.
3. Закрепить `k1=1.2`, `b=0.75`, Unicode-токенизацию, casefold и версионированный небольшой список стоп-слов. Числа и короткие обозначения сохранять.
4. Брать top20 каждого представления, объединять RRF с константой 60. Для кластера брать максимальную оценку его участника, затем top8 кластеров. Равенства разрешать стабильными ID.
5. Не вводить обязательных фильтров по категории, источнику, близости даты или равенству чисел.
6. Сохранять параметры, найденные mention_id, позиции/оценки каждого представления, итог RRF, переход к кластерам и потери при ограничениях.
7. Сохранить CandidateRetriever как границу заменяемого поиска. Проверить поведение `retrieve_candidates` до кластеризации, на следующей позиции и на завершённом запуске; не придумывать отсутствующие memberships.

Приёмка: числовой конфликт, одинаковый источник и неизвестная дата не блокируют выдачу. Пограничные случаи top20/top8 и равные оценки воспроизводимы. Отчёт не называет score вероятностью идентичности.

### Шаг 6. Завершить проверку и применение принадлежности

Файлы: `clustering.py`, кластеризующая часть `pipeline.py`, fixtures идентичности.

Как делать:

1. Для нового упоминания передавать всех отобранных кандидатов с основаниями всех участников, метаданными, подсказками и сохранёнными решениями. Повторяющийся текст можно передавать один раз со списком ссылок.
2. Проверять полноту контекста перед вызовом. Если проверка кандидата не помещается, явно фиксировать `unassessed`; не выбирать несколько удобных участников большого кластера. Любой непроверенный конкурент препятствует однозначному присоединению.
3. Требовать по каждому проверяемому кандидату identity, claim_compatibility, ссылки на упоминания/блоки и краткое основание.
4. Проверять ровно один ответ на кандидата, допустимые значения и ссылки на обе стороны именно этой пары. Блоки другого кандидата не могут подменить основания текущего.
5. Применять только полностью проверенный набор решений по следующей таблице.

| Ответ | Применение |
|---|---|
| Кандидатов нет | Новый отдельный кластер; проверка не требовалась |
| Все different | Новый отдельный кластер |
| Один same, остальные different | Присоединение к единственному кластеру |
| Несколько same либо конкурент uncertain | Отдельный кластер и неразрешённые соответствия |
| Неполный/ошибочный ответ, непоместившийся кандидат или API-ошибка | Отдельный кластер со статусом unassessed и причиной |

6. Числовой конфликт при установленной идентичности сохранять как `conflicting`, не выбирать верное число.
7. Оформить инструкцию идентичности с положительными, отрицательными и неопределёнными примерами. Проверить разные заседания, периоды, авторов/выпуски прогнозов, стадии, исходную оценку и официальный пересмотр.
8. Не выполнять автоматическое объединение двух ранее существовавших кластеров, разделение или пересмотр старых решений.

Приёмка: каждая принятая запись либо входит в кластер, либо остаётся отдельно. Ошибка проверки не меняет членство. Отсутствующая дата не превращается в установленное заседание. Числовой конфликт сам по себе не запрещает объединение.

### Шаг 7. Проверить сохранность, возобновление и квоту

Файлы: `pipeline.py`, `runtime.py`; переиспользуемые B2 jobs/attempts/artifacts, OneShotRunner, RequestCounter и денежный ledger.

Как делать:

1. Оставить отдельную B2-базу выбранного запуска/снимка и отдельный каталог новой системы. Старые базы не мигрировать ради этой работы.
2. Каждый сетевой пакет оформлять отдельным заданием. Ключ кэша включает полный запрос, профиль/модель, промпт и схему; для membership — также новое упоминание, состав и версии кандидатов.
3. Сначала сохранять API-артефакт. Затем одной транзакцией каталога публиковать решение, новый состав/версию кластера и продвижение позиции. Существующая запись неизменяемого step может служить такой транзакционной границей, если из неё однозначно восстанавливаются все три компонента.
4. При resume восстанавливать состояние из сохранённых шагов; успешно выполненный запрос применять повторно идемпотентно. Не выпускать повторный запрос только из-за незавершённого изменения каталога.
5. Для незавершённой попытки без успешного артефакта явно показывать прерывание и израсходованный резерв. Не превращать обычный resume в скрытый retry.
6. Сохранить одного активного исполнителя на запуск. Проверить flock при конкуренции и освобождение после падения процесса; heartbeat и fencing B2 должны запрещать публикацию позднего ответа после потери попытки.
7. В кредитном эксперименте открывать только явно переданный существующий общий журнал. Новый каталог запуска не создаёт квоту. Резерв расходуется до отправки и не освобождается автоматически при сбое.
8. В денежном режиме сохранить действующие проверки тарифов, квоты и bounds. Способ использования общей командной квоты должен быть явным: нельзя объявлять локальный ledger одного запуска общей квотой команды.
9. На попытку — один запрос. Ошибки авторизации, 429, транспорта и квоты останавливают сеть с сохранением текущего результата. Без автоматического repair, retry, замены модели или формата.
10. `.env` читать только сетевым CLI. Ключи не включать в запросные артефакты, manifest, отчёты и ошибки.

Приёмка: тесты с временными базами, управляемыми часами и имитацией API покрывают сбой до/после ответа, сбой до/после транзакции, конкурентный запуск, исчерпание общей квоты, потерю аренды, поздний ответ и неизменность cluster_id при resume.

### Шаг 8. Согласовать CLI, экспорт и документацию

Файлы: `__init__.py`, `__main__.py`, `output.py`, `checks.py`, `README.md`, `context/event-pipeline-progress.md`.

Как делать:

1. Сохранить Python API: plan_run, extract_mentions, retrieve_candidates, cluster_mentions, resume_run, export_run, evaluate_run.
2. Проверить соответствующие CLI-команды и status/demo/check. Сетевым командам обязателен конечный положительный max-calls.
3. Сделать поведение resume явным: какая стадия продолжается, где происходит переход extraction → clustering и как пользователь фиксирует частичное извлечение. Если команда продолжает только текущую стадию, это должно быть видно в status и документации.
4. Экспортировать mentions.jsonl, clusters.jsonl, decisions.jsonl, manifest, отчёт и достаточные источники/артефакты для разрешения всех ссылок. Включать одиночные и ещё не проверенные mentions.
5. Проверять экспортируемые строки по их схемам. Не записывать под именем контракта произвольный step другой структуры без отдельной документированной схемы.
6. Публиковать экспорт через временный каталог и атомарное переименование; не перезаписывать готовый экспорт.
7. В отчёте показывать покрытие, отклонённые записи, неразрешённость, ограничения top-K, запросы, usage и расход. Для кредитов с неизвестными тарифами стоимость остаётся неизвестной, а не нулевой.
8. Метку кластера брать из исходного gloss или ID и помечать как навигационную; дополнительного LLM-резюме не делать.
9. Обновить README, схему пайплайна и короткую точку продолжения в context. Описать команды из чистого checkout и зависимости; runtime устанавливать по закреплённым версиям.

Приёмка: пользователь по инструкции строит offline demo, прерывает и продолжает его, проверяет схемы и открывает самостоятельный JSONL-экспорт. Частичность видна без чтения SQLite.

### Шаг 9. Подготовить ручной пилот и измерить качество

Файлы: `evaluation.py`, `output.evaluate_run`, тесты; конфиденциальные данные и разметка — локально.

Как делать:

1. Проверить наличие снимка, описанного в `context/cluster-first-progress.md`. Там зафиксированы 3621 документ и первый seed из одного события/шести пар; это историческое описание, наличие локальных файлов нужно подтвердить.
2. Выбрать примерно 40 документов: связанные сообщения из разных и одинаковых источников, одиночные события и трудные отрицательные/неопределённые пары. Синтетические fixtures оставить отдельным набором.
3. Вручную отметить исходные блоки/координаты упоминаний, идентичность, неопределённости и при необходимости конфликт содержания. Статус — `single_annotator_draft`.
4. Разделить development/check по семействам событий вместе с перепечатками и редакциями. Не использовать случайное разделение статей. Связанные трудные отрицательные случаи также учитывать при группировке split.
5. До настройки сохранить baseline. Не размеченные явно пары не считать отрицательными; неопределённые метки не превращать автоматически в different.
6. Измерить извлечение: пропуски, лишние mentions, сохранность неполных упоминаний. Совпадение блока считать показателем локализации; оно не доказывает правильность gloss и не заменяет ручное сопоставление событий, особенно если в блоке несколько событий.
7. Измерить поиск отдельно: задать вручную gold mentions, прогнать тот же BM25/RRF и посчитать Recall@K. Дополнительно показать поиск по реально извлечённым mentions, чтобы различать ошибку извлечения и поиска.
8. Измерить кластеризацию только по размеченным отношениям: ложные объединения/разделения, precision/recall и долю неразрешённых соответствий. Отдельно учитывать пары, потерянные на извлечении.
9. Свести запросы, токены, использование кэша и расход в отчёт. Указать размер и состав набора, версии конфигурации и ограничения разметки.
10. Скриптовый offline-провайдер использовать для проверки исполнения по заданным ответам. Его совпадение с эталоном не является измерением качества LLM. Пока реального прогона нет, поля соответствующих метрик должны оставаться «не измерено».

Приёмка: имеется локальный пилот с прослеживаемыми источниками и split, воспроизводимый evaluator и отчёт с честным разделением механических тестов, ручной оценки и ещё не выполненного live-эксперимента. Численные цели качества установить после baseline, не придумывать их до измерения.

## 5. Контрольные точки и зависимости

| Точка | Завершённые шаги | Проверяемый результат |
|---|---|---|
| M0 | 1 | Отклонённый ответ не объединяет события; схемы согласованы |
| M1 | 2–4 | Из снимка получаются mentions с точными основаниями и полным аудитом |
| M2 | 5–6 | Поиск и membership дают объяснимые кластеры и сохраняют неопределённость |
| M3 | 7–8 | Проход возобновляется без повторного расхода, результат доступен через CLI/JSONL |
| M4 | 9 + регрессия | Подготовлены ручной пилот, evaluator, отчёт и границы доказанного качества |

Последовательность реализации: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8. Разметку шага 9 начинать после стабилизации блоков на шаге 3; итоговую оценку выполнять после M3. Это порядок работ, а не поручение запускать дополнительных агентов.

## 6. Обязательная итоговая проверка

В окружении с зависимостями из `llm/events/requirements.lock`:

```bash
python -m unittest discover -s llm/event_pipeline/tests -v
python -m llm.event_pipeline check
python -m unittest discover -s llm/events/tests -v
python -m llm.event_pipeline demo --output data/processed/event_pipeline/acceptance-demo
git diff --check
```

Для повторного demo выбирать новый выходной каталог: существующие экспорты не затирать.

Отдельно проверить: каждая принятая mention присутствует ровно в одном выходном кластере; все ссылки разрешаются; невалидное решение не применено; crash/replay не увеличивает число запросов; новый каталог не обнуляет общую квоту; секретов и исходных локальных данных нет в tracked diff.

Итогом офлайн-этапа является воспроизводимая и проверенная реализация, а не заявление о доказанном качестве извлечения реальной моделью. Живой эксперимент, его стоимость и последующий адаптер B6 оформляются отдельными задачами.
