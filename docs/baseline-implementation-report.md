# Технический отчёт: реализованный ML-бейслайн

> Обновление 22.10.2026: потребитель мигрирован на B6 v0.1/v0.2. Прежние ограничения приёма ниже описывают исторический срез. Актуальные результаты: [миграция](b6-v02-consumer-migration.md). Предметное покрытие ранкера этим не расширено.

Дата: 21 октября 2026 года. Ветка: `news-personalization`. Проверенный срез командного кода: `fadb048` — реализация B6 v0.2. Собственный ML-блок содержит локальные незакоммиченные изменения поверх этого среза.

## 1. Что получилось

Реализован локальный маршрут персонализации:

```text
Структурированное событие B6 v0.1
              ↓
Проверка и сохранение версии
              ↓
Профиль компании + наблюдаемые платёжные связи
              ↓
Отбор и объяснимый скоринг новостей
              ↓
Поиск фрагментов аналитики банка
              ↓
Сборка контекста → тестовый генератор → QA
              ↓
Карточка Insight v0.2 → сохранение → уточняющий вопрос
```

Ранкер и поиск работают обычным Python-кодом без нейросетевой модели. Генератор карточки пока детерминированный тестовый: он проверяет взаимодействие компонентов и сохранение происхождения данных. Настоящая LLM в этот маршрут не подключена.

**Система уже умеет воспроизводимо выбирать события по признакам компании и объяснять расчёт. Качество финансового анализа живой LLM и качество ранжирования по независимой разметке пока не измерены.**

## 2. Что реализовано в нашем блоке

### Приём событий и история версий

Файлы: [b6.py](../ranking/b6.py), [contracts.py](../ranking/contracts.py), [event_store.py](../ranking/event_store.py).

- Приём JSON/JSONL с ограничениями размера; отклонение повторных JSON-ключей и нечисловых констант.
- Проверка схемы, уникальности ID, существования ссылок, JSON Pointers, дат, десятичных диапазонов и границ цитат в Unicode-символах.
- Различение ошибок и предупреждений. Отсутствие полного исходного текста не выдаётся за успешную проверку цитаты по оригиналу.
- SQLite-хранилище с ключом `(event_id, event_version)`, hash содержимого и временем фактического получения.
- Повтор того же содержимого не создаёт новую запись. Изменённое содержимое с прежним номером версии вызывает ошибку.
- Пакетный импорт атомарен: некорректная строка или коллизия не оставляют половину батча.
- Отозванная новая версия не заменяется прежней активной. Можно получить доступный снимок на заданную дату.

Версия события сравнивается численно. Время публикации, подготовки версии и получения системой различаются; поздняя загрузка старой статьи не означает, что система знала её в прошлом.

### Профили компаний

Файлы: [profiles.py](../ranking/profiles.py), [normalization.json](../ranking/config/normalization.json).

`CompanyRepository` один раз загружает CSV и предоставляет нормализованный профиль по ID. Профиль включает ОКВЭД/отрасль, продукты банка, регион/город, категории возраста и численности, ВЭД/страны, выручку и групповые признаки.

Приняты следующие правила:

- Продуктовые флаги трёхзначные: `true`, `false`, `null`. Неизвестное значение не превращается в отсутствие продукта.
- Денежные значения обрабатываются через Decimal. Если единицы выручки и период не подтверждены, они остаются неизвестными.
- Совпадающие записи одного ID схлопываются; противоречивые не разрешаются случайным выбором строки.
- Каждый используемый признак имеет JSON Pointer, значение, качество и происхождение: файл/hash/запись/колонки либо производное правило.
- Версия профиля зависит от содержательных данных и правил нормализации. Техническая дата повторного импорта сама по себе версию не меняет.
- Дата загрузки CSV не считается датой состояния бизнеса. Для недатированного источника историческая применимость явно неизвестна.

Новая компания обрабатывается по тем же правилам; добавлять её ID в код или переобучать модель не требуется. Нормализация отрасли — авторская группировка, а не обученный классификатор.

### Платёжные связи

Файл: [graph.py](../ranking/graph.py).

Строятся направленные наблюдаемые связи из `PAYER`, `BENEFICIARY`, `PAY_AMT`, `PAY_CNT` для выбранного набора компаний.

Реализация потоково читает CSV, группирует выбранные строки во временной SQLite и не создаёт Python-словарь на каждую строку полного платёжного файла. В памяти остаются результаты выбранных компаний. Повторные запросы используют небольшой кэш по версии данных и настроек; определение версии по-прежнему требует чтения hash исходного файла.

Очистка и ограничения:

- Self-loops исключаются.
- Проверяются положительные суммы и целочисленное количество платежей.
- Все повторяющиеся направленные пары исключаются как неоднозначные до выяснения семантики дублей.
- Входящие и исходящие доли имеют разные знаменатели.
- Контрагенты без доступного профиля сохраняются как неизвестные соседи.
- Сохраняются покрытие, исключения и `share_quality`: `clean_observed`, `limited`, `unavailable`.
- Доля описывает очищенный поднабор файла. Она не объявляется долей оборота, закупок или доказанной зависимостью бизнеса.
- В данных нет подтверждённых дат платежей, валюты, периода и назначения. Из направления платежа не выводится автоматически роль поставщика или покупателя.

Для связи организации из новости с банковским ID нужен отдельный доверенный mapping: [entity_mapping.py](../ranking/entity_mapping.py). По похожему названию такая связь автоматически не устанавливается. Сейчас это обработка наблюдаемых рёбер, а не графовая нейросеть и не предсказание неизвестных связей.

### Отбор и ранжирование

Файлы: [signals.py](../ranking/signals.py), [engine.py](../ranking/engine.py), [event-mappings.json](../ranking/config/event-mappings.json), [rules.json](../ranking/config/rules.json).

Ранкер получает снимки событий, профиль компании, роль пользователя и дату среза. Выход — весь оценённый пул, итоговая лента, отложенные/исключённые события и причины.

В конфигурации восемь правил:

1. Ключевая ставка и кредитный продукт.
2. Ключевая ставка и депозит.
3. Ключевая ставка и лизинг.
4. Топливо и транспортная деятельность.
5. Зарплаты и ИТ-компания с известной категорией численности.
6. Сталь и подходящие ОКВЭД производства.
7. Торговые ограничения и совпадающая страна ВЭД.
8. Валютный курс и подтверждённые признаки ВЭД — как потенциальная экспозиция, без выдуманной валюты договора.

Правила сопоставляют структурированные поля конкретного утверждения, а не случайное слово в заголовке. Дополнительные каналы — подтверждённая прямая связь с компанией, связь через платежи и ограниченное лексическое совпадение. Параметры вынесены в конфигурацию, ветвлений по демонстрационным ID нет.

Группы баллов: отрасль, продукт, география, прямая связь, контрагент, механизм, макроконтекст и lexical. В группе выбирается сильнейшее основание с ограничением баллов; десять перепечаток не дают десятикратный вклад.

Формула бейслайна:

```text
base[group] = min(cap[group], strongest_applicable_reason)
weighted[group] = base[group] × role_multiplier[group] × age_weight
raw_total = sum(weighted[group])
score = min(1, raw_total / 100)
```

По умолчанию `age_weight = 2^(-age_days / 10)`. Для явно описанных предстоящих изменений и проверки ранее вступивших ограничений есть ограниченные исключения с пояснением. Неизвестная дата не заменяется выдуманной.

Высокая значимость — от 0.50, средняя — от 0.25, порог ленты — 0.15. Роли меняют отдельные группы множителями 0.8–1.2. Лента ограничивает число событий на одну тему. Сортировка воспроизводима: score, затем raw_total, затем ID.

Для контрагента с пригодным качеством доли базовое правило — `20 + 35 × observed_share`. При `limited` допускается только 5 баллов за сохранённую подтверждённую связь; процент не используется как сильный сигнал. Это проверено сквозным тестом на настоящем результате построения графа.

Каждая причина содержит баллы, нормированный вклад, использованные признаки, claims и пути полей события. Сумма вкладов совпадает со score. **Эта сумма объясняет эвристику, но не является вероятностью или величиной финансового ущерба.** Если применимого основания нет, событие может быть `deferred/unknown`; это не доказательство неважности.

### Поиск по аналитике банка — RAG

Файлы: [corpus.py](../llm/rag/corpus.py), [query.py](../llm/rag/query.py), [retriever.py](../llm/rag/retriever.py), [retrieval-policy.json](../llm/rag/config/retrieval-policy.json).

Используется BM25 по подготовленным OCR-чанкам. Есть нормализация Unicode/регистра/ё, стоп-слова и явные экономические формы/алиасы. Эмбеддинги сейчас не вычисляются.

Индекс строится при создании `Corpus`. Поисковый запрос не запускает повторный OCR и не перечитывает исходные PDF. Перед ранжированием отсекаются недоступные по дате и исключённые документы. В строгом режиме материал с датой без времени доступен со следующего московского дня; неизвестная дата не угадывается по названию.

До top-K действует фильтр полезности: предметное совпадение или достаточные содержательные lexical совпадения. Выдача не заполняется слабыми документами ради количества. Начальные лимиты — 5 фрагментов, не более 2 на документ и 10 000 символов общего контекста; перекрывающиеся фрагменты одной страницы фильтруются.

Выход `EvidenceBundle v0.1` содержит quote, PDF/page/границы, hash документа и текста, дату, статус проверки и план поиска. Один вызов — одна попытка 0/1/2; повторами управляет аналитик. `no_bank_evidence` означает отсутствие пригодных результатов поиска, а не отсутствие позиции банка.

Автоматическая проверка hash и OCR-границ подтверждает воспроизводимость текста. Она не подтверждает правильность числа на PDF и не заменяет смысловой проверки мнения банка.

### Аналитик, QA и сохранение контекста

Файлы: [orchestrator.py](../llm/agent/orchestrator.py), [context.py](../llm/agent/context.py), [source_registry.py](../llm/agent/source_registry.py), [qa.py](../llm/agent/qa.py), [run_store.py](../llm/agent/run_store.py), [questions.py](../llm/agent/questions.py).

Реализован фиксированный Python-конвейер без готовой мультиагентной системы приложения:

```text
Проверить входы → собрать контекст → найти evidence
→ получить draft → выполнить QA → сохранить результат
```

Первоначальный поиск допускает до двух дополнительных попыток. Генерация ограничена двумя вызовами тестового генератора суммарно, включая исправление. Контекст ограничен по байтам/цитатам/hits; сначала исключаются банковские дополнения, а исходные claims и существенные конфликты не обрезаются.

Registry источников формируется кодом. Генератор выбирает готовые IDs и не назначает собственные URL, цитаты, hashes или значения профиля. B6 source_fact копируется буквально с сохранением прогноза/отрицания. Условные персональные шаблоны ссылаются на реальные признаки выбранного synthetic профиля.

QA проверяет структуру, identity/refs, подмену цитат, неподдержанные числа, использование спорного числа, потерю прогноза/отрицания и безусловный финансовый эффект при неизвестных условиях. Банковское мнение не публикуется на основании одной найденной цитаты. Эти guards ограничены и не изображают полноценный фактчекинг.

Раздельно сохраняются structural status, semantic status и publication status. Сейчас независимый semantic review — `not_run`, результат — `limited` либо отказ. Статус `ready` тестовому генератору не присваивается.

`RunStore` хранит pinned входы, hashes, артефакты, шаги и итог. Завершённый run не дописывается: уточняющий вопрос создаёт child run. Проверяются company/role и актуальность события. Новые сведения из вопроса сохраняются как непроверенные пользовательские предположения и не меняют банковский профиль. CLI analyze и ask работают отдельными процессами с сохранённым состоянием.

## 4. Что сейчас пришло от командного препроцессора

Это отдельная командная реализация, подтянутая в ветку; её нельзя приписывать нашему ранкеру.

На срезе `fadb048` реализованы B1–B6: модели/разметка, архив статей, SDK-извлечение, нормализация, каталог событий и явная публикация/экспорт EventBundle v0.2. B6 документирован в [BUNDLE.md](../llm/events/BUNDLE.md): `publish()` сохраняет согласованный снимок, `get_event()` и `export_events()` читают его. B5 и B6 имеют отдельные номера версий; stale/withdrawn нужно обрабатывать явно.

**Важный незавершённый стык:** наш `ranking.b6` принимает v0.1. Новый B6 экспортирует v0.2 с `scenario` и `value_role` («до/после/сравнение»). Миграция нашего потребителя ещё не выполнена. Поэтому готовый offline маршрут на v0.1 не является готовым сквозным подключением нового producer.

Предыдущий [обзор B6](news-pipeline-b6-review.md) описывал срез `fd79650` до реализации публикации и является историческим. На текущем срезе producer уже есть.

## 6. Какие модели реально используются

| Компонент | Текущее состояние |
|---|---|
| Нормализация компаний и платёжный граф | Обычный Python/SQL, без обученной модели |
| Персональное ранжирование | Правила и заданные веса, без LTR/нейросети |
| RAG | BM25, без embedding-модели |
| Наш аналитик | `FixtureGenerator`, явно тестовые шаблоны, не LLM |
| Командный препроцессор B3 | SDK-адаптер и offline-режим существуют; live требует явной настройки тарифов/лимитов/квоты |

В [model_policy.json](../llm/agent/model_policy.json) записан будущий выбор: Qwen3.6/Gemma для извлечения, GLM для интерпретации, DeepSeek для объяснения сложных контрагентских случаев, Qwen-VL для графиков, Kimi для необязательной редактуры. Все маршруты этой политики выключены. В upstream B3 пример профиля по умолчанию указывает DeepSeek — единого действующего маршрутизатора этих настроек пока нет. Наличие списка разрешённых моделей не означает, что они подключены или сравнены по качеству/цене.

## 7. Возможность последующего развития

**Бейслайн можно развивать без полной переписки проекта.** Данные профиля, событие, Relevance и EvidenceBundle разделены; веса и mapping rules вынесены в конфигурацию; аналитик принимает генератор и retriever через Services.

| Что можно заменить позже | Что уже можно сохранить |
|---|---|
| Правила скоринга на обучаемый ранкер | Профили, snapshots, ограничения входов и refs результата |
| Перебор событий на индексированный/векторный отбор | События, версии и последующий этап оценки |
| Простые графовые признаки на признаки/эмбеддинги графовой модели | Наблюдаемые ID/рёбра, provenance и ограничения качества |
| BM25 на гибридный поиск | EvidenceBundle, точные цитаты и контроль дат |
| FixtureGenerator на разрешённую LLM | Контекст, registry, workflow, QA и история; потребуется бюджетный шлюз |

Это возможность развития, не готовая поддержка перечисленных моделей. В частности, candidate retrieval, scoring и формирование ленты сейчас соединены в `rank_events`: для взаимозаменяемых реализаций понадобится небольшой явный рефакторинг интерфейсов и новые tests. Объяснения обучаемой модели нельзя автоматически выдавать за нынешнюю точную сумму эвристических вкладов.

Текущая производительность ограничена архитектурой MVP: события перебираются для одной запрошенной компании, CSV профилей держится в памяти, граф строится для выбранного набора ID, индекс RAG и кэш графа локальны процессу. Многосерверный feature store, общая очередь, полноценный serving-cache и индексы большого потока пока не реализованы. Нельзя переносить замер для трёх компаний на одновременное обслуживание всей базы.

## 8. Что ещё не готово

1. Миграция нашего потребителя на B6 v0.2 и проверка нового exporter→ranking→agent.
2. Общий для всех модулей бюджетный шлюз и подключение живого генератора в нашем аналитике. В upstream NLP уже есть свой ledger; это не означает готовый общий контроль расходов команды.
3. Независимая смысловая проверка ответов и оценка важности новостей с аналитиком.
4. Кэш и интеграционный service/UI adapter из задания 06.
5. Независимый benchmark качества, нагрузочные проверки и полное демо с backend/frontend из задания 07.

**Текущий результат — проверяемый ML-бейслайн и рабочий offline-конвейер. Основной готовый актив — согласованные данные, алгоритмы, происхождение выводов и проверенная интеграция, на которые можно опереть дальнейшее улучшение методов.**
