# Общие правила выполнения заданий

Прочитать перед любым заданием 01–07. Договорённости по полям и функциям — в [INTERFACES.md](INTERFACES.md).

## Контекст проекта

Хакатон: новости и аналитика для клиента Альфа-Бизнеса. Сервис выбирает важные события для компании и объясняет влияние с доказательствами. Команда отдельно делает источник/NLP, backend и frontend. Здесь реализуется принимающая сторона: профили, ранжирование и аналитик.

Вход B6 — структурированный EventBundle v0.1. Выход B6 одинаков для всех компаний. В нём нет готовой значимости, профиля, финансового эффекта и позиции банка. Основные файлы:

- `docs/b6-event-contract.md`, `docs/contracts/event-bundle.schema.json`;
- `docs/b6-examples/{normal,forecast,conflict,partial}.json`;
- `docs/news-personalization-review.md`, `docs/news-personalization-plan.md`;
- `llm/agent/contracts/insight.schema.json` — прежний черновик v0.1;
- `docs/frontend-api-contract.md`, `frontend/src/types.ts` — потребительский формат;
- `llm/rag/` — существующие подготовка и BM25;
- `ranking/audit_data.py` — аудит CSV в текущей ветке.

В другой локальной ветке `ml/ranking-baseline` есть профили, граф, ранкер и тесты. Просматривать через `git show ml/ranking-baseline:<path>`, переносить нужные файлы выборочно после проверки совместимости. В текущей основе их нет. Не делать merge/reset всей ветки ради одного модуля; не восстанавливать удалённые документы и прежнюю историю.

## Старт работы

1. Выполнить `git status --short --branch`, прочитать применимые AGENTS.md, текущее задание и INTERFACES.md.
2. Проверить, что находишься в рабочей ветке персонализации или её согласованном ответвлении. Не переключать ветку поверх незавершённых изменений.
3. Сверить существующие файлы с описанием: часть заданий могла уже быть выполнена другим агентом.
4. Сохранить чужие изменения. Не применять `reset --hard`, `clean`, переписывание истории, push или публикацию без соответствующего поручения.
5. Перед переносом старого кода проверить отсутствие конфликта публичных функций/полей с новой спецификацией. Команды в заданиях — контракт ожидаемого запуска после реализации, не заявление, что сейчас они существуют.

Внутренние технические решения в пределах задания принимать самостоятельно и кратко фиксировать. Если нет API, raw-данных или ответа другого участника, завершать все независимые части на явно обозначенных fixtures. Внешнюю зависимость перечислить в отчёте; не останавливаться на первом вопросе и не притворяться, что отсутствующая проверка выполнена. Если prerequisite-задание отсутствует, сначала выполнить его согласованную минимальную часть либо явно вернуть зависимость, а не изобретать несовместимый временный контракт.

Выполнять задания инкрементально: 01A→01B, 02A→02B, 03A→03B с контрольными точками из файлов заданий. После каждого компонента запускать относящиеся к нему проверки, не откладывать их все до конца. Если поручен один подэтап, сдать его и явно перечислить оставшиеся; не объявлять весь блок готовым. Сначала рабочая цепочка B6 → три профиля → объяснимые рейтинги, затем необязательные расширения. Отсутствующие поля внешних контрактов не изобретать. Составить короткий план реализации и приступить к коду; составление ещё одного плана само по себе не завершает задание.

Зафиксированные договорённости после проверки LLM-отзыва — [review-01-03.md](review-01-03.md). Спецификация правил 03 — [RANKING-RULES.md](RANKING-RULES.md). EvidenceBundle schema/fixture создаёт 04, Insight v0.2 schema/fixture/migration — 05; это снимает лишнюю работу с 01. Связанные контракты нельзя менять только в одном задании.

## Среда и зависимости

Python baseline работает на 3.13. Для JSON Schema использовать библиотеку с Draft 2020-12 и FormatChecker; в исследовании проверена jsonschema 4.25.1. В репозитории нет единого Python-проекта для ML. Задание 01 создаёт минимальный `pyproject.toml` и `uv.lock` для ML с явным включением пакетов `ranking`, `llm`; backend остаётся на своём lock до интеграции его владельцем. Не рассчитывать на случайно установленный пакет.

Команды будущей реализации запускаются из корня через `uv run --frozen ...`. Не заставлять чистый checkout скачивать GPU-модели или вызывать платный API для обычных unit-тестов. Для тестов достаточно unittest и JSON Schema; новый фреймворк добавлять только при реальной необходимости.

Все пути данных принимать через конфигурацию/CLI и разрешать относительно корня проекта или явно переданного каталога. Не зашивать `/home/pavel/...`, текущий рабочий каталог или пути другой машины в код. Отсутствующие raw-файлы должны давать инструктивную ошибку либо переводить явно выбранную demo-команду на синтетику; не подменять реальный режим автоматически.

## Данные и Git

- `data/companies/`: 3 CSV с разделителем `;`, кодировкой UTF-8/BOM. Это локальные материалы.
- `data/analytics/`: 9 PDF. Локально есть OCR и 109 чанков; это не гарантия наличия у другого агента.
- `data/task/`, `data/context/`, полный OCR, индексы, профили, run trace и банковские цитаты из производных сохранять локально по существующим правилам публикации.
- В Git: код, схемы, конфигурации без секретов, явно синтетические fixtures, безопасные агрегаты и инструкции. Перед добавлением файлов просмотреть список staged; не использовать бездумный `git add .`.
- На старте 01 добавить игнорирование `/data/processed/ranking/`, `/data/processed/personalization/`, временных БД и локального state. Исходные данные не перемещать и не менять для удобства теста.
- Не считать `SYNTHETIC_U` доказательством искусственности всей банковской строки: профиль реальный обезличенный, отдельно от полностью вымышленного тестового профиля.

## Ограничения анализа

Факт из новости означает «так сообщает источник», не доказанную истинность. Прогноз, план, отрицание и стадия должны сохраняться. Тематические теги — сигнал отбора, не доказательство воздействия. `quality=complete` не гарантирует отсутствие конфликтов или пропущенных фактов.

Наличие кредита/лизинга не раскрывает сумму, тип ставки и даты пересмотра. Отсутствие продукта в банковской записи не доказывает отсутствие продукта в других банках. ОКВЭД описывает деятельность, но не структуру затрат. Регион регистрации не равен всем местам операций. Доля наблюдаемого платежа не равна доле оборота. Эти ограничения отражаются в reasons и ответах, а не только в README.

Не угадывать соответствие названий из новостей обезличенным ID. Entity mapping — отдельный вход со статусом, происхождением и областью применимости. Без него граф не доказывает связь с организацией из новости.

## Модели и деньги

Доступные названия-кандидаты заданы в `llm/agent/model_policy.json`. Это не подтверждение существования конкретного provider model ID. Для live-вызовов нужны разрешённая модель, ключ, адрес провайдера, тарифы, токен-лимит и выделенная квота. Ни одно из этих значений не выдумывать.

500 ₽/день — командный потолок, не личный бюджет каждого модуля. Численный токен-лимит ещё не зафиксирован. До настройки общего атомарного учёта live-вызовы закрыты. Оффлайн-генератор для тестов возвращает `generation_mode=fixture`; это не результат разрешённой LLM. Модель помощника, написавшего код, не становится runtime-моделью приложения.

Собственная агентная логика: обычные Python-функции, явное состояние и ограниченные переходы. Не подключать готовую мультиагентную систему. Повторный поиск выполняется по конкретной причине нехватки/противоречия, с сохранением артефакта и счётчика, а не бесконечным перезапуском того же промпта.

## Проверки и отчёт

Проверять поведение на ошибочных входах, обновлениях, неизвестных данных и изменении профиля. Не ограничиваться тестом «функция вернула свой же формат». Набор fixtures с написанными тем же агентом оценками пригоден для smoke-теста, но не независимого вывода о качестве.

Обязательны подходящие к изменению тесты; полные OCR/CSV-прогоны — только когда нужны и данные доступны. Не запускать E2E с внешними API в обычном unit-тесте. В отчёте указать фактические команды, количество проверок и `not_run` для внешних зависимостей.

Шаблон итогового отчёта:

```text
Задание и исходный commit:
Реализованные интерфейсы:
Изменённые файлы:
Команды проверки и фактические результаты:
Контрактные примеры и их статусы:
Использованные зависимости/модели/данные:
LLM usage и стоимость (или no_llm_calls):
Ограничения и внешние блокеры:
Что должен получить следующий агент:
```

Не менять вес/порог, чтобы один заранее известный тестовый ID получил нужное место. Не заявлять готовность UI, если проверен только JSON, и качество LLM, если тестировался только fixture-генератор.
