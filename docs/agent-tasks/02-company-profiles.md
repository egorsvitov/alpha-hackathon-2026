# Задание агенту 02: профили компаний и платежные связи

Реализуй модуль компании для персонализации новостей. Прочитай [COMMON.md](COMMON.md), [INTERFACES.md](INTERFACES.md), результат задания 01 и его схемы. Сохрани незавершённые чужие изменения. Это задача на код и проверяемые профили, а не новый EDA-отчёт без реализации.

## Цель

По company_id получить нормализованный CompanyProfile с воспроизводимой версией, неизвестными полями и происхождением каждого используемого признака. Для выбранных компаний добавить наблюдаемые платежные связи. Профиль должен работать и для ранкера, и для аналитика без повторного чтения/понимания CSV каждым модулем.

## Входные CSV

UTF-8/BOM, разделитель `;`. Номера записей в provenance — data_record_number с 1, не физическая строка файла (quoted newline может занимать несколько строк).

| Поле CSV | Выход профиля | Правило |
|---|---|---|
| SYNTHETIC_U | company_id | Непустой opaque ID |
| MAINOKVED_CODE / NAME | okved.code/name, industry | Код как строка; industry derived по версии mapping |
| ECO_MARK_LABEL | development_stage | Сохранить категорию, не придумывать экономический смысл |
| REVENUE_COMPANY | revenue.raw/unit/status/period | Decimal-string, единицы/период неизвестны до подтверждения |
| COMPANY_AGE_YEARS_GRADATION | age_band | Исходный интервал/категория |
| AMOUNT_WORKERS_FNS_GRADATION | employees_band | Основной доступный источник; если fallback SPARK — явное происхождение и правило |
| REGION / CITY | region/city | Нормализованная форма плюс raw в provenance |
| CL_PRODUCT_RKO/GAR/LOA/LEA/DEP/ZPP_MARK | продукты rko/guarantee/loan/leasing/deposit/payroll | 1/1.0 → true; 0/0.0 → false; пустое/неизвестное → null |
| FACTORING_MARK | products.factoring | Та же трёхзначная логика |
| FTS_FLAG / FTS_COUNTRY_NAME | fts_present/countries | Отдельно флаг и страны; противоречия не скрывать |
| GROUP_ID / CL_TYPE | group_id/client_type | Категориальный контекст, не доказательство владения |

NEGATIVEMARK не использовать как «компания проблемная»: смысл не подтверждён. Файл связей ФЛ не доказывает должность, собственность или контроль; в MVP не строить по нему такие признаки.

## Реализация профиля

1. Проверить заголовки, дубли колонок, лишние/недостающие ячейки и пустые company IDs. Неверный файл не должен частично превращаться в валидную базу без отчёта.
2. Прочитать/проиндексировать CSV один раз на экземпляр CompanyRepository. Не читать весь файл заново для каждой пары компания—новость.
3. Совпадающие строки одного ID схлопнуть с диагностикой. Если хотя бы одно содержательное поле различается — profile_conflict; не выбирать последнюю/первую строку по случайности.
4. Продукты с неожиданным значением сохранить unknown, добавить issue; `None` не превращать в False. Пустая строка отрасли или неправильный ОКВЭД — unknown, без фантазии LLM.
5. Проверить Decimal на finite/nonnegative для выручки. Разделители тысяч/десятичная запятая допускаются только явно описанным правилом; не угадывать двусмысленную запись.
6. Страны нормализовать словарём известных алиасов, например КИТАЙ/CHINA/CN → CN. Неизвестное название сохранить как неизвестный токен с raw-значением; не присваивать выдуманный ISO-код. false FTS + страны → conflicting, не обычная доказанная экспозиция.
7. Для каждого поля, используемого downstream, создать Feature. Derived industry ссылается на исходный ОКВЭД и mapping version. Даже идентификатор/доступный регион имеют provenance; нет ссылки «потому что так сказал агент».
8. Версия профиля учитывает source hash, normalization version/config hash, выбранный company record, graph при наличии. Роль и время запуска версии не меняют. Обновление правила при прежнем CSV должно менять version.
9. Реальный display_name — «Компания <ID>». В fixtures можно давать вымышленные названия с is_synthetic=true.
10. Подготовить профили с отличающейся экспозицией: перевозчик с лизингом, ИТ-компания с неизвестными условиями найма, торговая компания с ВЭД и кредитом/депозитом. Флаги real-профилей брать из CSV, а не подгонять под сценарий.
11. Заполнить `source_snapshot` по INTERFACES.md. `imported_at` — техническое время загрузки; оно не является датой состояния бизнеса. `data_as_of`/`exported_at` известны только из подтверждённого manifest источника, иначе null. Не выводить их из mtime, имени файла или даты хакатона. При неизвестной дате поставить historical_applicability=unknown и limitation; повторная загрузка того же содержимого не меняет profile_version только из-за imported_at. Исторический rank фиксирует конкретный профиль, но не заявляет, что он был известен или верен в прошлом.

## Платежный граф

В `df_Uid_payment_hack.csv` есть PAYER, BENEFICIARY, PAY_AMT, PAY_CNT. Нет дат, валюты, периода и назначения. Для одной операции «incoming» означает BENEFICIARY=company, «outgoing» — PAYER=company. Это не доказательство роли покупателя/поставщика.

Для первого MVP потоково просканировать файл и хранить только строки, касающиеся выбранных компаний. Не создавать 1,38 млн Python dict ради трёх профилей. Сканирование выполняется один раз на набор выбранных ID; повторные запросы используют результат с версией данных.

Политика очистки:

- Исключить self-loops; количество записать.
- Суммы Decimal finite > 0; count — положительное целое (десятичная запись с нулевой дробной частью допускается только явным parser-правилом).
- Все повторяющиеся directed pairs исключить как неоднозначные, пока не известна семантика агрегации. Даже если одна строка пары невалидна, остальные не становятся автоматически уникальными. Не суммировать возможные дубли.
- Не выбрасывать контрагента из-за отсутствия его профиля; сохранить ID, profile_known=false.
- Доли считать отдельно по направлениям: сумма конкретного контрагента / сумма оставшихся корректных строк направления. Сохранить знаменатель и статистику исключений в артефакте агрегации.
- Для каждого направления вернуть `graph_coverage` и `share_quality` по INTERFACES.md: число исходных/сохранённых/исключённых записей, долю сохранённых записей, известность сумм и знаменатель. Это покрытие доступного файла, не доля всех операций компании. При потере хотя бы одной не-self строки из-за дублей/ошибок share_quality=limited; никакой высокий процент в очищенном остатке не становится сильной зависимостью. Неизвестная сумма исключённой записи не принимается за ноль.
- Для пустого направления — нет соседей, не деление на ноль. Для loaded-графа с нулём соседей status остаётся loaded.
- `profile_coverage_by_nodes` считать по уникальным соседям; один ID в двух направлениях не считать дважды.
- Origin derived share включает путь/hash платежного файла, записи/ID агрегации, правила очистки и знаменатель. Одной ссылки на строку числителя недостаточно для воспроизводимости доли.
- graph_version меняется при изменении платежей, политики очистки или набора известности профилей. При attach меняется profile_version; повторный attach того же графа не дописывает бесконечные суффиксы.

Не решать entity mapping в этом задании. Можно выдать таблицу обезличенных соседей; преобразование реального названия из новости в банковский ID — отдельный подтверждённый ресурс.

## Приёмочные кейсы

P01–P10 из матрицы плюс:

- Флаги `1`, `1.0`, `0`, `0.0`, пустое, неожиданное; правильные три состояния.
- Новый company ID в тестовом CSV работает без изменений словаря ID и переобучения.
- Два одинаковых дубликата разрешаются, две разные записи — конфликт.
- Профиль и все refs проходят схему; JSON Pointer каждого Feature разрешается в ожидаемое значение. Для агрегатных features path должен существовать, не быть условной строкой.
- Граф на маленькой ручной таблице: A→B 30, A→C 70 даёт 0,3/0,7; отдельный incoming не влияет на outgoing-denominator.
- Повтор A→B исключён целиком; неизвестный C остаётся; self-loop не влияет на знаменатель.
- Проверить A→B 100, A→B 100, A→C 80, A→D 20: после исключения B доля C=0.8, но retained_record_fraction=0.5 и share_quality=limited. Ранкер не вправе дать сильный share-based сигнал. Невалидная сумма тоже делает покрытие ограниченным, а не «полным по доступным числам».
- Проверить недатированный источник: imported_at заполнен, data_as_of/exported_at=null, historical_applicability=unknown; replay не выдаётся за историческое состояние компании. Изменение подтверждённой даты источника меняет profile_version; изменение одного imported_at — нет.
- Одинаковые данные/правила → одинаковые версии; изменение правила или платежа → новая версия.
- Исходный переданный профиль не мутирует при attach: возвращается новый объект.
- CLI и тесты с synthetic CSV работают без банковского датасета.
