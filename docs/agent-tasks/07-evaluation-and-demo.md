## A. Набор событий и профилей

Минимум 20 разных event families × 3 профиля = 60 основных пар для одной фиксированной роли, например cfo. Ролевые варианты — отдельные поведенческие тесты, не объявлять их независимыми новыми событиями. Версии/дубли/повторные цитаты одной семьи не увеличивают число уникальных событий.

Профили: вымышленные DEMO_LOGISTICS, DEMO_IT, DEMO_TRADE, проходящие новую схему. Должны содержать разные отрасли/продукты/географию и реальные для задачи неизвестности. В отдельном локальном прогоне можно использовать три профиля из supplied CSV; их не публиковать как синтетические.

Содержание набора:

| Группа | Необходимые различия |
|---|---|
| Ставки | Сохранение, повышение, прогноз, предложение, отрицание решения |
| Отрасль | Топливо/перевозки, труд/ИТ, материалы/строительство, спрос/торговля |
| ВЭД | Страна из профиля, другая страна, неизвестная страна/направление |
| Контрагент | Подтверждённый synthetic mapping в demo, unresolved, эксперт/автор вместо target |
| Шум | Общие совпадающие слова без механизма, явно чужая отрасль/территория |
| Качество | Конфликт, частичные данные, неизвестная дата, разные модальности |
| Жизненный цикл | Поздняя старая версия, обновление, отзыв, восстановление |

Факты полностью синтетические, источники/названия явно учебные. Не давать вымышленные сведения под видом реальных новостей о настоящих компаниях. `content_kind=synthetic`, is_synthetic=true, evidence.quote/span согласованы. По возможности использовать factory только при создании fixtures, а затем зафиксировать JSON для воспроизводимости.

Manifest содержит dataset_version/hash, origin, created_by, family_id, IDs версий, profile versions, role, as_of, receipt times для replay, split. Для каждой fixture-фамилии фиксируется причина включения. Источники и IDs стабильны, не зависят от случайного UUID на каждом запуске.

## B. Разметка

Основная шкала значимости:

- 0 — в доступном профиле нет содержательного механизма/причины внимания; не означает доказанного отсутствия любого эффекта в реальном мире.
- 1 — общий контекст или слабая косвенная связь.
- 2 — существенный для профиля механизм, стоит включить в ленту.
- 3 — высокий приоритет внимания/проверки/действия при данном профиле и временном срезе.
- null — эксперт не может оценить при текущих данных; это не 0.

Отдельно отметить adequacy=adequate|limited|insufficient и actionability. Противоречивая новость может получить grade 3 как важный сигнал для проверки; не смешивать это с утверждением, что одно спорное число истинно.

Строка label:

```text
event_id, event_version, family_id,
company_id, profile_version, role, as_of,
grade: 0|1|2|3|null,
adequacy, rationale, expected_feature_paths[], expected_claim_ids[],
reviewer_id, label_origin=expert|developer_provisional,
review_status=draft|reviewed|disputed,
reviewed_at|null, dataset_version
```

Инструкция аналитику: оценивать по профилю/источнику, не смотреть score ранкера перед выставлением метки; фиксировать гипотезы, неизвестности и механизм. При двух разметчиках сохранить обе оценки, расхождение и принятое разрешение, не молча усреднять смысловую категорию.

Агент может подготовить provisional labels для теста, но не ставит себе expert/reviewed. Без независимого review отчёт пишет independent_benchmark=false, а продуктовые выводы о качестве не делает.

## C. Разделение настройки и контроля

Разбить по family_id, до подбора весов, с фиксированным seed/manifest. Все версии, дубли и переформулировки семьи остаются в одном split. На маленьком наборе разумно выделить минимум 5 разных семей под контроль, остальные под development; точный состав фиксируется заранее.

Изменение правил после просмотра ошибок control требует новой итерации/свежего контрольного набора, а не повторного объявления того же результата независимым. Профили в smoke могут повторяться, но тестировать также новый неизвестный ID/профиль для отсутствия hardcode.

## D. Метрики ранжирования

Сначала определить общий eligible pool: доступные на срезе валидные актуальные события, пригодные по временной/availability policy **до персонального candidate filtering**. Отдельно отчитать excluded по отсутствию данных/дат и число важных размеченных событий вне этого pool. Не скрывать потери данных внутри высокого recall по удобной выборке.

Для scored и final feed считать отдельно:

1. Candidate recall: relevant = grade≥2; |relevant ∩ candidates| / |relevant|. Если relevant пуст — null.
2. nDCG@5: gain=2^grade−1, log2(position+1), ideal по всем размеченным eligible events, а не только прошедшим отбор. При IDCG=0 — null.
3. Precision@5: число grade≥2 в первых пяти **уникальных событиях** / 5. Короткая лента не улучшает знаменатель. Дополнительно можно precision@returned, но не подменять им основную метрику.
4. Recall@5 и список пропущенных grade=3 с причинами candidate/threshold/diversity/time/data exclusions.
5. Coverage labels: сколько пар требовалось и сколько оценено, какие split/role и число компаний/семей.

Если в eligible pool есть неразмеченные пары, строгие полные ranking metrics=null с reason=incomplete_judgments; допускается отдельный явно подписанный judged-subset report, не смешанный с полным. Не принимать grades.get(id,0) без проверки покрытия.

Сравнить минимум два baseline: порядок по свежести и простые отраслевые совпадения; затем объяснимый ранкер. Сохранить версию правил и неизменный набор событий/профилей для сравнения. На 60 provisional парах не заявлять статистически доказанное превосходство.

## E. RAG, аналитика и операционные метрики

Для RAG judgments: query/task ID, допустимые document IDs/pages, нужна ли конкретная дата/горизонт, должно ли быть отсутствие ответа, reviewer status. Recall@K по target pages/docs и доля temporal violations. Не засчитывать страницу лишь за совпадение темы, если она не поддерживает нужный вывод.

Для Insight отдельно:

- Referential coverage: claims со всеми разрешимыми source/feature refs / все claims соответствующего типа. Это структурная метрика.
- Supported-claim rate по ручной смысловой проверке: поддержанные / проверенные; conditional claims проверять вместе с assumptions. Если ручного review нет — null, не 100% за наличие ссылок.
- Critical errors: выдуманная позиция банка, факт вместо прогноза, отрицание наоборот, чужая компания/источник, некорректное число/единица/период, уверенный вывод по спорному значению.
- Completeness: нужные разделы либо содержательны, либо честно отмечены insufficient/not_applicable; не по числу заполненных строк.
- Usefulness/actionability: экспертная оценка следующего шага и понятности влияния.
- Abstention/limited rate: сколько отказов/уточнений и были ли они обоснованны; нулевые ошибки за счёт отказа на всё не считать успехом.

Операционные: p50/p95, объём выборки, cold/warm cache, стоимость и input/output tokens на **попытку** и на финальный insight, среднее число retries, cache hit rate. Не смешивать fixture latency со скоростью реального провайдера. При no_llm_calls стоимость 0 только для выполненных offline действий; прогноз live cost остаётся unknown.

## F. Воспроизводимый demo

Создать CLI demo, использующий реальные публичные функции модуля, а не повторяющий их логику в отдельном скрипте:

1. Загрузить fixtures в отдельный state_dir с тестовыми часами.
2. Выбрать DEMO_LOGISTICS и получить feed по role/as_of.
3. Открыть событие о топливе/ставке, показать Relevance и trace.
4. Выбрать DEMO_IT и показать тот же event с другим основанием или объяснимым отсутствием в feed.
5. Получить Insight, раскрыть ссылки до news evidence и feature values. При отсутствии подходящего RAG bank_view отсутствует честно.
6. Задать уточнение в контексте сохранённого run.
7. Повторить запрос — проверить cache и actual cached flag.
8. Добавить новую event_version — пересчитать; затем withdrawn — убрать текущую карточку; поздняя старая версия не возвращает её.
9. Показать conflict/partial/budget_exhausted сценарии.

Два режима: `fixture` (детерминированная генерация, явная маркировка) и `live` (только разрешённая настроенная модель через общий budget). Скрипт не переключается на fixture молча при ошибке live.

Если backend/frontend ещё не подключены, документировать CLI/service demo как таковое. В документе для backend дать точную последовательность HTTP вызовов после подключения. POST raw news не работает через наш fixture importer: полноценный путь upload→producer→EventBundle отдельно проверяется с владельцем NLP.

## Приёмка и handoff

E01–E08 из матрицы. Отдельные unit-проверки формул:

- При k=1, выбран grade 2, лучшая доступная grade 3 → nDCG=3/7.
- Два релевантных результата из пяти слотов → P@5=0.4, даже если возвращено только два.
- Повтор одного ID не увеличивает precision/recall.
- Отсутствие положительных меток даёт null для nDCG/recall; отсутствие разметки не становится нулевой оценкой.
- Разделение family-level исключает попадание v1 в train и v2 в control.
- Плохая новость, отфильтрованная по данным, отражается в exclusion report; качество не считается по заранее выбранным успешным кейсам.
