## Как использовать

Открыть нужный файл, скопировать его целиком агенту, работающему в этом репозитории. Каждый файл содержит вводную и поручение прочитать общие решения из соседних файлов. История чата агенту не нужна. Если агент не имеет доступа к репозиторию, передать вместе с заданием COMMON.md, INTERFACES.md и перечисленные в задании исходные контракты.

Начинать с задания 01. Следующие задания используют его схемы и интерфейсы. Агент обязан сначала проверить фактическое состояние ветки и уже сделанную работу, а не повторять её или перезаписывать чужие изменения.

## Порядок при одном агенте

`01A → 01B → 02A → 03A → 03B (без графа) → 02B → 03B (графовая ветка) → 04 → 05 (offline) → 06 → 07`.

Так сначала получается работающая лента на профилях без платежей, затем добавляется граф. Оба запуска 03B — инкрементальная реализация одного модуля; завершённую часть не переписывать. Можно выполнить 02B сразу после 02A, если граф уже почти готов. Для запуска отдельного этапа передать весь файл задания и явно указать `Выполни только 01A` (аналогично для остальных). Критерии завершения каждого этапа перечислены внутри задания. 03A можно проектировать после 01A на fixtures, но выбор snapshots проверяется через store из 01B.

После 02 подготовить профили и задания на разметку из 07, чтобы аналитик мог оценивать новости параллельно разработке. Не откладывать вопрос API/тарифов/лимитов до завершения 05: заранее подготовить координатору точный список нужных конфигурационных данных, но не останавливать offline-разработку.

## Порядок при двух исполнителях

Сначала один исполнитель завершает 01 и фиксирует схемы. Затем:

- Исполнитель A: 02 → 03 → ранжировочная часть 07.
- Исполнитель B: 04 → бюджетная часть 06 → 05 → оставшаяся часть 06.
- Общая проверка: 07; backend-разработчик подключает подготовленный сервис к HTTP и Docker.

Это схема распределения будущей работы, не поручение автоматически запускать несколько агентов. В одном checkout не выполнять параллельно переключение веток/коммиты и не редактировать общий CLI/схемы двумя исполнителями одновременно. Для параллельной реализации использовать отдельные рабочие деревья с согласованной основой.

Критерий MVP для 01–03: один EventBundle проходит ingestion, соединяется с тремя schema-valid профилями и даёт воспроизводимые рейтинги с разными обоснованиями через CLI и Python API. Сложные миграции БД, seen-state, новый CompanyContext и эмбеддинги не являются условием этого MVP. Векторный retrieval можно добавить отдельным измеряемым расширением; текущий план задаёт объяснимый baseline, а не запрещает будущую гибридную систему.

## Контрольные точки

1. **M1:** четыре B6-примера проверяются, сохраняются и соединяются с тремя профилями; плохие входы получают понятную ошибку.
2. **M2:** выводятся три ленты с разными причинами приоритета; никакой LLM не нужна.
3. **M3-offline:** весь маршрут до Insight и QA работает на явно тестовом генераторе. Это проверка кода, не демонстрация качества LLM.
4. **M3-live:** при доступных разрешённой модели, тарифах и общей квоте получен реальный результат с источниками, расходом и QA. Без этих условий статус `not_run`, не фиктивный успех.
5. **M4:** адаптер подключён backend-разработчиком, интерфейс получает реальные ответы модуля, сценарии обновления, вопроса и ограничений проверены. Если подключение ещё не сделано, честно сдаётся только сервисная/CLI-интеграция.

## Готовые короткие поручения

Для первого запуска:

> Реализуй задание из `docs/agent-tasks/01-contracts-and-ingestion.md`. Прочитай указанные в нём общие документы и исходные схемы. Доведи реализацию до приёмки и выполни проверки. Сохрани чужие изменения, не публикуй исходные данные и не пушь без отдельного поручения. В конце отчитайся о файлах, командах, результатах и оставшихся ограничениях.

Для следующего запуска заменить номер/название файла. Для последовательного выполнения всего блока:

> Выполняй задания `docs/agent-tasks/01-...` — `07-...` в порядке из README. Проверяй каждую контрольную точку перед переходом к следующей. Если нет API, сырых данных или экспертной разметки, продолжай независимую работу на явных fixtures, а зависимые проверки отмечай `not_run`. Не подменяй реальную модель тестовым ответом без маркировки. Не повторяй завершённые этапы и не меняй внешние контракты молча.

## Что должно остаться после каждого задания

- Реализация и минимальные существенные проверки в области задания.
- Команды запуска с актуальными путями, без несуществующих файлов.
- Закреплённые зависимости и обновлённые notices для реально добавленных компонентов.
- Краткий отчёт `docs/implementation/<номер>-result.md`: сделано, проверки, результаты, ограничения, следующий шаг. Не писать туда сырые данные клиентов и ключи.
- Для каждого критерия матрицы: `passed`, `failed`, `not_run` или `not_applicable` с причиной. Сам файл задания остаётся спецификацией и не становится журналом выдуманных успехов.
