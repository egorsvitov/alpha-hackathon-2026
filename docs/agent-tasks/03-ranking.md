Это конфигурация гипотез, а не извлечение нового факта из тега. Словарь расширяемый, неизвестные метки сохраняются в диагностике. Не приписывать RAG-темы автоматически всем близким словам.

### Исполнимые правила вместо свободного толкования таблицы

Точный минимальный DSL и восемь начальных правил заданы в [RANKING-RULES.md](RANKING-RULES.md) и [ranking-rule-examples.json](ranking-rule-examples.json). Перенести их в `ranking/config/event-mappings.json`, добавить config validator и positive/negative тесты. Это проект конфигурации, не утверждение о наличии работающего engine. Не заменять реальные значения B6 `asserted/affirmed` придуманным `fact` и не искать объект новости по случайному слову из заголовка.

Сопоставлять selector с полем конкретного claim; refs должны указывать на совпавшее поле. Совпадения только в ranking_features дают отдельный слабый metadata candidate, но не активируют claim-based баллы из примеров. География регистрации, известная ВЭД и предмет новости — разные признаки; правила имеют явную scope policy. Прогноз может получить тот же приоритет внимания, но всегда с conditional basis; он не превращается в произошедшее изменение. На unknown/negated значениях claim-based observed award не начисляется.

По умолчанию учитывать участников в substantive roles из claims. Автор прогноза/издатель/цитируемый эксперт не становится объектом новости. Для неизвестной роли entity-match даёт максимум диагностический кандидат, без сильного сигнала «событие о компании».

Географический канал по ВЭД не использует conflicting country feature как подтверждённое совпадение. При fts_present=false и непустых странах отметить конфликт, не начислять country points. При неизвестном флаге, но непротиворечивых наблюдаемых странах допустима условная причина с missing-context; неизвестная доля/направление остаются неизвестными.

Не схлопывать все claims до одной action. При negated не применять механизм как произошедший положительный факт. Событие «санкции не введены» может быть важно как снятие ожидания, но не как введённое ограничение. Для forecast/plan/proposal причина явно отражает модальность.

Для conflicts построить набор спорных `(claim_id, field_path)`; родительский путь покрывает потомков. Производный числовой признак не вычислять, если любой dependency спорен. Другие безопасные признаки события остаются доступны.

## B. Доступность и временная политика

На входе StoredEvent; использовать общий выбор актуальной версии из 01. Сначала latest на as_of, потом качество и доступность, иначе есть риск воскресить withdrawn. Сортировка входа не должна влиять на результат.

Начальная конфигурация:

- lookback_days=30 по публикации;
- undated publication → deferred с publication_date_unknown; прямой анализ возможен отдельно;
- будущая публикация/receipt/producer update → excluded на данном срезе;
- withdrawn и insufficient → excluded, исходные причины сохраняются;
- partial с пригодными claims → allowed с limited evidence;
- старое объявление может оставаться кандидатом, если утверждение об утверждённом/вступающем изменении имеет **известный** effective interval в ближайшие 14 дней; ограничить такой fallback возрастом 180 дней и явно записать причину;
- Для санкций/регулирования добавить `durable_recheck` fallback до 180 дней: latest содержит asserted/affirmed claim со stage=effective и известным effective_at.start не позже as_of. Если по тому же объекту есть repeal/negation или спорна стадия/дата, этот fallback не включать. Причина — «ранее сообщалось о вступлении ограничения в силу; проверить актуальность», evidence_status=limited, а не утверждение «ограничение точно действует сейчас». Для него age_weight floor=0.5; после 180 дней deferred с `durable_status_requires_refresh`.
- неизвестные границы периода не заменять датой публикации. Forecast horizon не использовать как effective_at.

`effective_at.end` — конец календарного окна **начала действия**, не срок прекращения ограничения. Не выводить продолжающееся действие из одного такого интервала, отсутствия отмены в потоке или прошедшей даты прогноза. При неизвестной стадии/дате старое событие остаётся deferred с причиной нехватки контекста. Нужен свежий источник либо будущий отдельный мониторинг долгоживущих рисков; новостная лента не объявляется полным реестром действующих ограничений.

Пределы — конфигурируемые стартовые настройки, не объективные истины. При изменении политики меняются config hash и результаты кэша.

Для MVP точный перебор доступных событий по выбранной компании допустим. Не строить заранее таблицу всех 85 тысяч компаний × всех новостей. При росте добавить inverted index позже, сохранив API.

Кандидат получает хотя бы один сигнал: отраслевой, продуктовый, географический, macro, entity/counterparty или ограниченный lexical. Свежесть сама по себе не создаёт бизнес-релевантность.

Lexical fallback: использовать тексты claims/название деятельности, а не весь архив. Удалять стоп-слова, требовать несколько содержательных совпадений; совпадения только «компания», «рынок», «Россия» недостаточны. Не превращать текстовое сходство в сильную оценку влияния. Явно несовместимая территория/предмет ограничивают соответствующий канал; при этом не выключать независимый подтверждённый канал.

Если совпадений нет — deferred с `no_candidate_signal_unknown_relevance`, score=null, level=unknown. Не заявлять «точно не важно». Хранить этот пул для оценки recall и разбора пропусков.

## D. Скоринг без скрытой магии

Перенести стартовые веса старого ранкера как некалиброванную основу, привести их к новой конфигурации. Одно событие не должно получать больше баллов просто из-за десяти одинаковых claims/перепечаток.

Группы: industry, product, geography, entity, counterparty, mechanism, macro, lexical. В пределах одной причины/дублирующего механизма брать наиболее сильное основание; связанные product flags не суммировать бесконтрольно. Прямую entity-связь и ту же связь через собственный граф не считать дважды. Все группы имеют явный cap.

Стартовая таблица баллов (сохранить как конфиг, не как ветвления по ID):

| Группа | Основание/баллы | Cap |
|---|---|---|
| industry | Точный применимый ОКВЭД-префикс 42; широкая отрасль 34 | 42 |
| product | Ставка: loan 28, leasing 15, deposit 20; профильный продуктовый механизм до 30 | 30 |
| geography | Подтверждённый регион 14; страна ВЭД 18, с оговоркой об экспозиции | 20 |
| entity | Подтверждённая связь с объектом события | 65 |
| counterparty | 20 + 35 × доля нужного направления, только с mapping и share_quality=clean_observed | 55 |
| mechanism | Авторская гипотеза из старых rules, с применимым ОКВЭД/географией | 25 |
| macro | Ставка/ВВП как общий контекст | 4 |
| lexical | Достаточное содержательное совпадение | 10 |

Если в B6 нет ОКВЭД, exact-префикс применяется только через явный версионируемый mapping предмета события, а не как будто producer передал такое поле. Цифры — некалиброванный baseline. Одна и та же гипотеза, найденная через aliases одного поля, считается один раз; разные механизмы могут давать разные группы, но не описываются как независимые источники доказательств.

При share_quality=limited наличие сохранённого ребра с проверенным entity mapping допускает только 5 counterparty points, без использования observed_share; reason code `payment_share_limited`. При unavailable/not_loaded — 0 graph points с limitation. Процент очищенного поднабора не называть долей выручки/закупок или доказанной зависимостью. Прямая entity-связь из другого подтверждённого канала не выключается из-за плохого графа.

Предлагаемая простая формула, которую нужно реализовать и описать:

```text
raw_g = min(group_cap_g, лучшая допустимая сила оснований группы)
role_g = raw_g * configured_role_multiplier(role, group)
age_weight = 2 ** (-max(0, age_days) / half_life_days)
weighted_g = role_g * age_weight
# для разрешённого upcoming/durable_recheck — конфигурируемый floor age_weight,
# с отдельной причиной; не скрытая замена даты публикации
raw_total = sum(weighted_g)
score = min(1, raw_total / 100)
contribution_g = score * weighted_g / raw_total, если raw_total > 0, иначе 0
```

Cap ограничивает **базовые** баллы до роли; product cap=30 и множитель 1.2 могут дать 36 до временного штрафа — это намеренная семантика. Для группы сохранять одну победившую причину (при равных баллах rule_id/claim_id лексикографически), остальные совпадения — только в diagnostics, без повторного вклада. Сохранить raw_total и scoring_diagnostics по INTERFACES.md. Два результата с score=1 различать по raw_total; считать saturation rate в отчёте, без выдуманного целевого качества.

Не добавлять положительную «свежесть» к нулевому бизнес-сигналу. Полураспад начать с 10 дней, старый upcoming floor=0.5; настройки записать в rules. В первой реализации использовать приведённую формулу; дальнейшие изменения проводить как новую версию правил и сравнивать на фиксированной разметке.

Роль: стартовые множители ограничить диапазоном 0.8–1.2. По умолчанию все равны 1; cfo: product=1.2, counterparty=1.1; treasurer: product=1.2, geography=1.1; ceo: industry=1.1, mechanism=1.1. Для chief_accountant оставить 1 до появления подтверждённого регуляторного/платёжного механизма, затем добавить правило с тестом. Недостаток признаков для роли не компенсировать выдуманным механизмом. При всех множителях 1 результат одинаков для ролей.

Начальные пороги согласованы с текущим UI: high ≥0.50, medium ≥0.25, low ниже, min_feed_score=0.15; это гиперпараметры для последующей разметки. При изменении порогов согласовать `docs/frontend-api-contract.md` и обе константы frontend, не менять их чужому владельцу молча. null → unknown. Сохранить неокруглённую сумму до вывода; в сериализации корректировать только численный rounding residual, не скрытый перерасчёт смысла.

Для v1 не вычислять экономическую «существенность» через произвольный процент: уровень 20% не даёт величины изменения. Magnitude-based bonus выключен до явного правила с metric/kind/unit/comparison/qualifier и независимой проверкой. Важность реализуется через подтверждённые связи, механизм и сроки.

## E. Объяснение и лента

Каждый Reason содержит raw_points, contribution, feature IDs, claim IDs/event paths, правило и тип основания. Проверить, что references относятся к текущим profile/event versions. Причина на одних ranking_features явно слабее по типу обоснования и не генерирует новый факт.

Формулировка: «В записи компании есть кредитный продукт; условия долга неизвестны». Недопустимо: «Ваш долг подорожает на X рублей» без источника обязательств и расчёта.

Ranked содержит весь scored-пул. Feed — top-K с порогом и ограничением 2 события на тему; high-priority override явно конфигурируется. Основную тему выбирать детерминированно из списка B6, не по случайному порядку set. Сортировка: score desc, raw_total desc, event_id asc. Для обновлений один event_id представлен одной выбранной версией. Формат элементов ranked/feed — общий wrapper из INTERFACES.md.

Если поддерживается seen_versions, ключ должен включать company/profile/role context; новая версия или изменившийся профиль не скрываются как уже просмотренные. Это необязательная функция v1 — не тратить на неё время до основной приёмки.

Сохранять hash снимков, rules, mappings, entity resolver; эти версии участвуют в воспроизводимости. Значения evidence_status и limitations не исчезают в top-K.

## Entity mapping

Принимаемый отдельный объект: resolver_version, entries с news_entity_id, company_id, status=verified|synthetic, provenance, область/дата действия. Его не создаёт LLM на основании похожих названий. Неподтверждённые сопоставления не активируют entity/counterparty score.

Synthetic mapping разрешён только в явном demo-режиме для синтетических событий; в live нельзя повысить привилегии, передав строку status=verified в пользовательской новости. Backend/владелец конфигурации отвечает за доверенное происхождение mapping. Лимитировать максимальный вклад графа и считать share в правильном направлении.

## Приёмка

R01–R14 из матрицы. Дополнительно:

- Проверки R10–R14 из обновлённой матрицы: источник времени, качество графа, saturation/caps, долгоживущие события и исполнимые правила.

- Fuel/transport > fuel/IT при фиксированных прочих условиях; изменение только релевантного признака изменяет причину/score.
- Product unknown не равен false и не порождает asserted факт о кредите.
- Rate hold не интерпретируется как повышение. Negated/forecast сохраняются в reasons.
- Конфликтующий rate value не участвует в числовом bonus; business-match остаётся с limited evidence.
- Десять эквивалентных claims с разными валидными ID/duplicate relations не повышают score; повтор одного claim_id должен быть отклонён валидатором. Перестановка claims сравнивается на уровне score с корректными refs и новой event_version, если payload изменился; обходить version_collision для такого теста нельзя.
- Source count и recency без бизнес-сигнала не проталкивают событие в high.
- Неопознанная entity не даёт прямой/графовый балл; автор прогноза не становится target.
- Сумма contributions совпадает со score, шкала 0..1, ссылки валидны, отсутствует NaN.
- Отчёт показывает deferred/excluded и причины, не только удачный top-K.
- На возрасте 30 дней обычный сигнал с 65 базовыми баллами и нейтральной ролью даёт 0.08125 и не попадает в feed.
