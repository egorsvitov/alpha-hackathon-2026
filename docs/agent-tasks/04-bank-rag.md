# Задание агенту 04: RAG для банковской аналитики

Реализуй поиск и упаковку доказательств для аналитика. Прочитай [COMMON.md](COMMON.md), [INTERFACES.md](INTERFACES.md), схемы из 01. На начальном этапе использовать synthetic profile/relevance fixtures; не ждать завершения всего ранкера.

## Цель

По событию и бизнес-контексту вернуть подходящие фрагменты аналитики Альфа-Банка с происхождением, датами, страницами, ограничениями OCR и историчности. На этом этапе не генерировать позицию банка и не делать LLM-вызовы ради самого поиска.

Контрольные точки: **04A — Corpus/индекс/query plan и фильтры**, затем **04B — EvidenceBundle/CLI, повторные попытки через внешний orchestrator, тесты и локальные probes**. Это одно задание одного владельца. Не менять уже работающие core-модули 01–03 ради внутренних типов RAG.

## Существующая основа

Прочитать `llm/rag/prepare_rag.py`, `search_rag.py`, `verify_artifacts.py`, `README.md`, `data/processed/document_catalog.json` и локальную структуру чанков.

Текущие чанки содержат chunk_id, document_id/hash, page, char_start/end, text/hash, extraction, verification_status, published_at/date_status, title/topics, historical_only, retrieval_eligible, source_type. Есть 109 локальных чанков, но они ignored и на чистом checkout могут отсутствовать.

Текущий BM25 читает корпус при каждом вызове и принимает тему строкой. B6 topic rates не совпадает с RAG policy_rate. OCR — черновой; совпадение чанка с OCR не доказывает корректность числа на исходном PDF.

Известные особенности: обзор стали относится к 2021 году несмотря на поздний footer; Gold_digest_August26 имеет неизвестную дату публикации и содержит сентябрьские данные. Не «исправлять» каталог по имени файла или желаемому результату поиска.

## A. Корпус и происхождение

1. Corpus принимает путь, а не читает жёстко зашитый cwd. Проверяет JSONL, уникальность chunk IDs, диапазоны, text hash, форматы дат и метаданные.
2. С corpus_version учитывать чанки, metadata/exclusions и версию индексирования. Изменение только даты документа тоже меняет версию.
3. Если OCR pages доступны, подтвердить page[start:end]==text; если PDF доступны — document SHA-256. Если не доступны, provenance_status явно ограничен, не «passed».
4. `retrieval_eligible=false` исключается всегда из смысловой выдачи. historical_only исключается по default, но допускается отдельным config/query intent с маркировкой.
5. Индекс строится один раз на версию; повторный поиск не читает все PDF и не делает OCR. Пустой/отсутствующий корпус возвращает unavailable/no_bank_evidence с объяснением.
6. Перенос или пересборка корпуса не должна сохранять старые IDs для изменившихся текстов. Для demo/test corpora установить source_kind synthetic и не представлять их как реальные банковские материалы.

## B. Query plan

Составить из B6/профиля/relevance компактные запросы:

- метрика/объект + модальность (например, прогноз ставки) + горизонт;
- экономический механизм, который реально отмечен в Relevance;
- отраслевой/географический контекст, если он связан с событием;
- при конфликте — запрос к первичной/банковской аналитике по предмету конфликта, но без попытки доказать один заранее выбранный вариант.

Не включать всю строку профиля, названия всех продуктов и весь текст событий во все запросы: это размывает поиск. Не использовать числа с конфликтующим источником как единственно верный query anchor.

Начальный mapping:

| B6 | RAG темы/запрос |
|---|---|
| rates / policy_rate / interest_rates | policy_rate, при кредитном механизме credit/bonds |
| inflation | inflation; объект fuel → дополнительно fuel |
| market_indicator + labor/wages | labor |
| gdp/consumption/demand | gdp/consumption |
| gold | gold/commodities |
| steel | steel/commodities; исторический статус проверяется отдельно |
| counterparty | counterparties, только при реальном предметном совпадении |

Неизвестный тег не даёт пустую выдачу из-за непредусмотренного жесткого фильтра: сделать объяснимый общий lexical запрос. Сохранить каждый query, фильтры и причину его создания.

## C. Время и пригодность

Для `as_of` сначала отфильтровать недоступные по дате документы, затем ранжировать. Не ранжировать future-документы и не удалять их только после выбора top-K — иначе можно потерять пригодный результат.

Для date-only publication использовать отдельную задокументированную политику: в строгом intraday replay документ считается доступным с начала следующего дня Europe/Moscow, поскольку точное время неизвестно. Для обзорного daily режима можно сравнивать календарные даты, но обязательно отметить, что внутридневная доступность не доказана. Режим и политика входят в corpus/query config version. Не придумывать точный час выхода документа.

Документ с неизвестной датой исключить из строгого replay; можно сохранить в diagnostics как потенциальный источник для ручной проверки. Не подставлять месяц из заголовка или дату скачивания.

MVP default — strict replay. Отдельный `research_current` режим может возвращать недатированные/исторические материалы только в диагностике с причиной ручной проверки, **не в пригодных hits** и не как актуальную позицию банка. Переключение режима не делает OCR/дату проверенными. Не ослаблять default ради красивого демо.

Дата публикации не сообщает горизонт прогноза. При выборе фрагмента сохранить извлечённый/ручной horizon, если он проверен; если нет — limitation. Старый прогноз можно показать как исторический контекст, но не как текущий факт или последнюю позицию банка автоматически.

## D. Поиск, дедупликация и retries

1. BM25 baseline с фиксированной tokenizer/config версией, детерминированный tie-break по chunk_id.
2. Вернуть ограниченное число кандидатов (старт top_k=5, max_chunks_per_document=2), ограничить суммарный размер контекста. Значения конфигурационные.
3. Устранить почти одинаковые overlapping chunks той же страницы, не теряя locator. Резать цитату по бюджету только целиком с пересчётом end/hash; запрещена незаметная обрезка после создания evidence ID.
4. Hit — кандидат в доказательства. retrieval_score не преобразовывать в вероятность истинности.
5. При отсутствии результатов attempt=1 расширяет topic-фильтр/алиасы, сохраняя даты и exclusions. attempt=2 использует другой обоснованный механизм/уточнение, а не повторяет идентичный запрос.
6. Счётчик попыток принадлежит orchestrator: retriever делает одну явно заданную попытку за вызов. Не запускать вложенные бесконтрольные циклы retry внутри retriever и поверх него.
7. Если результатов нет, status=no_bank_evidence. Если корпус недоступен — unavailable. Если кандидаты есть, но дата/происхождение/охват ограничены — partial. Ни один статус не означает автоматическое подтверждение bank_view.

Русский поиск: Unicode NFKC, casefold, ё→е, токены кириллицы/латиницы/цифр, версионируемые стоп-слова и экономические aliases (ставка/ставки; кредит/кредитование; инфляция/цены; зарплата/оплата труда; ВВП/экономический рост; золото). Синонимы расширяют поиск, а не доказывают экономическую эквивалентность утверждений. Прежнюю обрезку всех слов до шести букв не считать достаточным решением; использовать явные формы/обоснованный tokenizer с тестами и notices при новой зависимости.

Перед top-K применить admission policy: BM25>0 и предметное совпадение основного объекта/метрики или версионируемого экономического concept, а не одни общие слова/регион/название компании. Для общего lexical fallback требовать минимум два содержательных совпадения, если нет явного предметного concept. Сохранить причины допуска/отказа в query diagnostics. Слабые совпадения не добирать до пяти. Если никто не прошёл — `no_bank_evidence` с limitation `insufficient_relevance`; новый несовместимый status не нужен. Тесты: синонимичный русский запрос находит нужный фрагмент, документ с общими словами по другой теме не проходит.

Один вызов retrieve_evidence = одна попытка, attempt строго 0/1/2. При attempt>0 retry_reason обязателен; выход query_plan фиксирует attempt, фактический query, фильтры, temporal mode, retry reason и config/corpus version. Сам retriever не делает дополнительных вызовов. Public signature из INTERFACES.md сохраняется, второй почти одинаковый RetrievalResult не вводить.

Значение ok — пригодные поисковые кандидаты с проверенными обязательными метаданными; partial — кандидаты есть, но происхождение/OCR/полнота ограничены; no_bank_evidence — поиск по доступному корпусу не дал пригодных candidates; unavailable — корпус технически недоступен/не загружен. Пустой успешно загруженный корпус отличается от отсутствующего. Ни один статус не означает, что у банка отсутствует мнение или что найденный текст уже подтверждает bank_view.

## E. EvidenceBundle

Каждый hit соответствует EvidenceBundle schema, созданной в начале этого задания по INTERFACES.md. Полный chunk допустим как начальная цитата, но бюджет prompt собирается позже по смыслу. Для выбранной цитаты хранить точные координаты, исходный/текстовый hash, страницу и version.

Существующая v0.1 Insight.sources отличается от нового EvidenceBundle: не выдавать сырые BM25 hits напрямую в UI. Сначала аналитик/QA выбирает использованные фрагменты; source registry строится кодом в 05.

Ручная проверка должна иметь отдельный record: doc hash, page, boundaries/quote hash, reviewer/method/date. Не поднимать весь PDF или все chunks до visually_checked_excerpt из-за одного проверенного предложения. Автоматическая текстовая проверка не является визуальной проверкой PDF.

## Проверки и команды

```bash
uv run --frozen python -m llm.rag retrieve --event docs/b6-examples/normal.json --profiles data/examples/personalization/profiles.json --company-id DEMO_TRADE --relevance data/processed/personalization/relevance-demo.json --as-of 2026-10-20T18:00:00+03:00 --corpus data/processed/rag_chunks.jsonl --output data/processed/personalization/evidence.json
uv run --frozen python -m unittest discover -s llm/rag/tests -v
```

`relevance-demo.json` должен быть получен из 03 либо из contract-fixture 01 с явной пометкой, а не предполагаться существующим. В README дать команду его подготовки перед retrieve. Для тестов использовать corpus fixture, не обязательные банковские PDF.

Приёмка G01–G08 из матрицы:

- rates находит policy_rate через mapping; неизвестный factor не ломает загрузку.
- Future/undated/historical/excluded документы не попадают в строгий default.
- Date-only boundary проверен на раннем/позднем срезе одного дня.
- Изменение текста, даты или exclusions меняет corpus_version.
- Quote соответствует диапазону и hash; повреждение даёт ошибку, не «похожую» цитату.
- Повторяющиеся перекрытия не заполняют весь top-K.
- Пустой корпус, ноль совпадений и непроверенный OCR дают разные статусы/ограничения.
- Retry расширяет запрос, но не ослабляет временные ограничения ради результата.
- Никаких LLM-вызовов и автоматического скачивания внешних источников.

Если доступен полный локальный корпус, выполнить существующие пять smoke-probes и дополнительные интеграционные запросы из B6. Отдельно указать: это вручную подобранные проверки, не независимый retrieval benchmark. На выходе передать 05 EvidenceBundle, правила статусов и способ получить raw locator для QA.
