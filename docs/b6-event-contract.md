# Выход B6 для модуля аналитики компании

Контракт интеграции v0.1, подготовленный до реализации NLP-модуля. JSON-примеры написаны вручную и целиком синтетические. Работающий producer B6 и HTTP-эндпоинты этим документом не объявляются реализованными.

## 1. Что получает другой участник

**B6 отдаёт `EventBundle` — одно событие с утверждениями источников, числовыми измерениями, временем, цитатами, признаками для поиска и явными конфликтами.** Этот объект одинаков для всех компаний. Повторно извлекать факты из статей внутри аналитики не нужно.

Для персонального анализа объединяются независимые входы:

```text
EventBundle из B6 ───────────────┐
CompanyProfile из ranking/ ─────┼─→ RAG → интерпретация → QA → Insight
Relevance из ранжировщика ───────┤
Роль пользователя + as_of ──────┘
```

Если участник реализует и ранжирование, и интерпретацию, сначала он вычисляет `Relevance` по `EventBundle + CompanyProfile`. Если только интерпретацию — получает `Relevance` готовым. Банковские доказательства он запрашивает через RAG; они не входят в B6.

В B6 **нет** `company_id`, профиля клиента, оценки релевантности конкретной компании, финансового эффекта, готовых рисков и рекомендаций или позиции банка. Не выводить эти сведения из тематических меток. Реальные имена организаций в новостях не означают установленное соответствие обезличенным `SYNTHETIC_U`.

Файлы для начала разработки:

- [JSON Schema](contracts/event-bundle.schema.json) — точные названия, типы и обязательность полей.
- [Обычное событие](b6-examples/normal.json) — учебное решение о сохранении ставки.
- [Прогноз](b6-examples/forecast.json) — ожидание аналитического центра, а не принятое решение.
- [Конфликт](b6-examples/conflict.json) — одно решение, два источника с разными значениями.
- [Неполные данные](b6-examples/partial.json) — план без даты, направления и числа.

## 2. Форма выдачи и верхний уровень

Первый способ передачи — обычный JSON-объект из Python-функции `get_event(event_id)`. Для пакетной интеграции `export_events()` выдаёт JSONL: один полный `EventBundle` на строку. Сейчас вместо producer используются файлы из `b6-examples/`. Транспорт не меняет структуру объекта; внутренний HTTP API пока не нужен.

`get_event` возвращает последнюю доступную версию события. Неизвестный ID — отдельная ошибка `event_not_found` на границе адаптера, а не пустой успешный `EventBundle`. Потребитель сохраняет полученный снимок для воспроизводимости. Историческое получение по `as_of` этот интерфейс пока не обещает.

| Поле | Содержание | Как использовать |
|---|---|---|
| `schema_version` | В этой версии строго `"0.1"` | Проверить совместимость до разбора |
| `event` | ID, версия, заголовок, тип, даты обработки и состояние | Идентификация, обновления, первичная фильтрация |
| `ranking_features` | Темы, отрасли, география, объекты, показатели и экономические факторы | Поиск кандидатов и подготовка запроса в RAG |
| `claims[]` | Структурированные утверждения конкретных источников | Основание для фактической части анализа |
| `sources[]` | Метаданные конкретных версий статей | Происхождение и маркировка материала |
| `evidence[]` | Точные фрагменты текста со ссылками на источники | Цитирование и проверка извлечения |
| `conflicts[]` | Варианты несовместимых утверждений об одном событии | Ограничения для числовых признаков и выводов |
| `relations[]` | Дубли, явные обновления и связанные стадии | Не считать повторные публикации новыми фактами |
| `limitations[]` | Человеко-читаемые ограничения данных | Передать в анализ и итоговый ответ |

Все перечисленные поля обязательны. Пустой массив означает отсутствие переданных элементов, а не доказательство отсутствия соответствующего явления. Неизвестное скалярное значение — `null`, где это допускает схема. Число или участник не выдумываются ради заполнения поля.

Схема и её версия относятся только к выходу B6. Внутренние структуры извлечения могут меняться без изменения этого контракта через адаптер B6. Несовместимое изменение внешних полей требует новой версии и обновлённых примеров.

### `event`

- `event_id`: непрозрачный стабильный ID события, не ID статьи и не ID компании.
- `event_version`: положительное целое; повышается при изменении выдаваемых утверждений, источников, конфликтов, признаков или ограничений. Повторная выдача того же содержания версию не повышает.
- `title`: нейтральный заголовок для навигации; не заменяет `claims` и не является самостоятельным доказательством.
- `event_type`: одна из категорий схемы, включая `other`. Это классификация события, а не бизнес-значимость.
- `first_published_at`: самая ранняя известная дата публикации среди текущих переданных источников; `null`, если все даты неизвестны. Это не дата самого события и не обязательно первое сообщение в мире.
- `updated_at`: время подготовки этой версии B6, с часовым поясом. Не использовать вместо даты новости для оценки свежести.
- `availability`: `active` или `withdrawn`. `withdrawn` означает, что событие больше нельзя использовать как активную основу отчёта; это не самостоятельное утверждение о том, что событие не происходило.
- `quality`: `complete`, `partial` или `insufficient`. Описывает пригодность переданных данных, а не истинность события и не отсутствие конфликта. `partial` означает известную неполноту обработки или нехватку существенных для понимания полей, с пояснением в `limitations`; необязательный неизвестный атрибут сам по себе не требует этого статуса. `insufficient` означает, что данных недостаточно для содержательного анализа. `complete` не является гарантией идеального recall LLM.

При `withdrawn` или `insufficient` не формировать новый уверенный персональный вывод. Если `claims` пуст, нет фактического основания для анализа. Ошибки обработки новой статьи передаются через результат батча, а не маскируются под обычное событие.

### `ranking_features`

`topics` использует уже знакомые фронту категории: `rates`, `sanctions`, `fx`, `trade`, `inflation`, `counterparty`, `industry`, `other`. Остальные массивы — нормализованные строковые метки, а не числовые веса:

- `industries`: отрасли, например `steel`, `retail`;
- `geographies`: коды или нормализованные названия, например `RU`;
- `objects`: объекты, например `policy_rate`, `steel`;
- `metrics`: показатели, например `policy_rate`, `revenue`;
- `factors`: экономические темы, например `interest_rates`, `fx`, `demand`.

Метки помогают отобрать кандидатов. Списки, кроме `topics`, расширяемые; неизвестная метка не должна ломать потребителя. Они не устанавливают факт воздействия, его знак или величину. Например, `interest_rates` не означает, что у компании плавающая ставка по кредиту. Для обоснования использовать исходные `claims`, признаки профиля и RAG-доказательства. Метки могут объединять разные варианты конфликтующих утверждений, поэтому не использовать их как согласованный факт.

## 3. Утверждения, время и числа

Каждый `SourceClaim` содержит:

| Поле | Семантика |
|---|---|
| `claim_id` | ID конкретного утверждения; при исправлении содержания создаётся новый ID |
| `text` | Короткая формулировка утверждения с сохранением модальности |
| `modality` | `asserted`, `forecast`, `plan`, `proposal`, `opinion`, `unknown` |
| `polarity` | `affirmed`, `negated`, `unknown`; отрицание не определяется знаком числа |
| `stage` | Стадия: `announced`, `proposed`, `approved`, `effective`, `repealed`, `observed` либо `null` |
| `attribution` | Кто сделал прогноз или утверждение: `{entity_id, name}` либо `null`; это не обязательно издатель |
| `participants[]` | Участники с `entity_id`, исходно понятным `name` и семантической `role` |
| `action`, `object` | Нормализованные действие и объект либо `null` |
| `geographies[]` | Указанная в утверждении география |
| `time` | Четыре независимых временных поля, описанные ниже |
| `measurements[]` | Измерения с единицами, типом изменения и базой сравнения |
| `evidence_ids[]` | Непустой список фрагментов, обосновывающих утверждение |
| `field_evidence` | Словарь `JSON Pointer к полю утверждения → evidence_ids[]` для проверки конкретных полей |

`asserted` означает «источник сообщает как о факте», а не «независимо установлено». `forecast` не превращается в `asserted` по наступлении даты прогноза. `approved` с будущей датой действия отличается от `effective`. `attribution`, `action`, `object` и роли участников сохраняются независимо: автор прогноза не становится участником прогнозируемого решения.

`entity_id` может быть `null`, если нормализация не установила сущность. ID организаций новостного корпуса находятся в своём пространстве имён; их нельзя сравнивать с `company_id` из банковского CSV без отдельной таблицы соответствий.

### Время

В `time` обязательны четыре поля, каждое может быть `null`:

- `occurred_at`: когда произошло действие или было принято решение;
- `effective_at`: когда оно начинает действовать;
- `observation_period`: за какой период приведена статистика;
- `forecast_horizon`: к какому периоду относится прогноз.

Непустой период имеет `{start, end, text}`. `start` и `end` — включительные календарные границы `YYYY-MM-DD` или `null`, `text` — исходное выражение времени. Одна дата задаётся равными границами; месяц — его календарными границами, что не утверждает конкретный день события внутри месяца. Для неразрешимого выражения сохраняется текст с неизвестными границами. Не подставлять год или дату публикации без оснований; неопределённость описать в `limitations`.

### Числа

Измерение содержит `measurement_id`, `metric`, `kind`, `value`, `unit`, `qualifier`, `comparison_period`.

- `kind`: `level`, `absolute_change` или `relative_change`.
- `value`: десятичная строка, например `"14.0"`, либо диапазон `{"min": "185", "max": "190"}`. Для расчётов использовать `Decimal`. Границы диапазона должны быть упорядочены.
- `unit`: нормализованная единица. Для первой интеграции: `percent`, `percentage_point`, `basis_point`, `RUB`, `USD`, `EUR`, `CNY`, `tonne`, `barrel_per_day`, `count`; составные единицы допускаются строкой, например `RUB/USD`. Неизвестную единицу сохранять и не конвертировать догадкой.
- `qualifier`: `exact`, `approximate`, `gt`, `gte`, `lt`, `lte`. Для диапазона допускаются `exact` или `approximate`; границы и приблизительность не отбрасываются.
- `comparison_period`: база сравнения для изменения, если она указана; для уровня обычно `null`. Период самого наблюдения находится в `claim.time.observation_period`.

Множители единиц приводятся к базовым величинам: 1,31 млрд ₽ → `"1310000000"`, `RUB`. `"14"` в `percent` означает 14%, не 0,14. Изменение с 14% до 15% составляет 1 процентный пункт; нельзя считать его ростом на 1%. B6 передаёт только извлечённые измерения; вычисленные аналитиком величины должны быть отмечены как расчёты.

Одно утверждение может содержать уровень одного показателя и его изменения к разным базам. Рост выручки и сокращение персонала — разные утверждения. Неизвестное число означает отсутствие соответствующего измерения, а не значение 0.

## 4. Доказательства, конфликты и исправления

`sources` описывает конкретные версии статей. `source_id` однозначно указывает на пару `article_id + article_version`. В `content_kind` различаются оригинал, пересказ, синтетический текст, пользовательский материал и неизвестное происхождение. `is_full_original_text = false` не означает автоматически синтетику.

`evidence` содержит `source_id`, `field` (`title` или `text`), `quote` и полуинтервал `[start, end)` в Unicode-символах соответствующего поля неизменяемой версии статьи. Producer гарантирует точное совпадение цитаты. В JavaScript это индексы кодовых точек, а не UTF-16 code units. Полный текст не передаётся в каждый `EventBundle`: его сохраняет модуль источников; для цитирования достаточно `quote`. В примерах весь текст учебной статьи совпадает с единственной цитатой.

`field_evidence` использует пути относительно `SourceClaim`, например `/measurements/0/value` либо `/measurements/0`. Ссылка на объект покрывает его содержательные дочерние поля. Все непустые существенные извлечённые поля должны иметь основания; технические ID не нуждаются в цитате. Утверждение принадлежит одной версии статьи: все его evidence ссылаются на один `source_id`; разные статьи дают разные `SourceClaim`.

Смысловая поддержка числа и его связи с субъектом всё равно проверяется QA. Совпадение текста цитаты не доказывает достоверность публикации.

### Конфликт

В `conflicts[]` каждый элемент задаёт `conflict_id`, описание и варианты `{claim_id, field_path}`. Путь указывает на спорное поле соответствующего утверждения. Значения не копируются в третье «каноническое число».

Пример `conflict.json`: одно установленное решение содержит два утверждения о ставке 20% и 21%. Потребитель обязан:

1. Сохранить оба варианта и их источники.
2. Не выбирать победителя по числу публикаций или порядку массива.
3. Не использовать спорное значение как согласованный числовой признак.
4. При необходимости дать условные сценарии либо сообщить, каких данных не хватает. Независимые от спорного поля выводы остаются допустимыми.

Отсутствие конфликта не равно независимой проверке факта. Конфликт может существовать и при `event.quality = complete`.

### Связи и обновления

`relations` содержит `type`, `from_id`, `to_id`, `target_kind`:

- `duplicate_claim`: эквивалентные текущие утверждения этого события; `target_kind = claim`. Это повторяемость сообщения, а не гарантия независимости источников.
- `updates`: новое утверждение → явно заменённое старое; `target_kind = claim`. Старый ID может отсутствовать в текущем bundle и относится к архиву. Сам текст старого утверждения для анализа текущего события не нужен.
- `related_stage`: более поздняя стадия → предыдущая стадия; `target_kind = event`. Связанный `event_id` может находиться в другом bundle. Нельзя рекурсивно загружать всю историю без ограничения.

Отношение `conflicts_with` из архитектурного плана представлено развёрнутым массивом `conflicts`, чтобы передать конкретные спорные поля. Дублировать его в `relations` не требуется.

`claims`, `sources` и `evidence` описывают текущие свидетельства, история хранится producer отдельно. Исправление публикации меняет её версию и состав текущих утверждений. Если это исправление того же события, его `event_id` сохраняется, а `event_version` повышается. Исчезновение утверждения из новой версии не считается опровержением.

Любое изменение `event_version` делает прежний персональный результат устаревшим. При `withdrawn` прежний результат не показывается как актуальный. Кэш аналитики должен учитывать как минимум ID и версию события, ID и версию профиля, роль, временной срез, версии используемой аналитики и конфигурации генерации.

## 5. Как начать реализацию аналитики

1. Читать `normal.json` вместо вызова producer, проверить его по JSON Schema.
2. Получить профиль компании из соседнего модуля. Для первого локального примера можно использовать `data/examples/synthetic_profiles.json`; это существующая синтетическая заготовка, не финальный контракт профилей.
3. Если ранжирование входит в вашу зону, вычислить причины релевантности, сохраняя ID использованных признаков. B6 не задаёт формулу score.
4. Составить запрос к RAG по типу события, объектам, участникам, периодам и профилю. Учитывать `as_of`; для исторического анализа нужен корректный снимок событий, а не только фильтр даты банковских PDF.
5. Передать генератору текущие утверждения, evidence, ограничения, конфликты, профиль и результаты RAG. Проверить выводы, при необходимости ограниченно повторить поиск.
6. Сформировать выход по существующей схеме `llm/agent/contracts/insight.schema.json`, затем адаптировать его к фронту по `docs/frontend-api-contract.md`.

При подключении живого producer заменяется загрузчик, а не код интерпретации.

### Совместимость с текущей схемой Insight

Входной `SourceClaim` не является готовым выходным `Insight.claim`. В частности, прогноз нельзя переписать как свершившийся факт, даже если текст источника извлечён корректно.

- `Insight.event_id` берётся из `event.event_id`. Текущая схема Insight не содержит отдельного `event_version`; сохранять версию во внутреннем контексте запуска и артефакте трассы, не терять её при кэшировании.
- На выходе `Insight.sources` создавать запись на используемый evidence-фрагмент: `source_id = evidence_id`. Иначе несколько цитат из одной статьи не помещаются однозначно в существующее поле `quote`.
- `locator` может иметь форму `article:<article_id>@<article_version>#<field>:<start>-<end>`; `quote` берётся буквально из evidence. Метаданные издателя и URL сохраняются в B6 для адаптера UI.
- Для синтетического источника использовать `type = synthetic_news`, `verification_status = synthetic`. Для остальных новостных источников — `type = news`, по умолчанию `verification_status = pending_review`; автоматическая проверка цитаты не равна `visually_checked_excerpt`.
- Существующая схема Insight не хранит `content_kind`. До расширения схемы передавать ограничение о пересказе в `limitations` и сохранять метаданные B6 в контексте. Не представлять цитату пересказа как дословную цитату оригинального СМИ.
- ID источников в выходных утверждениях должны ссылаться на фактически использованные evidence; ID признаков — на данные профиля. Вычисленный риск или эффект не копируется из `ranking_features`.
- Если подходящей аналитики банка нет, не создавать утверждения `bank_view`; в ответе фронту `bank_position = null`. Сохранить явную маркировку вывода AI.
- `NewsEvent.sources_count` во фронте — число различных текущих статей, а не цитат и не доказанных независимых источников. При неизвестной дате не выдумывать её ради обязательного поля UI: это ограничение отдельно обрабатывает адаптер фронта.

## 6. Минимальная приёмка на стороне потребителя

- **normal:** решение и ставка переданы с источником; эффект кредита условный, если тип ставки компании неизвестен.
- **forecast:** прогноз не отображается как состоявшееся решение; автор и горизонт сохранены.
- **conflict:** ни 20%, ни 21% не используются как бесспорное значение; варианты видны в ограничениях или сценариях.
- **partial:** неизвестные дата, направление и величина не заполняются догадками; допускается ограниченный результат или запрос уточнения.
- Два профиля могут получить разные интерпретации одного `EventBundle`, не меняя исходные утверждения.
- Повышение `event_version` требует пересчёта; `withdrawn`, `insufficient` и пустые `claims` не проходят как обычный успешный анализ.
- Каждая ссылка результата разрешается в evidence или признак компании; ссылка на архив в `updates` не требует использовать устаревший факт.

Проверка JSON Schema контролирует форму, но отдельно нужны проверки ссылок, уникальности ID, диапазонов, путей конфликтов и цитат. Включённые примеры проверены по схеме и по этим связям; качество извлечения на реальных статьях они не измеряют.
