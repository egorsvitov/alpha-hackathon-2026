# Разбор news-pipeline и план персонализации

Дата проверки: 21 октября 2026 года. Основа новой ветки `news-personalization`: `news-pipeline`, коммит `d0f7c8a` («контракты»). Анализ относится к этому снимку, а не к будущей реализации producer.

## 1. Главный вывод

Контракт позволяет начать нашу часть независимо от готовности NLP. На вход поступает **одно событие, общее для всех компаний**, с утверждениями и цитатами. Наша задача — соединить его с профилем компании, оценить значимость и объяснить влияние с помощью аналитики банка.

```text
EventBundle ─→ проверка и сохранение снимка ─┐
CompanyProfile + роль + as_of ──────────────┼─→ отбор → ранжирование
                                          │          ↓
Банковские документы → RAG ────────────────┴─→ интерпретация → QA → Insight → UI
```

Новость повторно парсить не нужно. Тематическая метка помогает найти кандидата, но не доказывает воздействие на компанию. Например, наличие кредита не сообщает остаток долга, тип ставки и дату пересмотра.

## 2. Что действительно есть в этой ветке

| Компонент | Состояние на проверенном коммите |
|---|---|
| Вход B6 | Описание, JSON Schema Draft 2020-12, четыре ручных синтетических примера |
| Producer NLP | Не реализован в этой ветке; `get_event()` и `export_events()` описывают будущую границу интеграции |
| Компании | Скрипт `ranking/audit_data.py`, примеры профилей; нормализованного CompanyProfile-контракта нет |
| Ранжирование | В этой ветке не реализовано |
| RAG | Есть OCR/чанкинг, BM25-поиск, фильтры по теме и дате; готового аналитического ответа нет |
| Агент | Черновая схема Insight и пример, политика моделей; оркестратора и бюджетного шлюза нет |
| Backend | FastAPI-заглушки с фиксированными ответами, не подключённые к B6/RAG |
| Frontend | Типы, примеры ответов и интерфейс; реальные backend-схемы пока с ними расходятся |

Ранее реализованный ранкер сохранён отдельно в локальной `ml/ranking-baseline`. Создание ветки от `news-pipeline` не перенесло его код. Его следует переносить выборочно и адаптировать вход; сливать целиком старую ветку вместе с прежней историей не требуется.

Исходные CSV и банковские PDF находятся локально и не включены в Git. По сохранённому аудиту: 85 525 строк компаний, 85 514 уникальных ID; один ID содержит 12 конфликтующих записей. Платежей 1 380 585 строк. Эти данные — база профилей, а не размеченные пары «компания—релевантная новость». Локально есть 109 RAG-чанков; свежая копия репозитория без исходников/производных их не получает автоматически.

## 3. Что мы получаем: EventBundle v0.1

Первоисточники: [описание](b6-event-contract.md), [схема](contracts/event-bundle.schema.json), [примеры](b6-examples/).

| Поле | Что означает | Использование у нас |
|---|---|---|
| `schema_version` | Сейчас строго `0.1` | Проверить до обработки; неизвестную версию отклонить явно |
| `event` | ID, версия, тип, даты, доступность, качество | Дедупликация версий, актуальность, решение о допустимости анализа |
| `ranking_features` | Темы, отрасли, география, объекты, показатели, факторы | Отбор кандидатов и формирование RAG-запросов |
| `claims[]` | Утверждения конкретных источников | Основа фактической части; сохранять модальность и отрицания |
| `sources[]` | Метаданные версий статей | Издатель, URL, дата, происхождение, синтетическая маркировка |
| `evidence[]` | Цитата и координаты в версии статьи | Трассируемость результата до фрагмента источника |
| `conflicts[]` | Ссылки на спорные поля утверждений | Исключить спорные величины из безусловных расчётов |
| `relations[]` | Дубли, исправления, связанные стадии | Не усиливать сигнал перепечатками; учитывать обновления |
| `limitations[]` | Ограничения входных данных | Передавать генератору и показывать существенные ограничения пользователю |

Все девять полей обязательны, многие массивы могут быть пустыми. Пустой массив не доказывает отсутствия явления. Большинство объектов запрещает дополнительные поля: собственные профили/оценки нельзя дописывать внутрь EventBundle, их нужно передавать отдельным контекстом.

### Идентичность и версии

- Ключ снимка — `(event_id, event_version)`. Версия повышается при изменении содержания выдачи, а не при каждом вызове.
- `event_id` не равен ID статьи или компании. `source_id` обозначает конкретную версию статьи; `claim_id` — утверждение; `evidence_id` — цитату.
- Новая версия должна инвалидировать старые персональные результаты. Повторная обработка той же версии должна быть идемпотентной; иной payload с тем же ключом — ошибка интеграции.
- `get_event(event_id)` обещает последнюю доступную версию, а не исторический снимок. Для воспроизводимости сохраняем полученный JSON, хэш и время получения у себя.
- Неизвестное событие — `event_not_found`, не пустой успешный bundle. Пакетный формат — JSONL, один bundle на строку.

### Какие утверждения допустимо использовать

`modality` различает сообщение как о факте, прогноз, план, предложение, мнение и неизвестный тип. `asserted` означает позицию источника, а не независимую проверку истинности. Прогноз остаётся прогнозом после наступления его горизонта.

`polarity=negated` нельзя превратить в положительный факт, а `stage=approved` не означает, что решение уже действует. `attribution` сохраняет автора прогноза отдельно от участников события. Эти поля должны доходить до LLM и QA без потери.

### Время и числа

Дату публикации, время сборки B6, дату решения, дату вступления, период статистики и горизонт прогноза нужно хранить раздельно. `updated_at` не подходит для расчёта свежести новости. `first_published_at` — минимум среди текущих переданных источников и может измениться при смене состава источников.

Для воспроизведения на дату `as_of` мало отфильтровать банковские документы: сам bundle должен быть известен системе к этому моменту. Одного `get_event()` для этого недостаточно; нужен архив снимков с временем доступности. Будущий горизонт прогноза допустим, публикация из будущего относительно среза — нет.

Числа — десятичные строки или диапазоны строк. Использовать `Decimal`, сохранять `unit`, `kind`, `qualifier`, базу сравнения и горизонт. `14 percent` — 14%, а не 0,14; процентные пункты и относительные проценты различаются. Уровень ставки не сообщает величину её изменения. Неизвестное число не превращается в ноль.

### Цитаты и конфликты

Цепочка оснований: `claim_id → evidence_ids → evidence.source_id → sources`. `field_evidence` уточняет, какая цитата обосновывает конкретное поле по JSON Pointer. Утверждение принадлежит одной версии статьи.

Координаты цитаты — полуинтервал `[start, end)` в Unicode-кодовых точках; JavaScript-индексы UTF-16 могут отличаться. Полного исходного текста в bundle нет. Поэтому принимающая сторона может проверить длину цитаты и связи, но для проверки точного совпадения с текстом ей нужен доступ к неизменяемой версии статьи. Цитата из пересказа остаётся цитатой пересказа.

В конфликте 20%/21% не выбираем число голосованием и не усредняем. Помечаем спорные поля и их дочерние значения, а также зависимости производных расчётов. Независимые от них выводы допустимы с явным ограничением. `quality=complete` не означает отсутствия конфликтов.

## 4. Сопоставление с профилем компании и ранжирование

| Данные B6 | Данные компании | Что можно оценить |
|---|---|---|
| `industries`, `objects`, `event_type` | ОКВЭД, отрасль | Отраслевую релевантность через явный словарь соответствий |
| `factors`, `topics`, подтверждённые claims | Флаги кредитов, лизинга, депозитов, факторинга | Возможный канал влияния; без выдуманных сумм и условий |
| География claims и меток | Регион, город, страны ВЭД | Географическую экспозицию, учитывая уровень страны/региона |
| Участники claims | ID компании и платёжная сеть | Прямую/контрагентскую связь только при отдельном подтверждённом entity mapping |
| Времена и стадия | `as_of`, роль пользователя | Свежесть, срок действия и приоритет управленческого действия |
| Конфликты, неполнота | Неизвестные признаки профиля | Допустимость вывода и потребность в уточнении |

Реальные названия из новости не сопоставляются с `SYNTHETIC_U` автоматически: в банковской базе нет подтверждённого справочника имён/ИНН. Без таблицы соответствий граф даёт связи обезличенных узлов, но не доказывает, что организация из новости — контрагент клиента. Синтетические сопоставления допустимы только с явной пометкой демо.

Для MVP: широкий отбор по меткам → объяснимые правила значимости → сохранение причин и feature IDs → ограниченный анализ лучших кандидатов. Сложное ранжирование по эмбеддингам можно добавлять после появления оценки качества. Семантическая похожесть не равна финансовой значимости.

Релевантность и достоверность стоит хранить отдельно: противоречивая новость о важном контрагенте может быть высокоприоритетной для проверки, хотя уверенный финансовый вывод невозможен. Отсутствие продукта в этом банке не доказывает отсутствие обязательств в других банках.

## 5. RAG и аналитика

Запрос формируем из подтверждённых объекта/показателя, модальности, горизонта и бизнес-контекста. Например, `policy_rate` + прогноз на конец года + кредитный продукт. Сохраняем цитаты новости отдельно от фрагментов банковской аналитики.

Словари сейчас различаются: B6 использует тему `rates`, а RAG — `policy_rate`; среди RAG-тем также есть `gold`, `steel`, `labor`, `gdp`, `commodities`. Нельзя передавать `topics[0]` прямо в фильтр RAG: для `rates` получится пустая выдача. Нужен собственный версионируемый mapping с fallback-поиском без узкого фильтра. Расширяемые метки B6 должны сохраняться, даже если правила пока их не знают.

RAG возвращает кандидатов в доказательства, а не готовую позицию банка. Проверяем дату публикации, горизонт прогноза, предмет и качество OCR. Если поддержки нет, `bank_position=null`. Повторный поиск ограничен; после исчерпания попыток — ограниченный ответ, а не выдуманное подтверждение.

Предлагаемая цепочка нашей части:

1. Проверить bundle по схеме и межполевым ограничениям, сохранить снимок.
2. Применить политику доступности/качества и временного среза.
3. Получить нормализованный профиль и причины релевантности.
4. Получить evidence из RAG с ограниченным повторным поиском.
5. Сгенерировать условные риски, возможности и следующий шаг; отделить факт, мнение банка и вывод AI.
6. Проверить ссылки, модальность, даты, числа и наличие признаков клиента для персональных выводов.
7. Сохранить trace, результат и расход; преобразовать ответ для UI.

## 6. Разрывы между действующими контрактами

| Разрыв | Что нужно согласовать/реализовать |
|---|---|
| CompanyProfile пока не зафиксирован | JSON Schema профиля: `company_id`, `profile_version`, нормализованные значения, неизвестность, `features[]` с ID и происхождением |
| Синтетические профили и UI называют продукты по-разному | `loan/deposit` против `loans/deposits`; выбрать внутренний формат и адаптер |
| UI требует выручку в млрд рублей | Единицы исходного CSV пока не подтверждены; хранить raw и статус единиц, не выдавать гипотезу за установленный факт |
| UI-профиль требует `is_synthetic: true` | Для реальных обезличенных профилей нужен `boolean` и отдельная семантика демо; иначе реальные данные будут маркированы синтетикой |
| Insight v0.1 не содержит `event_version` и `profile_version` наверху | Сейчас сохранять в контексте/trace; желательно расширить схему совместно с владельцем |
| Insight источники не хранят publisher/URL/content_kind | Сохранять B6-снимок; адаптер строит UI-evidence по исходным метаданным |
| SourceClaim и выходной Insight.claim различаются | Явное преобразование; на выходе ссылка на evidence-фрагмент, а не просто статью |
| Статусы агента и UI различаются | Агент: ready/limited/needs_clarification/...; UI: ok/insufficient_data. Утвердить отображение ограничений, ошибок и исчерпания бюджета |
| UI требует дату новости, B6 допускает null | Поддержать неизвестную дату в типах/рендеринге или отдельный честный сценарий; не подставлять updated_at |
| UI заменяет unknown-значимость на low | Это теряет отличие «не знаем» от «малозначимо»; согласовать отдельную маркировку неопределённости |
| UI ожидает вклад факторов в сумме равный score | При переносе ранкера учесть шкалу 0..100 против 0..1, клиппинг и штрафы; показывать именно итоговые вклады |
| Backend response_model не совпадает с frontend types | Например, `synthetic_u` вместо `company_id`, строковые блоки анализа вместо списков утверждений; требуется backend-адаптер |
| Пустые риски UI трактует как «не выявлены» | Для неполноты это вводит в заблуждение; показывать причину отсутствия и статус данных |

Ключ кэша: минимум event ID/version, company ID/profile version, роль, `as_of`, версия конфигурации и использованного корпуса аналитики. Отзыв события должен инвалидировать и выдачу ленты, и уже сохранённые карточки. Простой URL по event ID не является ключом персонального результата.

## 7. Политика на четырёх примерах

| Пример | Ожидаемое поведение нашей части |
|---|---|
| `normal.json` | Решение о сохранении 14%, не повышение/снижение. Для кредита — условный канал стоимости фондирования; без утверждения об изменении платежа |
| `forecast.json` | Ожидание учебного аналитического центра на 23 октября, а не принятое решение. Сохранить автора и горизонт |
| `conflict.json` | Два значения одного решения. Не использовать 20% или 21% как согласованную ставку; показать ограничение/сценарии |
| `partial.json` | Неизвестны дата публикации, срок, направление и число. Ограниченный анализ/уточнение; свежесть не рассчитывается как для датированной новости |

Дополнительно: `withdrawn` убирает текущую карточку из активных; `insufficient` или пустые `claims` не дают обычного успешного анализа. Такие события можно сохранить для аудита и обработки обновлений. `partial` не означает автоматический полный отказ, а `complete` не означает доказанную истинность.

## 8. Выполненные проверки и их пределы

Четыре примера прошли JSON Schema с включённой проверкой форматов и отдельные структурные проверки: уникальность ID, ссылки evidence/source, единый источник утверждения, пути field_evidence/conflicts, длины цитат, порядок дат/диапазонов, минимум дат публикации.

Пять испорченных копий normal-примера прошли саму JSON Schema, но были отклонены дополнительной проверкой: несуществующий evidence, неверный конец цитаты, обратный числовой диапазон, обратный период, неправильная первая дата публикации. Это подтверждает необходимость семантического валидатора на границе приёма.

Повторяемый исследовательский скрипт: [review_event_bundle.py](../scripts/review_event_bundle.py). Запуск из корня:

```bash
uv run --no-project --with jsonschema==4.25.1 python scripts/review_event_bundle.py
```

Это проверка примеров и части инвариантов, не готовый production-валидатор и не оценка качества извлечения. Смысл цитат, полнота field_evidence и точное совпадение с отсутствующим полным текстом статьи независимо не проверены. Живой producer, API, LLM, стоимость и end-to-end сценарий не тестировались; вызовов LLM не было.

## 9. Следующие шаги нашей ветки

1. Зафиксировать CompanyProfile и Relevance, включая feature provenance, неизвестные значения и шкалу score.
2. Перенести полезный код профилей/графа/ранжирования из ML-ветки, сохранив EventBundle как внешний вход. Не сводить bundle к старой упрощённой новости с потерей модальности и конфликтов.
3. Реализовать загрузчик примеров/JSONL, полный валидатор ссылок и хранилище версий. Держать сырой снимок рядом с подготовленным контекстом.
4. Написать отображение словарей B6 → отрасли/продукты/география/RAG и первый объяснимый скоринг без LLM.
5. Показать одно событие для двух разных компаний с разными причинами значимости, проверяемыми feature IDs и честными ограничениями.
6. Подключить RAG и затем разрешённую LLM через бюджетный шлюз; сделать четыре сценария выше и проверки обновления/отзыва.
7. Согласовать адаптер Insight → frontend с backend-разработчиком. Метрики проверять на отдельно размеченных парах компания—событие; синтетические примеры контракта не являются независимым бенчмарком ранжирования.

У владельца B6 нужны: единый словарь нормализации отраслей/географии/действий, гарантия стабильности ID и версий, способ получать обновления/отзывы и неизменяемую версию исходной статьи для QA. Начать разработку по существующим примерам можно до ответов на эти вопросы.
