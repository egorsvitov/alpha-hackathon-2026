# План реализации Impact Retriever

Статус: задачи на реализацию, не отчёт о готовом retrieval. Архитектура — [architecture.md](architecture.md), выход — [contract.md](contract.md). Старый ранкер удалён; не использовать его код или результаты как механизм нового отбора.

## Правила для исполнителя любой задачи

- Прочитать эти три документа и соответствующий код инфраструктуры. Сохранить пользовательские незакоммиченные изменения.
- Работать в `retriever/`; общие B6/profile/storage компоненты пока остаются в `ranking/`.
- Не выполнять оплачиваемые LLM-вызовы без настроенных цен, резервирования бюджета и разрешённой модели. До этого — шаблонные представления и offline fixtures.
- Не импортировать `llm.agent.tests.relevance_fixture` в runtime. Это только проверка старого аналитического контракта.
- Не создавать «живые» поля путём подстановки demo-данных. Demo/live и отсутствие данных различаются явно.
- Для каждого артефакта сохранить версии входов и конфигов; для нового пакета/модели — pin/lock и THIRD_PARTY_NOTICES.
- Тесты формата, сохранности и скорости не выдавать за качество рекомендаций. Gold-разметка людьми и model-generated labels хранятся раздельно.
- В финальном отчёте задачи указать изменённые файлы, фактические проверки, известные ограничения и следующий зависимый этап.

## Порядок и границы поставок

```text
R1 контракт и foundation ─┬→ R2 профиль компании ──┐
                         └→ R3 события и индекс ──┼→ R4 каналы → R5 fusion/handoff
R0 evaluation protocol ───────────────────────────┘                  │
                                             R6 оценка ←────────────┘
                                             R7 аналитик/backend ← R5 + R6
                                             R8 incremental/perf ← R3 + R5
```

R0 начинается до тюнинга. R2 и R3 независимы после R1. Это зависимости работ; отдельные агенты сейчас не запущены. Первый проверяемый срез: одна компания → индекс фиксированного окна → кандидаты с исходными доказательствами, без обязательного LLM.

## R0. Оценка качества до подбора правил

**Вход:** 100 собранных новостей в эксперименте; реальные/синтетические профили; существующие B6-примеры; Domodedovo attachment, если доступен локально.

**Сделать:**

1. Создать `retriever/evaluation/README.md`, `judgments.schema.json`, `cases.jsonl`, `evaluate.py`. Примеры и разметка разделены; raw news/реальные профили остаются в ignored artifacts.
2. Выбрать 8 профилей: перевозки автомобильные и авиационные, IT, торговля с/без ВЭД, строительство, производство, компания с неполными данными. Для каждого зафиксировать именно известные признаки; при отсутствии подходящей реальной записи явно использовать synthetic profile. Названия из новостей не сопоставлять анонимным ID без mapping.
3. Использовать общее фиксированное окно до 100 уникальных событий; 800 company-event пар на одну фиксированную роль CFO как первый полный assessment set. Пользовательские роли проверить отдельным расширением, не смешивать их без меток.
4. Шкала: 0 нет обоснованной связи; 1 тематическая/слабая связь; 2 правдоподобное влияние при явно названных условиях; 3 прямая существенная связь с подтверждёнными предпосылками. Unknown/not_judged — отдельные значения, не 0.
5. Каждая метка содержит basis feature/claim refs, missing_context, annotator, annotation_version и synthetic flag. Часть меток 2/3 размечают два человека; расхождения сохраняются. LLM может предложить weak label, но он не попадает в human test автоматически.
6. Разделить dev/test по story groups/времени до настройки. Никаких перепечаток одной истории в обеих частях. Дополнительно проверить перенос на удержанные профили, если размер набора позволяет.
7. Метрики: Recall@10/20/30 до аналитика (relevant = label>=2), recall класса 3 отдельно, Precision@20, nDCG@10 при graded labels, доля дублей, покрытие, latency. Для каждой метрики показать число запросов и positives; queries без positives отмечать отдельно, не подменять неопределённый recall нулём.
8. На 100 событиях не использовать Recall@100/300 как доказательство качества. Для неполной pooled-разметки явно писать pooled recall/judged coverage и не объявлять его полным recall.

**Проверка:** ручной мини-пример метрик с известным ответом; пропуск разметки не считается отрицанием; duplicate cluster split запрещён; результаты содержат hash dataset/split/config.

**Готово:** код оценки и пустая форма human-judgments работают; статус качества остаётся `not_evaluated`, пока независимые метки не готовы. Имплементация поиска может идти параллельно разметке.

**Сделать:**

2. Реализовать typed request/result и две стадии проверки: JSON Schema + refs/hashes/time invariants. Составные claim refs обязательны.
3. Сделать fixtures: ready с одним member, empty, partial/conflict/scenario, cluster из двух snapshots, degraded с причиной. Для ready использовать существующий B6 v0.2 целиком, а не сочинённую неполную копию.
4. Зафиксировать четыре роли в lower-case и timezone-aware `as_of`; неизвестный company_id — ошибка, не пустой профиль.
5. Включить retriever в setuptools package discovery; зависимости добавлять в root pyproject/uv.lock по фактической необходимости. Не тащить `.venv` и экспериментальные artifacts в пакет.

**Проверка:** неверный hash, чужой feature_id, потерянный conflict, string event_version, неподдерживаемая версия отвергаются; source refs двух событий с одинаковым claim_id разрешаются раздельно.

**Готово:** контракт валидируется автономно. Аналитик и backend ещё не считаются подключёнными.

## R2. Профиль и запросы компании

**Вход:** CompanyRepository, normalizer, feature provenance, уточнения QA по полям.

**Сделать:**

1. Исправить/проверить revenue metadata (RUB/2025/placeholder 1000), NEGATIVEMARK и CL_TYPE; versioned mapping и тесты на эти значения. Не превращать неизвестное/пропуск в False/0.
2. Реализовать `company_views.py`: business, finance, trade_geo; каждый view имеет feature_ids, text/hash, quality, unknowns, version.
3. Шаблоны описывают известные признаки и явно условные вопросы: «есть кредит; возможны изменения условий нового финансирования; тип действующей ставки неизвестен».
4. Не кодировать пустые views. Регион регистрации не превращать в маршрут, страны ФТС — в валюту, продукты — в величины денежных потоков.
5. Кэшировать views по hash релевантного содержимого профиля и версии шаблонов. Изменение другой компании не должно менять content-hash этой компании. Импорт/полный source hash хранить отдельно как provenance.
6. GROUP_ID передавать в контекст; graph/group expansion оставить выключенным до отдельного эксперимента с доказательствами.

**Проверка:** два профиля одной отрасли с разными продуктами дают одинаковый business и разные finance; неизвестный продукт не становится наличием; изменённый соседний CSV-record не инвалидирует текст текущей компании; нет ветвления по demo IDs.

**Готово:** шаблонные запросы для любого валидного профиля; ни одного LLM-вызова.

## R3. Представление событий и воспроизводимый индекс

**Вход:** B6 v0.2 через EventStore; заданные as_of/window. Данные CPU-эксперимента помечены quote-only и не заменяют тест полноценного препроцессинга.

**Сделать:**

1. Реализовать `eligibility.py` и `event_views.py`: latest visible version → availability/quality → временное окно → поисковый текст. Сохранить исходный bundle.
2. Разрешить other, пустые factors/industries, partial с evidence. Проверить future receipt/update/source dates, withdrawn, insufficient. Unknown publication обслуживать только по явно выбранной политике с limitation.
3. BM25 document = одно событие. Dense fragments = claims/chunks с offsets и refs; в тексте присутствуют контекст сценария/отрицания/атрибуции. Для длинного одиночного claim использовать overlapping token windows.
4. Реализовать `embeddings.py` с интерфейсом encode_queries/encode_documents и model fingerprint. Первым подключить pinned E5-small CPU; policy `query: company`, `passage: event`. Не использовать старые npy с обратными prefix roles.
5. Реализовать `index.py`: exact float32 matrix + BM25 corpus + metadata manifest. Публиковать в temp directory, проверить hashes/размеры, затем atomic rename. Незавершённый индекс не читается.
6. Входной snapshot фиксирован на as_of. Изменение модели, текста или chunk policy требует нового индекса. Повреждённый/mixed-model индекс отвергается явно.

**Проверка:** новая withdrawn не восстанавливает старую active; новый future update не виден в прошлом; существенный claim после 512 токенов доступен через отдельный chunk; partial сохраняет claims/conflicts; reopen index даёт те же результаты; CPU provider проверен; веса не включены в Git.

**Готово:** команды build/load индекса фиксированного окна без поиска компаний и без LLM.

## R4. Независимые поисковые каналы

**Вход:** views компании и опубликованный индекс.

**Сделать:**

1. `channels/lexical.py`: BM25 по событию, NFKC/casefold/ё→е, одинаковые tokenizer rules для query/doc, сохранение сущностей/чисел/аббревиатур. Отдельно измерить улучшение от русского stemmer; любой пакет фиксируется в lock/notices.
2. `channels/dense.py`: точное cosine/dot product нормированных векторов, chunk→event max, top-K на каждый непустой view. Результат содержит winning chunk и view, не выдуманный механизм.
3. `channels/structured.py`: подтверждённые entity matches и versioned conditional factor/exposure matches. Не переносить старые баллы. Нет совпадений — пустой канал, не фильтр на остальные.
4. Единый ChannelHit: snapshot key, rank, raw_score, channel, matched feature IDs, claim/chunk refs, match_kind и limitations.
5. Каждый канал имеет отдельные тайминги и ошибки. Запрос не читает CSV заново и не загружает модель на каждое событие.

**Проверка:** sparse/dense находят события с other и пустыми factors; валютный/продуктовый факт не возникает из неизвестного; no lexical overlap даёт пустой BM25; exact search сверяется с ручным dot product на маленькой матрице; ограничения as_of применяются до top-K.

**Готово:** можно получить и оценить три независимых списка, без fusion.

## R5. Слияние, ограничения контекста и handoff

**Вход:** результаты R4 + профили и snapshots R1–R3.

**Сделать:**

1. Реализовать fusion по архитектуре: max-RRF по dense views, затем сумма трёх групп каналов; deterministic tie-break; dedup по snapshot/event.
2. Точные дубли не должны занимать весь бюджет. Для разных event IDs объединять только по явным доказательствам/правилам; сохранять member snapshots и grouping version. Отказ от grouping лучше ошибочного объединения независимых событий.
3. Budget selection: настраиваемые лимиты событий и фактических входных токенов модели аналитика. Пока модель не подключена — offline counter явно помечен как estimate, резерв и отсутствие гарантий точного тарифа. Не обрезать conflicts/evidence ради лимита.
4. Проверить резерв для уникальных каналов; все отброшенные кандидаты сохранить в trace с reason. Не использовать старые min_feed_score/topic caps.
5. Реализовать `service.retrieve_candidates` и CLI `retrieve`; результат = candidate_batch + trace. Полный контекст компании один раз на batch; raw scores только в trace.
6. Отличать empty, degraded, budget_exhausted и ошибку индекса. Данные слабого dense-only match маркировать гипотезой, не установленным бизнес-влиянием. Порог relevance допускается только после dev-калибровки.

**Проверка:** одинаковые входы → одинаковая выдача; добавление лишнего chunk не повышает score без лучшего match; отсутствие одного view не ломает запрос; поломка всех каналов не превращается в empty success; 20–40 нерелевантных событий не добавляются ради количества; loss после budget измеряется.

**Готово:** первая полная offline цепочка компания → кандидаты с проверяемым B6, без аналитических выводов.

## R6. Сравнение методов и решение о релизе

**Вход:** human-gold R0 и реализация R5.

**Сделать:**

- Сравнить BM25, dense single-view, dense three-view, hybrid single-view, hybrid three-view при одном embedding backend, одном окне, split и одинаковом бюджете.
- Затем отдельно сменить encoder: E5-small → E5-large/BGE-M3. Не менять одновременно шаблоны, grouping, бюджет и модель.
- Только затем отдельно проверить LLM profile enrichment, observed payment context, grouping, role weighting. У каждой абляции один меняющийся фактор.
- Для каждого варианта: Recall до и после budget, recall label=3, nDCG/precision, duplicate rate, доля unknown и degraded, p50/p95, tokens, память, версии. Показать ошибки Domodedovo и других типов событий отдельно.
- Правила/пороги подбирать только на dev. Сохранить per-query результаты и разброс; маленькая выборка не даёт уверенных выводов о всей базе.

**Начальные цели, подлежащие согласованию до просмотра test:** Recall@20(label>=2) >=0.80; ни одного пропуска заранее зафиксированных критических regression cases; hybrid не хуже выбранного простого baseline по полноте после того же token budget. При малом числе positives писать абсолютные counts, не только проценты. Это цели, не текущие измеренные результаты и не гарантия полноты бизнеса.

**Проверка:** неизменяемая test-разметка, отсутствие temporal/story leakage, точное воспроизведение отчёта по команде evaluate.

**Готово:** обоснован выбор конфигурации либо явно зафиксирован провал, требующий изменения representations. Без меток релиз не называется quality-validated.

## R7. Аналитик и backend — отдельная интеграция

**Вход:** ImpactCandidateBatch, текущий QA/source registry/RunStore и Bank RAG; действующий UI-контракт Влада/Максима.

**Сделать:**

1. Новый context builder принимает batch/member, company context и refs без Relevance score. Сохранить проверки B6, hashes, времени и всех конфликтных вариантов. Не передавать только совпавшие features.
2. Аналитик оценивает механизм по каждому candidate_id: supported/conditional/insufficient/rejected, основания, urgency/role relevance. Получает Bank RAG через ограниченный инструмент; not_found не создаёт позицию банка.
3. Подключение разрешённого провайдера — через отдельный gateway, budget reservation, фактический usage, retries/cache. Идентификатор модели и тарифы берутся из разрешённой конфигурации. FixtureGenerator остаётся тестовым режимом, не «живой аналитикой».
4. QA проверяет источники, сценарии и отделение банковской аналитики от AI. Допускаются ноль готовых инсайтов и запрос уточнения.
5. Финальную сортировку делать по аналитическому результату; первый вариант без дополнительного listwise LLM. При отказе модели отдавать pending/failed-analysis, а не переименованный cosine в importance.
6. Новый backend adapter: strict B6 v0.2, точные snapshot hashes, составные refs. Старый отказ v0.2 и fallback без hash не переносить. Исторический adapter можно оставить только для явно legacy данных.
7. Кэш включает profile/event/bank/model/prompt/QA versions; tenant/company/role проверяются при чтении. Не делать одинаковые запросы параллельно без single-flight/резерва.

**Проверка:** B6 v0.2 → retrieval → analyst fixture → API; отдельный live smoke только после настройки бюджета; отсутствующая позиция банка; отказ/таймаут API; неизвестная компания; scenario/negation/conflict; trace восстанавливает каждое доказательство; front не показывает retrieval score как важность.

**Готово:** согласованный сквозной контракт и взаимодействующий сценарий. Локальный retriever отдельно может быть готов раньше.

## R8. Инкрементальность и нагрузка

**Вход:** выбранная после R6 конфигурация, целевой CPU-сервер и профиль нагрузки.

**Сделать:**

1. Обновление индекса только на новые/изменённые события; новый manifest публикуется атомарно. Читатель заканчивает запрос на одном snapshot.
2. Receipt/updated watermark, явный index_stale, обработка tombstones/withdrawn. Исторические запросы обслуживать только соответствующим snapshot; никакой скрытой подмены текущей версией.
3. Encode-cache по text+encoder fingerprint; компания — по content profile hash. При смене модели новые query и document vectors публикуются вместе.
4. Прогнать смешанные длины и длинные chunks при 60 входящих новостях/мин плюс concurrent feed requests. Число embedding calls может быть больше числа новостей из-за chunking; считать оба.
5. Замерить p50/p95, RSS, очередь, пропускную способность, cold/warm start. Наши локальные E5-цифры — ориентир, не серверный SLA.
6. При реальном bottleneck exact search сравнить ANN с exact по recall, latency и памяти. Не внедрять ANN до измерений.

**Готово:** воспроизводимый нагрузочный отчёт на целевом железе, bounded queues/timeouts, понятное поведение при перегрузке.

## Что сознательно отложено

GNN, ColBERT, обученный reranker, дистилляция, полный LLM-анализ 85 тысяч компаний, второй LLM listwise pass, внешняя векторная БД. Их можно добавлять через интерфейсы encoder/channel/fusion после появления разметки. Наличие интерфейса — возможность замены, не обещание прироста качества.
