# Состыковка персонализации с backend Влада

Дата: 21.10.2026. Проверен актуальный `origin/feature/backend`, commit `2b68a54508021345dd1425814ae5dc4372c329a5` после `git fetch origin --prune`. Backend прочитан непосредственно из Git; его ветка не вливалась в рабочую ветку. Наш блок — текущие локальные файлы `ranking/`, `llm/agent/`, `llm/rag/`.

## Результат

Прямой Python-вызов подходит. Однако подключение сейчас не готово: backend-адаптер ожидает другой результат ранкера, в DataStore он ещё не используется, а карточки и уточняющие ответы пока формируются демологикой backend.

Необходимы три интеграционных слоя: подготовка входов ранкера, адаптация ленты и адаптация карточки/чата. B6 v0.2 — отдельная обязательная миграция нашего потребителя.

## 1. Что уже есть у Влада

- Эндпоинты компаний, ленты, карточки, вопроса, загрузки новости, feedback и метрик.
- `backend/app/services/ranking_adapter.py` с функцией `adapt_ranking_response_to_feed`.
- В backend-модели фактора добавлены `feature_ids`, `event_fields`, `basis`, `provenance`.
- Роли совпадают: `ceo`, `cfo`, `treasurer`, `chief_accountant`.
- Ожидаемый диапазон score совпадает: 0–1.

Но `DataStore.get_feed()` по-прежнему вызывает собственный `_score_event_for_company()`, а не наш `rank_events`. Карточка, чат и метрики тоже остаются самостоятельными демонстрационными реализациями. Сам факт добавления файла адаптера не подключил ML.

В `origin/main` на момент проверки файла `ranking_adapter.py` нет. Для интеграции важно ссылаться на точный commit/ветку, а не считать изменение уже доступным в main.

## 2. Реальный Python-контракт ранкера

```python
from ranking.engine import rank_events, load_rules

response = rank_events(
    snapshots,       # list[StoredEvent], не сырые новости и не B6 dict
    profile,         # нормализованный ML-профиль с features/provenance
    role=role,
    as_of=as_of,     # datetime с timezone
    rules=load_rules(),
    entity_mapping=None,
    top_k=5,
)
```

Сначала выполняются проверка/импорт B6 в наш EventStore и выбор версий на дату. Профиль приходит из нашего CompanyRepository либо согласованных ML-fixtures. UI-модель компании не является входным ML-профилем.

Результат содержит `feed`, `ranked`, `deferred`, `excluded`, версии и дату среза. Каждый элемент `feed` выглядит так:

```text
{
  snapshot: {
    event_id, event_version, payload_sha256,
    received_at, source_mode, ingest_id
  },
  relevance: {
    company_id, profile_version, user_role, as_of,
    score, level, reasons, candidate_channels,
    feature_ids, claim_ids, evidence_status,
    limitations, scoring_version, rules_sha256, ...
  }
}
```

В `feed` нет полного `event`, bundle и словаря всех признаков профиля. Backend-адаптеру дополнительно нужен доступ к **точным входным StoredEvent и профилю**. Нельзя подставлять новейшее событие вместо сохранённой версии: карточка перестанет соответствовать посчитанной ленте.

## 3. Подтверждённые проблемы адаптера

В изолированном окружении NLP загружены реальные схемы/адаптер из commit Влада и передан настоящий результат нашего `rank_events` на синтетическом тестовом событии.

| Поле | Наш результат | После текущего адаптера |
|---|---|---|
| ID | `demo:rate-hold` | `unknown` |
| score | `0.36741214813127643` | `0.0` |
| причины | 2 структурированные причины | пустой список факторов |
| заголовок | доступен в исходном bundle | пустая строка |
| дата | доступна в исходном bundle | константа `2026-10-21` |

Это молчаливое искажение, а не ошибка в самом скоринге.

Причины и необходимые изменения:

| Сейчас в адаптере | Должно быть |
|---|---|
| `item.get("score", 0)` | `item["relevance"]["score"]`; отсутствие — ошибка |
| `item.get("reasons", [])` | `item["relevance"]["reasons"]` |
| `item.get("event", {})` | bundle из точного StoredEvent по snapshot и hash |
| `reason["event_fields"]` | Наше поле `event_paths`, затем явный mapping в DTO |
| `features_used` в элементе feed | Выбор записей из `profile["features"]` по feature_ids |
| `published_at`/фиксированная дата | `bundle.event.first_published_at`; неизвестную дату не выдумывать |
| `event_type` как UI topic | Явная таблица event_type→topic либо согласованный выбор ranking_features.topics |
| `contract_version`/`version` в event | Версия находится в корне `bundle["schema_version"]`; валидация до ранкера |
| score > 1 автоматически делится на 100 | Чужой/некорректный диапазон отклоняется; наш score и contribution уже 0–1 |
| bank position выводится по типу новости | Только наличие допустимых bank_view claims после QA |

Отдельная проба показала: объект, подогнанный под ожидаемую адаптером форму и помеченный `event.schema_version="0.2"`, не отвергается. Проверка версии сейчас не является валидатором B6: она смотрит другие поля. Проба проверяет только адаптер, не обход валидатора нашего ML-блока.

Для трассируемости мало оставить `feature_ids`: надо сохранить `claim_ids`, reason_id, пути события, версии/hash и ограничения. Их можно добавить в DTO либо сохранять полный ML-артефакт на backend и отдавать явную ссылку/идентификатор артефакта. Сам текст detail происхождение не заменяет.

## 4. Профиль, события и время

У backend продукты называются `loans`, `deposits`, `guarantees`; у ML — `loan`, `deposit`, `guarantee`. У нас есть tri-state признаки, quality, origins, страны и ограничения выручки. UI требует `revenue_bn_rub: float`, хотя единицы реального исходного значения не подтверждены; реальная выручка не должна автоматически превращаться в миллиарды.

Рекомендуемая схема: **ML-профиль — источник для ранкера**, UI-профиль — его отображение через отдельный mapper. Для первого демо выбрать один общий набор синтетических компаний с одинаковыми company_id и profile_version. Независимые наборы backend и ML сейчас имеют разные ID. В backend CompanyProfile также жёстко задано `is_synthetic=True`: реальным профилям потребуется отдельное согласование DTO.

Backend-лента не принимает as_of и не возвращает event_version/hash. Сервер может выбирать as_of сам, но должен закрепить его и версии на весь запрос; карточка и чат должны продолжать тот же контекст. При обновлении — явный новый расчёт, а не незаметная подмена источников.

Неизвестный ID компании/новости сейчас заменяется первым seed-объектом. Для настоящего режима требуется 404, иначе можно показать анализ чужой компании или события.

## 5. Карточка и чат — отдельный контракт

Наш [Insight v0.2](../llm/agent/contracts/insight.v0.2.schema.json) не равен backend Insight. Проверка настоящего fixture-результата через схему Влада дала ошибки на `status`, `generated_by`, `event`, `relevance.explanation`, структурированных reasons, `what_happened` и `trace`.

| ML | Backend / требуемое решение |
|---|---|
| `claims` с section | Разложить по what_happened, why_it_matters, risks, opportunities, next_actions, bank_position |
| `sources` и source_ids | Evidence и evidence_ids через стабильный mapping; сохранить исходные refs/hash/границы |
| `section_states` | Передавать статусы разделов; пустой список не означает отсутствие риска |
| `generation_mode="fixture"` | Backend generated_by сейчас допускает только live/cached; расширить DTO |
| `status="limited"`, QA axes | Backend сейчас допускает ok/insufficient_data; сохранить подробный статус/QA, не объявлять fixture готовой живой аналитикой |
| trace — объект с шагами и artifact_ids | UI trace — список; показывать реальные шаги, сохранять полную трассу отдельно |
| unknowns с affected_paths/question | Явный mapper в UI unknowns |

Тестовый генератор пока не делает полноценный финансовый анализ. Нельзя заполнять отсутствующие риски, численные эффекты и позицию банка существующими общими фразами DataStore, выдавая их за результат ML.

Уточняющий вопрос должен идти в нашу логику child run с реальным run_id. Проверки company/role/event, актуальности, перезапуска и наследования контекста уже есть в ML; backend сейчас возвращает шаблон и заявляет дополнительный поиск независимо от реального выполнения.

Загрузка новости сейчас принимает text, но сохраняет только краткую карточку в памяти. Для живого пути надо сохранять текст в архиве B2, запускать preprocessing→publish→ingest и показывать состояние обработки. Иначе загруженная новость до нашего анализа не дойдёт.

## 6. Запуск и ответственность процесса

Backend Dockerfile копирует только backend и ставит backend lock. В таком образе нет `ranking`, `llm`, JSON-схем и конфигов, RAG-корпуса и зависимости jsonschema из нашего блока. Для in-process нужна сборка из корня монорепозитория с общей согласованной средой и явными локальными volumes для данных/состояния. Сырые конфиденциальные данные не добавлять в образ или Git.

Долгий синхронный ML-вызов нельзя выполнять прямо в async handler, блокируя event loop. Для бейслайна достаточно sync handler/контролируемого threadpool. Но SQLite connection нельзя просто перенести между потоками: наш EventStore создаёт обычное sqlite3-соединение. Соединения должны создаваться и использоваться в своём потоке, либо ML выполняется выделенным исполнителем с очередью. Выбрать одну модель выполнения и проверить её.

Владов обработчик карточки сейчас превращает любое исключение в 404. Для настоящего ML различать not found, неподдерживаемый/невалидный вход, недоступность provider и внутреннюю ошибку. Отсутствие результатов и поломка ML не должны подменяться seed-аналитикой.

## 8. Минимальная приёмка

1. Сравнить настоящий rank_events→adapter→FeedItem: тот же ID, score без перенормировки, те же причины и корректные ссылки.
2. Проверить неизвестные ID, пустую ленту и rejected input: никаких автоматических первых компаний/событий или seed-результатов.
3. Проверить withdrawn и новую версию: лента обновляется, старая карточка не подменяет закреплённый источник новым.
4. Отобразить реальный limited fixture: виден режим и ограничения; нет придуманной позиции банка/процента финансового эффекта.
5. Задать вопрос, перезапустить процесс и продолжить по run_id; вопрос к чужой компании отклоняется.
6. Прогнать импорт и два запроса из чистого контейнера, чтобы обнаружить зависимости, пути и SQLite threading.

В рамках этой проверки выполнены реальные probes ранкера→адаптера и ML Insight→backend schema; чужая ветка загружалась через git show в изолированные Python-модули. API-сервер и Docker не запускались, backend-код и ML-контракты не менялись. Запросов к LLM и отправки сообщений Владу не было.
