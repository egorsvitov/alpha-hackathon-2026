# Основной путь: оригиналы новостей и тематические векторы компаний

Решение пользователя, 23 октября 2026: перейти с обязательного предварительного
EventBundle B6 v0.2 на поиск по исходным публикациям. Старый B6-путь остаётся
контролем; конверсия всех новостей в B6 не является условием нового поиска.
Приведённое ниже тематическое расширение — план, а не уже выполненная миграция.

## Что уже есть

- Старый retriever: multilingual-e5-small, revision614241f622f53c4eeff9890bdc4f31cfecc418b3,
  384 dimensions, CPU ONNX INT8, masked mean + L2, query:/passage: prefixes.
- Новый GPU путь: BAAI/bge-m3, revision5617a9f61b028005a4858fdac845db406aefb181,
  1024 dimensions, FP32, CLS + L2, без префикса.
- В эксперименте BGE закодировал представления20 компаний и128 компаний для
  производительности, в том же пространстве, что3012 коротких публикаций.
  Массовая миграция всей базы компаний ещё не выполнена.
- Старый и новый пути используют описания деятельности/признаков, а не только
  название компании. Есть base3 business/finance/trade_geo, условные механизмы
  и LLM-каталог546 ОКВЭД с двумя широкими поисковыми описаниями на деятельность.

Переход E5→BGE требует заново вычислить векторы. Обучение весов encoder для этого
не требуется. Одной размерности недостаточно для совместимости: фиксируются
model/revision, tokenizer, pooling, prefixes и нормализация. Существующие E5/BGE
представления не смешивать в одном cosine-поиске.

## Следующее расширение

Подготовить версионированный каталог отдельных тематических запросов по видам
деятельности. LLM формирует его один раз на отрасль/роль, а не на каждую компанию
при каждом поиске. Переиспользовать существующий каталог, но пересмотреть охват
и разделить смешанные описания на самостоятельные темы.

Каждый элемент содержит topic_id, тип деятельности/роль, поисковый текст,
механизм релевантности, условия применимости, статус hypothesis, версию prompt/
модели и сведения о проверке. Нужны отдельные BGE-векторы тем; их не усреднять
в один вектор компании. Общие тексты кодировать один раз с сохранением mappings.

Примеры для строительства: проектное/долгосрочное финансирование; оборотный
капитал и задержки оплаты; цены строительных материалов; разрешения/эскроу;
кадры; гарантии исполнения контрактов. Набор зависит от роли: девелопер,
генподрядчик и электромонтажная организация имеют разную применимость тем.

Отраслевой запрос о финансировании допустим без положительной банковской метки
loan, но остаётся гипотезой. Отсутствие продукта в записи нашего банка не
доказывает отсутствие кредита в других банках и не доказывает отсутствие
потребности в финансировании. Подтверждённые признаки компании и отраслевые
предположения сохраняются отдельно.

Поиск: top-K отдельно на тему и канал → ограниченный union → max RRF внутри
семейства с фиксированными весами → reranker по конкретной теме → ограниченный
контекст с reading groups → общая карточка → персональная аналитика.
Количество запросов не должно само по себе добавлять новости суммарные голоса.
Для каждой находки сохраняются тема, основания, статус и ранги.

## Проверка перед масштабированием

На одном корпусе/профилях/бюджете сравнить base3, два широких LLM-описания и
отдельные тематические запросы. Разметить полезные пропуски и ложные совпадения
по каждой теме. Проверять роли участников: банк и его корпоративный заёмщик,
девелопер и подрядчик. Учитывать уже найденный шум навигационных страниц.
Размер набора тем и веса выбрать на dev; test сохранить замороженным.

После проверки построить BGE mapping/cache для всей базы компаний и сделать
raw-путь основным runtime. Не переобучать модель и не выполнять массовые
LLM-вызовы без отдельной необходимости; новый API-бюджет этим планом не назначен.
