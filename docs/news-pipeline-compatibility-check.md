## Главный блокер: версия и смысл утверждений

[B6 producer](../llm/events/BUNDLE.md) возвращает `schema_version="0.2"`. Наш [валидатор](../ranking/b6.py) использует [схему v0.1](contracts/event-bundle.schema.json).

На bundle, действительно полученном через `EventBundleService.publish()/get_event()`, воспроизведены ошибки:

```text
/schema_version                     const: ожидается 0.1
/claims/0                           additionalProperties: scenario
/claims/0/measurements/0             additionalProperties: value_role
```

Импорт выбросил `BundleValidationError`; в новой потребительской базе осталось 0 событий. Это корректный защитный отказ, но персонализировать такой поток пока нельзя.

Дополнительная проверка примеров: 4/4 примера v0.1 принимаются; 7/7 примеров v0.2 отвергаются.

Затронуты не только загрузчик и ранкер. [Контекст аналитика](../llm/agent/context.py) повторно вызывает тот же валидатор, поэтому обход проверки при импорте не решит интеграцию.

Новые поля нужно сохранить и учитывать:

- `scenario`: базовый, альтернативный либо неуточнённый сценарий с текстом условия; поле может быть `null`.
- `value_role`: `reported`, `before`, `after`, `comparison` — роль конкретного измерения.
- Факт/прогноз уже различаются через `modality`; наличие v0.2 не заменяет эту проверку.

Простая замена строки версии или удаление новых полей теряет смысл. Отдельно надо проверить, что значение «до» не интерпретируется как текущее, а альтернативный сценарий — как безусловное событие. Сейчас ранкер использует прежде всего типы/объекты/метрики для тематической экспозиции и не реализует полноценную интерпретацию этих новых полей.

Поля `Relevance.schema_version=0.1` и `Insight.schema_version=0.2` относятся к другим контрактам: автоматически менять их вслед за EventBundle не требуется.

## Что обнаружено в новом адаптере

На синтетической записи без сети проверены преобразование, строгая валидация `ArticleInput` и настоящий `EventStore.import_batch`: статус `completed`, disposition `new`.

Ограничения реализации:

1. `Article` допускает произвольные строки даты/URL, а B2 — только корректные timestamp с часовым поясом и абсолютные URI. Примеры `20.10.2026` и `relative/path` проходят модель сборщика, но отвергаются B2. Адаптер это не исправляет; нужен явный отчёт о rejected-записях. Обычный сборщик уже нормализует дату, поэтому это проверка границы, а не утверждение, что все его статьи ошибочны.
2. Прямой вызов `to_article_input_dict()` на пустом тексте выдаёт невалидный для B2 словарь. `load_news_corpus()` такие статьи пропускает. Наличие статьи только с заголовком ещё не означает, что она попадёт в NLP.
3. Загрузчик молча пропускает невалидные JSON/Article и пустой текст; отсутствующий файл даёт пустой список. В пробе из трёх строк — корректная, пустая, испорченная — возвращена одна без диагностики остальных. Для демо терпимо, для контроля покрытия нужны счётчики и причины пропусков.
4. `content_kind="original"`, `is_full_original_text=bool(text)`, `is_synthetic=False` назначаются адаптером. Сам адаптер полноту/происхождение не проверяет. Его следует применять к оговорённому реальному корпусу сборщика; синтетические fixtures должны получать собственную достоверную маркировку. Наш проверочный пример был искусственным и использовался только во временной базе, не как реальная новость.
5. Добавлен callable-адаптер и ручной сценарий, но его наличие само по себе не запускает B2–B6 автоматически из сборщика. Нужен управляющий вызов обработки/публикации.

`news_adapter_test.py` расположен вне `llm/events/tests`, поэтому стандартный discovery из таблицы ниже его не запускает. Вместо него выполнена независимая проверка адаптера на временном искусственном корпусе; сеть и реальный сбор новостей не запускались.

## Окружения

В изолированном окружении из `llm/events/requirements.lock` producer и наш consumer импортируются совместно — проверки границы выполнены именно так.

Но `uv run --frozen` из корневого `pyproject.toml` содержит зависимости только нашего ML-блока. Попытка импортировать новый адаптер там заканчивается `No module named 'pydantic'`. Дополнительно два lock-файла фиксируют разные версии jsonschema: корневой — 4.25.1, NLP — 4.26.0.

Это не причина заводить микросервис. Для совместного процесса нужно согласовать единое окружение/lock; текущая успешная проверка в окружении NLP не является таким согласованием.

## Что сделать для состыковки

1. На нашей стороне добавить явную поддержку EventBundle v0.2 с сохранением v0.1 и версии исходного payload. Сохранить точные claims, provenance и hashes, не делать скрытый downgrade.
2. Проверить семантический валидатор, скоринг, контекст и QA на scenario/value_role: «до/после», сравнение, прогнозы и альтернативные сценарии. Ошибку не маскировать fallback в backend.
3. Решить миграцию сохранённых событий: ключ потребителя сейчас `(event_id, event_version)`. Новый payload с тем же ID/номером даст коллизию; номера разных схем нельзя без проверки считать одной последовательностью. Для первой проверки использовать отдельную новую базу, не удаляя прежнюю.
4. Согласовать общее окружение зависимостей для выбранного способа in-process интеграции.
5. Прогнать publisher→export→наш импорт→ранкер→аналитик на новой базе, включая withdrawn, обновления, конфликты и повторы публикации. Дальше подключать API и UI.

В этой работе изменена только история слияния/полученные файлы и добавлен этот отчёт. Миграция контрактов и исправление кода адаптера не выполнялись.
