# B2: архив батчей, редакции статей и задания

Реализованы библиотека `EventStore` и CLI на стандартном `sqlite3`, без новых зависимостей. Исполнителя заданий, LLM-вызовов, автоматических повторов, бюджетного шлюза и сопоставления событий в B2 нет. Эти компоненты подключаются через API ниже.

## Быстрый запуск

Использовать окружение и зависимости из [README](README.md). Команды выполняются из корня проекта:

```bash
.venv/bin/python -m llm.events.storage_cli import-batch ../alpha-context/articles.json
.venv/bin/python -m llm.events.storage_cli list-batches
.venv/bin/python -m llm.events.storage_cli list-batches --status importing
.venv/bin/python -m llm.events.storage_cli show-batch <batch_id>
.venv/bin/python -m llm.events.storage_cli resume-batch <batch_id>
.venv/bin/python -m llm.events.storage_cli list-versions <article_id>
.venv/bin/python -m llm.events.storage_cli get-article <source_id>
.venv/bin/python -m llm.events.storage_cli current-article <article_id>
```

По умолчанию база находится в `data/processed/events/state.sqlite3` относительно корня репозитория. Путь явно меняется глобальным параметром **перед подкомандой**:

```bash
.venv/bin/python -m llm.events.storage_cli --db /tmp/events-demo.sqlite3 import-batch ../alpha-context/articles.json
```

Каталог `data/processed/events/` исключён из Git целиком, включая SQLite, WAL/SHM и сырые входные данные. База backend не изменяется. База создаётся при открытии `EventStore`; схема существующей базы проверяется и не пересоздаётся автоматически.

Все команды выводят JSON. Импорт возвращает код 0 при `completed`, код 1 при `partial` или `rejected`. Ошибки операций возвращают `{status: "error", issues: [{code, path, message}]}` и код 1; неверные параметры CLI — код 2. `show-batch` показывает сохранённое состояние без обработки элементов. При прерывании процесса квитанцию можно найти через `list-batches --status importing`, даже если первоначальный вызов не успел вернуть ID.

## Статьи и неизменяемые версии

`article_id` должен быть стабилен и глобально уникален в проекте. Сборщик может включать в него пространство имён, например `tass:12345`. B2 не меняет ID, URL, заголовок, тело и другие поля `ArticleInput`. URL не определяет идентичность публикации.

Исходный файл сохраняется как точные байты BLOB вместе с SHA-256 и временем получения. Версия статьи хранит канонический валидированный `ArticleInput`, включая значения по умолчанию. Это меняет представление JSON, но не строковые значения; позиции цитат в `text` и `title` сохраняются. Отдельного файлового хранилища, способного рассинхронизироваться с SQLite, нет.

Версия — следующее положительное целое внутри ID. `source_id` — строка UUIDv5 с `uuid.NAMESPACE_URL`, имя — канонический JSON `['alpha-events', article_id, article_version]` (`ensure_ascii=False`, `sort_keys=True`, `separators=(',',':')`). Для потребителя ID непрозрачен. Содержимое определяется существующим B1 `article_sha256` всего `ArticleInput`.

| Вход | Действие |
|---|---|
| Новый ID | Версия 1, исход `new` |
| Хэш совпадает с текущей редакцией | Исход `unchanged`, без новой версии |
| Хэш уже был в истории, но не текущий | Исход `historical`, текущая редакция не меняется |
| Ранее неизвестный хэш | Следующая версия, исход `updated` |
| Явное восстановление | Новая версия с копией старого содержимого и основанием восстановления |

Заголовок, дата, URL и происхождение текста — часть сравнения. Порядок JSON-ключей, пробелы оформления и явное значение по умолчанию не создают редакцию. Неизвестная ранее редакция с более ранней датой публикации всё равно считается новой полученной редакцией: дата публикации не устанавливает порядок исправлений. Для более точной политики сборщику потребуется отдельная достоверная версия источника.

Восстановление выполняется явно:

```bash
.venv/bin/python -m llm.events.storage_cli restore-version <article_id> 1 --reason "Источник подтвердил исходный текст"
```

Возвращаются новый `ArticleRecord`, прежний текущий `source_id`, ID восстановленной версии и причина. Причина обязательна. Восстановление непосредственно текущей версии отклоняется как `already_current`; восстановление исторической версии всегда создаёт новую, даже если такое содержимое встречалось несколько раз. Старые записи сохраняются. История доступна через `list_versions`, точный снимок — через `get_article(source_id)`.

## Квитанции и возобновление импорта

`import_batch` принимает путь либо `bytes`. Каждый вызов создаёт новый `batch_id`; повтор файла остаётся отдельным фактом получения, но не создаёт лишних редакций. При невозможности прочитать файл возвращается `input_io_error`: сохранить не полученные байты невозможно.

- Принимается JSON-массив UTF-8, включая BOM файла. JSONL пока не поддерживается.
- Повреждённый JSON, дублирующиеся JSON-ключи, нештатные константы `NaN`/`Infinity` или другой корневой тип отклоняют батч целиком; байты и причина сохраняются.
- Ошибки отдельных `ArticleInput`, включая некорректный Unicode, не блокируют остальные элементы.
- Перед записью редакций проверяются повторяющиеся ID: разные варианты одного ID отклоняются все как `ambiguous_article_versions`. Полные совпадения допустимы; опущенные значения по умолчанию сравниваются после валидации.
- Сохранение редакции, смена текущего указателя, отзыв старых заданий и результат элемента коммитятся одной транзакцией.
- Прерывание оставляет батч в `importing`. `resume_batch` использует архивные байты, пропускает уже сохранённые результаты и завершает остальные. Изменение исходного файла после прерывания не влияет на возобновление.

Квитанция содержит `batch_id`, имя входа, время получения/завершения, SHA-256 байтов, `total_count`, `import_status`, `counts`, `items`, `issues`, `current_changes`.

`import_status`: `importing`, `completed`, `partial`, `rejected`. Счётчики: `new`, `updated`, `unchanged`, `historical`, `invalid`, а при незавершённом импорте также `pending`. Неподдающийся разбору файл имеет `total_count=null` и ошибку уровня батча; пустой массив корректен и завершается с нулевыми счётчиками.

Каждый элемент содержит `index`, `article_id`, `source_id`, `previous_source_id`, `disposition`, `issues`. У ещё не обработанного элемента поля ID могут быть неизвестны. `current_changes` содержит сохранённые переходы `new/updated` с прежним и новым `source_id`; это журнал изменений при импорте, а не гарантия, что редакция остаётся текущей после последующих батчей.

## API для B3

```python
from llm.events import EventStore, ProcessingSpec

store = EventStore()  # либо EventStore('/data/events.sqlite3')
receipt = store.import_batch('incoming.json')
current = store.get_current_article('tass:12345')

# Только демонстрационная конфигурация хранения, провайдер не подключён.
spec = ProcessingSpec(
    processor_name='demo:no-execution',
    processor_version='1',
    configuration={'model_id': None, 'prompt_version': 'test', 'output_schema_version': 'test'},
)
job = store.enqueue(current.source_id, spec)
cached = store.get_cached_result(current.source_id, spec)
claimed = store.claim_next(spec, worker_id='example-worker')
if claimed:
    token = claimed.active_attempt.token
    store.save_artifact(token, 'diagnostic', {'note': 'Storage API example only'})
    store.complete_attempt(token, {'claims': []}, schema_version='test')
```

Это демонстрация сохранения состояния, а не рабочий extractor или валидированный результат B3. `get_article` и `get_current_article` возвращают ровно `ArticleRecord` B1 и подходят для `validate_grounding`; `list_versions` возвращает дополнительные метаданные, вложив `ArticleRecord` в поле `record`.

### Конфигурация и кэш

`ProcessingSpec` содержит `processor_name`, `processor_version`, `configuration` — JSON-объект. Реальный B3 должен включить в него влияющие на результат ID/версию модели, версию/хэш промпта и выходной схемы, параметры генерации и, если применимо, нормализатора. Ключи доступа остаются в конфигурации подключения, а не в `ProcessingSpec`.

Хэш — SHA-256 канонического JSON всей спецификации. Ключ задания и кэша — `source_id + spec_hash`. Повторное `enqueue` возвращает то же задание во всех его состояниях; само по себе это не запрос повторного запуска. Изменение реальных настроек требует другой спецификации. Кэш между статьями или редакциями не разделяется.

Импорт не создаёт задания. `enqueue` разрешает только текущую редакцию. `get_cached_result` возвращает `ArtifactRecord` либо `None`, а не один payload. Только `succeeded` даёт попадание в кэш. Исторический успех остаётся доступным по явно указанному старому `source_id` для аудита; для текущего анализа сначала получать `get_current_article`.

Постановка через CLI требует JSON-файл спецификации:

```bash
.venv/bin/python -m llm.events.storage_cli enqueue --source-id <source_id> --spec processing-spec.json
.venv/bin/python -m llm.events.storage_cli enqueue --batch <batch_id> --spec processing-spec.json
.venv/bin/python -m llm.events.storage_cli show-job <job_id>
```

В варианте `--batch` исторические, ошибочные, ещё не принятые и уже устаревшие редакции пропускаются; ID пропущенных элементов возвращаются в `skipped_indices`. Точные повторения текущего `source_id` ставятся один раз. Восстановленная редакция требует отдельной постановки по её новому `source_id`.

### Состояния, аренда и попытки

| Операция | Допустимый переход |
|---|---|
| `enqueue(source_id, spec)` | Новое задание `pending` или существующее без изменения |
| `claim_next(spec, worker_id)` | `pending → running`, новая попытка и токен |
| `complete_attempt(token, payload)` | `running → succeeded`, итоговый артефакт и состояние одной транзакцией |
| `fail_attempt(token, issues)` | `running → failed`, структурированные ошибки попытки |
| `defer_job(job_id, reason)` | `pending → deferred`, без попытки |
| `defer_job(job_id, reason, token=...)` | `running → deferred`, действующая попытка закрывается |
| `retry_job(job_id)` | Явный `failed/deferred → pending` для текущей редакции |
| `requeue_expired()` | Истёкшая попытка `interrupted`, задание `pending` |
| Новая редакция/восстановление | Незавершённые старые задания `superseded`, их активные попытки отзываются |

`claim_next` выбирает только текущие статьи и точную спецификацию. Захват выполняется атомарно; два конкурирующих соединения не получают одну попытку. Аренда по умолчанию 900 секунд, настраивается `lease_seconds` положительным целым. `renew_lease` продлевает её от текущего времени и не сокращает прежний срок. Ровно в момент истечения токен уже недействителен.

Ни автоматического heartbeat, ни таймера возврата, ни цикла исполнителя нет. B3 вызывает `renew_lease` во время долгой работы и `requeue_expired` при восстановлении. `claim_next` сам не переоткрывает просроченную попытку. После перезапуска приложения незавершённые попытки можно вернуть явной командой:

```bash
.venv/bin/python -m llm.events.storage_cli requeue-expired
.venv/bin/python -m llm.events.storage_cli retry-job <job_id>
.venv/bin/python -m llm.events.storage_cli list-attempts <job_id>
```

Неизвестный токен даёт `attempt_not_found`, истёкший/завершённый/отозванный — `stale_attempt`. Старая попытка не может обновить состояние новой. Время аренды хранится как UTC epoch; часы инъецируются в тестах, ожиданий через `sleep` нет.

### Артефакты и ошибки

`save_artifact(token, kind, payload, schema_version=None)` сохраняет неизменяемый промежуточный артефакт только действующей попытки. Payload — конечное JSON-значение: объект, массив, строка и т. д.; не Python-объект, `NaN` или бесконечность. Строка может содержать сырой невалидный JSON-ответ модели. B2 не считает такой ответ корректным извлечением.

`complete_attempt` атомарно сохраняет итоговый артефакт и успех задания. `payload=None` отклоняется как отсутствие результата; для нуля найденных событий использовать явный массив/объект. Смысловую валидацию результата выполняет B3/B4 перед завершением.

`get_artifact`, `list_artifacts(attempt_id)`, `get_job` и `list_attempts(job_id)` позволяют восстановить контекст. При неудаче можно сначала сохранить сырой ответ, затем передать в `fail_attempt` непустой список `Issue`. Ошибка и промежуточные данные не становятся успешным кэшем.

Новая редакция отзывает `pending/running/deferred` задания старых редакций. Исторические `succeeded/failed` и их артефакты сохраняются. Задания со статусом `superseded` повторно не открываются; для нового текущего `source_id` создаётся своё задание.

## SQLite и ограничения эксплуатации

База хранит семь таблиц: архив редакций, текущие указатели, батчи, элементы батчей, задания, попытки и артефакты. Архив, результаты элементов и артефакты защищены от UPDATE/DELETE триггерами. Данные батча нельзя переписать при смене статуса. Внешние ключи и уникальные ограничения включены.

Используются короткие явные транзакции `BEGIN IMMEDIATE` для записи и `BEGIN` для согласованного чтения. Внешняя работа выполняется между вызовами API, без открытой транзакции. Соединения создаются на операцию и закрываются после неё; отдельный `close()` для `EventStore` не требуется.

Настройки: `foreign_keys=ON`, WAL, `synchronous=FULL`, `busy_timeout=5000`. Хранилище рассчитано на локальный диск одного компьютера или локальный Docker-том, не сетевую ФС. Для тестов можно передать `busy_timeout_ms=0`; производственное значение по умолчанию — 5 секунд. Блокировка возвращается как `storage_busy`; при незавершённом импорте найти квитанцию и возобновить её.

Принадлежность определяется `application_id=0x414C5048`, схема — `user_version=1`. Пустой новый файл инициализируется. Чужая, неполная или неизвестная версия отклоняется как `unsupported_storage_schema`, без очистки и автоматической миграции. Для UPSERT требуется SQLite 3.24 или новее; проверка выполнена на Python 3.13 со SQLite 3.46.1.

Сбой после ответа провайдера, но до фиксации артефакта может потребовать повторного платного вызова. B2 обеспечивает целостность сохранённого состояния; учёт незавершённых расходов и политика повторов принадлежат B3/бюджетному шлюзу.

## Проверка

```bash
.venv/bin/python -m unittest discover -s llm/events/tests -v
.venv/bin/python -m llm.events.schemas --check
.venv/bin/python -m llm.events.check_contracts
```

Тесты используют временные SQLite-файлы и управляемые часы. Проверяются повторные загрузки, исправления и восстановление, неоднозначные ID, продолжение из архивных байтов, откат незавершённых транзакций, сохранность прежних цитат, кэш, артефакты, состояния, конкурентный захват, аренды и отозванные токены. Набор B1 также запускается. В тестах нет сети, LLM и обязательных внешних данных.
