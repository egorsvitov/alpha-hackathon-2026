# B5: каталог событий и решения по парам

B5 принимает **явно выбранные** итоговые артефакты B4 `normalized_claims`, группирует утверждения о событиях и сохраняет версии каталога. Исходные утверждения и доказательства не переписываются и не удаляются. Основной путь работает офлайн. Числовой конфликт не мешает принадлежности одному установленному событию.

Выход — внутренний `CanonicalEventRecord b5.1`. Контракт B6 v0.2 не меняется: создание `EventBundle`, признаки ранжирования и публикация реализованы отдельным [сервисом B6](publication.md). B5 не оценивает влияние на компанию, истинность публикации или полноту извлечения.

## Запуск

Используются существующие зависимости из `requirements.lock`, Python 3.13+. Из корня проекта:

```bash
.venv/bin/python -m llm.events catalog schema --check
.venv/bin/python -m llm.events catalog check
.venv/bin/python -m unittest discover -s llm/events/tests -v
```

Синтетический набор содержит 33 самостоятельных случая с вымышленными статьями, утверждениями, ожидаемыми парами и группами. Ожидания заданы вручную в `fixtures/make_catalog.py`, без вызова сопоставителя. Проверка дополнительно проверяет структуру и происхождение цитат через B1. Никаких внешних файлов, сети и ключа не требуется.

## Миграция SQLite

Новые базы создаются со схемой **4**. B6 добавляет неизменяемые публикации и версии bundle. Открытие старой базы через `EventStore` требует явной миграции:

```bash
.venv/bin/python -m llm.events catalog --db data/processed/events/state.sqlite3 migrate
```

Для v3 выполняется `3 → 4`, для v2 — `2 → 3 → 4`, для v1 — `1 → 2 → 3 → 4`. Перед каждым шагом создаётся отдельная резервная копия через SQLite backup с правами 0600. `--backup <path>` задаёт путь первой копии; существующий файл не перезаписывается. `--to 2` выполняет только первый шаг для базы v1; `--to 3` останавливается до добавления B6. Такие базы требуют оставшихся шагов перед открытием текущим EventStore. Старый `migrate_v1_to_v2` всегда заканчивается версией 2 независимо от актуальной версии схемы.

Миграция сохраняет статьи, source ID, задания, артефакты и журнал расхода. Каталог хранится в той же локальной NLP-базе, отдельно от backend. Новые таблицы: конфигурации каталогов, выбранные входы, запуски/снимки, события и версии, состав событий, ручные решения. Снимки и журнал решений защищены от UPDATE/DELETE. Обычное открытие не мигрирует и не пересоздаёт старую или неизвестную базу.

## Выбор входов и снимки

```bash
.venv/bin/python -m llm.events catalog --catalog news init
.venv/bin/python -m llm.events catalog --catalog news plan \
  --artifact-id <b4_artifact_1> --artifact-id <b4_artifact_2>
.venv/bin/python -m llm.events catalog --catalog news apply \
  --artifact-id <b4_artifact_1> --artifact-id <b4_artifact_2>
.venv/bin/python -m llm.events catalog --catalog news events
.venv/bin/python -m llm.events catalog --catalog news pairs --uncertain-only
```

`--db` и `--catalog` — глобальные аргументы, их ставят перед подкомандой. `init` обязателен. `plan` не записывает снимок; `apply` добавляет явно перечисленные статьи к выбранным входам и пересобирает весь каталог. Для одной статьи выбирается один результат B4. Другой результат той же редакции требует `--replace`; два разных результата одной статьи в одном вызове отклоняются. Исторический B4 не принимается как текущий.

Проверяются итоговый тип/владелец/успех задания, хэши и цепочка B3 → B4 → архивная редакция, затем повторно выходной контракт B4. Пригодные утверждения `partial` сохраняются с предупреждениями. Пустой корректный результат допустим. Разные результаты извлечения одной статьи не увеличивают число независимых источников.

Конфигурация `CatalogConfig` закрепляет правила `b5.1`, `top_k=20`, `max_claims=10000`, `max_comparisons=1000000`. Превышение лимита прерывает операцию до публикации. Хэш реализации и конфигурация поискового адаптера также закрепляются. Для изменения конфигурации или реализации:

```bash
.venv/bin/python -m llm.events catalog --catalog news rebuild --config <config.json>
```

Без `--config` пересборка сохраняет численные настройки и явно принимает текущую реализацию правил. Новый результат вычисляется вне транзакции, затем короткая `BEGIN IMMEDIATE` проверяет ревизию каталога, поколения входов и текущие редакции. Конкурентное изменение даёт `catalog_changed`, частичный снимок не публикуется. Точный повтор возвращает `cached`, не повышая версии.

## Идентичность и содержание

`describe_identity(ClaimContext)` возвращает известные признаки, недостающие признаки и основания. Исполняемая матрица всех 11 категорий находится в `matching.IDENTITY_MATRIX`. У статистики совокупность может задаваться явным объектом и географией; организация-автор оценки не подменяет совокупность наблюдения. Для курса требуется установленный вид `official_exchange_rate` или `market_exchange_rate`.

Доказательства признаков ссылаются на пути утверждения и evidence ID. При извлечении обозначения документа/выпуска `path` указывает на `/evidence/<index>/quote` контекста; дополнительно сохраняются source ID, поле и абсолютные Unicode-координаты совпадения. Поддержаны явные конструкции «постановление/закон/приказ/решение №…», «прогноз/обзор/выпуск №…» и «выпуск от YYYY-MM-DD». Свободные инструкции не исполняются. Неизвестное обозначение не придумывается.

Для прогноза нужны автор, предмет, горизонт и выпуск. Отсутствующий выпуск, приблизительно восстановленный год, дата публикации или одинаковое число не доказывают идентичность. `uncertain` сохраняет отдельные группы. Это намеренная причина низкой автоматической полноты на пересказах без обозначений выпусков.

Поиск — объединение структурных блоков, BM25 внутри категории и ручных пар. BM25 использует Unicode-токены без морфологии, `k1=1.2`, `b=0.75`. Top‑20 ограничивает только лексическую часть; структурные совпадения не обрезаются по top‑k. Различие чисел не исключает кандидата. Поиск заменяется объектом с методами `configuration()` и `search(contexts, config, manual_pairs)`; конфигурация адаптера должна описывать его фактическую реализацию.

`compare_claims` возвращает независимые `identity` и `content`. Дубликаты сравниваются по полной структурированной пропозиции, с Decimal-значениями и без технических ID, текстов пересказа и цитат. Неизвестные границы периодов не становятся доказательством эквивалентности. Дополнительное измерение — дополнительное содержание. Автоматический конфликт ограничен несовместимыми точными числами/непересекающимися точными диапазонами при совпадении аспекта, сценария, ролей и базы. Для приблизительности нет придуманного числового допуска.

Объединение требует совместимости со всеми участниками группы; транзитивная цепочка не заменяет проверку. Сценарии, роли before/after и разные базы не теряются. Конфликт сохраняется ссылками на поля, без общего «правильного числа». `updates` автоматически выводится только для установленного того же события и явного исправления публикации («исправление», «исправлен…», «вместо ошибоч…»). Иные пересмотры требуют ручного подтверждения. `related_stage` требует общего явного документа, органа, предмета и юрисдикции; порядок поддержан для proposed → approved → effective → repealed. Прогноз с решением автоматически не связывается.

## Ручные решения

`review` читает JSON `ReviewRequest`. ID пары располагают в лексикографическом порядке:

```json
{
  "left_id": "<smaller_claim_id>",
  "right_id": "<larger_claim_id>",
  "identity": "same_event",
  "reason": "Совпадение выпуска подтверждено по указанным материалам"
}
```

```bash
.venv/bin/python -m llm.events catalog --catalog news review --request <review.json>
.venv/bin/python -m llm.events catalog --catalog news reviews
.venv/bin/python -m llm.events catalog --catalog news revoke <review_id> --reason "Основание пересмотрено"
```

Разрешены `same_event/different_event/uncertain`. Дополнительно `content` может задать `duplicate_claim/complements/conflicts_with/updates`; по умолчанию содержание сравнивается правилами при установленной идентичности. Для `updates` обязательны `from_id` нового и `to_id` заменённого утверждения. Новое должно быть текущим; цель может быть архивной из ранее опубликованного снимка этого каталога. Архивная цель не возвращается как текущий факт.

Основание обязательно. Ручная связь не исправляет исходные данные и не обходит явные несовместимости типа, автора прогноза, периода или стадии. Числовые конфликты и дубликаты проходят структурные ограничения. При несовместимости группы команда перечисляет мешающие пары без применения решения. Отмена — новая запись журнала; прежняя запись остаётся. Если ранее уже существовало другое решение этой пары, отмена нового восстанавливает действие предыдущего.

## Актуальность, ID и история

Триггер изменения текущей редакции B2 в транзакции импорта помечает зависимые каталоги как устаревшие. Текущие чтения, включая список событий и changes, возвращают `catalog_stale`, пока не выполнен `rebuild` или `apply`. Чтение истории всегда требует явной ревизии или версии события.

Пересборка исключает старые свидетельства, даже если B4 новой редакции ещё не готов. Выбранная статья остаётся в зависимостях, а пропуск её нового B4 отражается в ограничениях. Исчезновение утверждения не означает опровержение. Полученный позднее B4 новой редакции нужно явно применить.

Продолжающаяся установленная идентичность сохраняет event ID. Версия меняется при изменении содержимого, решений или ограничений, но не на точном повторе. При объединении сохраняется самый ранний ID, другие становятся `withdrawn`. При разделении ID сохраняется у группы с якорем; если его нет — с минимальным оставшимся прежним claim ID. Исторические цитаты остаются воспроизводимы. Пустой текущий event — `withdrawn`, с очищенными текущими свидетельствами и явной историей замещения; скрытых перенаправлений нет.

```bash
.venv/bin/python -m llm.events catalog --catalog news event <event_id>
.venv/bin/python -m llm.events catalog --catalog news event <event_id> --version 1
.venv/bin/python -m llm.events catalog --catalog news events --revision 1 --include-withdrawn
.venv/bin/python -m llm.events catalog --catalog news changes --since 1
```

## Явная LLM-рекомендация

```bash
.venv/bin/python -m llm.events catalog --catalog news check-pair \
  --left <claim_id> --right <claim_id> --profile <profile.json> --limits <limits.json>
.venv/bin/python -m llm.events catalog --catalog news show-recommendation <artifact_id>
```

Для офлайн-проверки добавить `--offline-responses <responses.json>` в формате B3. LLM получает только выбранную пару, доказательства и диагностику, возвращает `PairRecommendation`. ID доказательств и пути проверяются. Результат `pair_recommendation` — только рекомендация; `succeeded` означает структурную корректность, а не установленную идентичность. Каталог и ручные решения не меняются.

Используются бюджет, SDK-адаптер, heartbeat и отсутствие автоматических повторов B3. Один запрос на попытку. Без подтверждённых тарифов/лимитов/квоты и явного live-enabled сеть закрыта. Кэш включает обе редакции, оба артефакта/утверждения, правила, промпт, схему и профиль. Потеря аренды якорного задания не создаёт успешный результат; поздний расход сохраняется. Изменение второго источника делает рекомендацию неприменимой. `show-recommendation` каждый раз вычисляет актуальность; прошлому флагу доверять нельзя. Для применения требуется отдельный `review` с основанием.

## API для B6 и оценка

```python
from llm.events import EventStore, CatalogService, CatalogConfig

catalog = CatalogService(EventStore(), catalog_id="news")
catalog.create_catalog(CatalogConfig())
preview = catalog.plan_catalog_update([b4_artifact_id])
receipt = catalog.apply_artifacts([b4_artifact_id])
events = catalog.list_events()
event = catalog.get_event(events[0].event_id)
changes = catalog.changes_since(0)
```

`CanonicalEventRecord` содержит claims/sources/evidence/conflicts/relations/limitations, версии, anchor, ссылки на решения и `semantic_support=not_assessed`. `validate_catalog_record` проверяет его напрямую общими проверками B1, без фиктивного EventBundle. JSON Schema генерируется из моделей; `schema --check` не пишет файлы. B6 должен обрабатывать `catalog_stale`, `withdrawn` и `event_version`, не выбирать спорное число и не считать число публикаций независимой проверкой.

```bash
.venv/bin/python -m llm.events catalog evaluate --gold llm/events/fixtures/synthetic.json
.venv/bin/python -m llm.events catalog evaluate \
  --gold data/context/events/development-gold.json --articles ../alpha-context/articles.json
```

Оценка использует заданные нормализованные утверждения B1. Неразмеченные пары не считаются отрицательными. Отчёт содержит полноту кандидатов, precision/recall идентичности/дублей/конфликтов на размеченных парах, долю uncertain среди проверенных кандидатов, ложные слияния среди пар с известной принадлежностью и решения по размеченным парам. Это не качество B3, не независимый benchmark и не проверка истинности.

На текущих 15 статьях: 73 заданных утверждения, 10 размеченных связей, 5 положительных пар идентичности. Поиск находит все 5; правила объединяют 1 из 5, ложных слияний среди известных пар нет. Остальные положительные пары оставлены раздельно из-за отсутствующих обозначений выпуска и неполной идентичности. Дубль из разметки автоматически не подтверждён. Локальный отчёт хранится под игнорируемым `data/context/events/b5/`; результаты не заявляют высокую полноту автоматического сопоставления.

Основания подхода: локальные deep-research материалы и [Choubey & Huang, EMNLP 2017](https://aclanthology.org/D17-1226/) — раздельные within/cross-document связи, аргументы и контекст событий. Использованы принципы, без копирования кода, весов и численных порогов обученной модели.

## Публикация B6

После `apply`, `rebuild`, `review` или `revoke` выполнить отдельный B6 `publish`.
`CatalogService.get_event()` по-прежнему возвращает внутреннюю запись B5.
Для внешнего EventBundle использовать `EventBundleService.get_event()`:
его `event_version` — самостоятельная версия B6, а связь с ревизией/версией B5
хранится внутри SQLite. Изменение только решений аудита B5 может не менять B6.

Команды, ошибки stale, пакетный экспорт с withdrawn и проверка совместимости
описаны в [BUNDLE.md](publication.md). Подключение ranking v0.1 требует отдельной миграции.
