# B3: извлечение и проверка

Основной исследуемый вариант — `ExtractionService` из `extraction/service.py`.
Он делает discovery на полной статье, строит фиксированный план и выполняет небольшие
пакеты. Кандидаты компилируются в общий b3.1, который читает B4. Имена форматов
`two-stage.v2`/`span-ids.v1` сохранены, чтобы не менять историю.

## Семь предметных шаблонов

`observation`, `indicator_forecast`, `forecast_revision`, `decision_forecast`,
`scenario_forecast`, `decision`, `action`. Их определения и синтетические примеры —
`extraction/prompts.py`, строгие модели — `extraction/staged_models.py`.
Discovery предлагает один или два варианта; второй этап подтверждает тип или отказывается.
Пересмотр держит before/after вместе; разные сценарии и периоды разделяются.

Пакет содержит до трёх упоминаний, заголовок, нужные и соседние абзацы. Большой пакет
разделяется **до** API; слишком большой одиночный элемент получает deferred. Вызов один
на попытку. Length, ошибка JSON, некорректные ссылки не запускают повтор или repair.

## Основания по ID

Код заранее задаёт границы предложений/строк в неизменённой статье, например `P1.S1`.
Модель для каждого поля возвращает `{value, evidence:[...]}`, где основание имеет вид:

```json
{"fragment_id":"P1","start_id":"P1.S1","end_id":"P1.S2"}
```

Для одного предложения start_id=end_id. Диапазон непрерывен и не пересекает абзац.
Текст цитаты и координаты берёт код. Табличные строки, их заголовки и единицы доступны
как отдельные единицы. Сегментация консервативна и не является лингвистической разметкой.
Числа и выражения времени модель всё ещё должна передать исходными, без нормализации.

Старые основания `{fragment_id,quote}` читаются для совместимости с результатами v2.
Если выбранное предложение повторяется, компилятор расширяет **выбранный срез** до
уникальной цитаты для B4; исходные координаты остаются в bindings. Первое совпадение
произвольно не выбирается. Новые wire-схемы требуют ссылки по ID.

Ошибка отдельного упоминания/записи сохраняется с причиной, пригодные записи продолжают
обработку. Аудит учитывает processed/excluded/unresolved/rejected/deferred/missing.
Неполнота передаётся B4 структурированным предупреждением, затем учитывается B6.

## API сервиса

| Операция | Назначение |
|---|---|
| `discover(source_id)` | Полная статья → упоминания |
| `plan_extraction(discovery_id, persist=True)` | Сохранить план и хэши запросов |
| `run_extraction(plan_id, max_jobs=N)` | Выполнить/возобновить пакеты |
| `assemble_variant(plan_id, batch_ids, variant='A')` | Локально собрать b3.1 и аудит |
| `normalize_variant(assembly)` | Передать выбранный результат в B4 |
| `verify_extraction(normalized_A_id, max_jobs=N)` | Проверить все принятые A утверждения |
| `assemble_variant(..., variant='B', ...)` | Отобрать исходные кандидаты по проверке |
| `publish_variant(variant, normalized_ids, experiment_id=...)` | Отдельные B5/B6 для A и B |

Сборка не создаёт фиктивных сетевых вызовов. Кэш привязан к источнику, реализации,
профилю, плану и пакету. B дополнительно связан с конкретным A; значения не исправляет.

## Проверка B

Каждый пакет содержит до двух принятых B4 утверждений. Для всех применимых критичных
полей требуются supported и основания. contradicted/not_found/ambiguous, пропуск проверки
или неизвестная критичная роль исключают целый кандидат. A остаётся неизменным.
Отобранные исходные кандидаты повторно проходят B4 → отдельный B5 → B6.
`semantic_support=not_assessed` B4 не подменяется оценкой модели; вердикты лежат отдельно.
Известные чрезмерные отказы описаны в checkpoint; качество проверки ещё не подтверждено.

## Запуск и лимиты

```bash
python -m llm.events extract --help
python -m llm.events extract --db <db> --profile <profile.json> discover --source-id <id>
python -m llm.events extract --db <db> --profile <profile.json> plan \
  --discovery-artifact-id <id> --save
python -m llm.events extract --db <db> --profile <profile.json> run \
  --plan-artifact-id <id> --max-jobs 3
```

Для обычных реальных вызовов добавить `--limits <limits.json>` с подтверждёнными тарифами,
лимитами модели и квотой. В профиле — execution_mode=live, модель, endpoint, формат и
явные настройки thinking. Секрет читается только из LLM_API_KEY, в ProcessingSpec не входит.
SDK не делает скрытых повторов. Профиль не переключается автоматически.

Кредитный эксперимент — явные флаги `--experimental-credits --journal <quota.sqlite3>
--max-requests 60`. Это постоянный общий счётчик, а не новая квота каждого запуска.
Настройки профиля замораживаются. Не сбрасывать журнал при возобновлении.
Существующий журнал и остаток указаны в checkpoint. Обычные рублёвые ограничения
отдельного runner этим режимом не отключаются.

Команда `experiment --articles <json> --gold <json> --max-jobs N --experiment-id <id>
--output <dir>` выполняет A для всех трёх статей, затем B. Ручной эталон не передаётся модели.
Полные входы, запросы, ответы, usage и bundles сохраняются в локальном отчёте.
Максимум три статьи относится к контролируемому эксперименту, а не размеру хранилища.

Для простой отладки остаётся один запрос на статью с полным b3.1:
`python -m llm.events llm prepare/enqueue/run ...`. Его пример профиля —
`profiles/offline.json`, сценарные ответы — `profiles/offline-responses.json`.
`llm calls/show-call/budget/reconcile` показывает расход обычного runner.

Прежние compact/form/rows и two-stage.v1 не выполняются. Исторические артефакты доступны
как JSON через хранилище; возвращение старого процессора требует исходного checkpoint.
