# B4: проверка доказательств и нормализация

B4 принимает сохранённый результат B3 и конкретную архивную редакцию статьи. Основной путь работает правилами, без API. Результат `NormalizedArticleResult` версии `b4.1` содержит пригодные `SourceClaim` B1, точные цитаты с координатами, ошибки отклонённых кандидатов и трассу преобразований. Категория события хранится рядом с каждым утверждением для B5. События, связи и ранжирование B4 не создаёт.

`verification_status=structure_quotes_and_rules_checked`, `semantic_support=not_assessed`: проверено совпадение цитат с текстом и применение ограниченных правил, а не истинность публикации, полнота извлечения или независимое смысловое следование каждого поля. Наличие числа в цитате само по себе не доказывает правильную привязку к компании или периоду.

## Запуск и офлайн-проверка

Установите уже закреплённые зависимости по [README](README.md); новых NLP-пакетов нет. Команды из корня проекта:

```bash
.venv/bin/python -m unittest discover -s llm/events/tests -v
.venv/bin/python -m llm.events.schemas --check
.venv/bin/python -m llm.events.extraction_cli schema --check
.venv/bin/python -m llm.events.normalization_cli schema --check
.venv/bin/python -m llm.events.normalization_cli check
```

В Git находятся 22 самостоятельных [вымышленных примера](fixtures/normalization.b4.1.json). Их [авторский сценарий](fixtures/make_normalization.py) явно задаёт кандидатов и ожидаемые значения, не вызывает нормализатор для построения эталона. Набор покрывает числа, сценарии пересмотра, роли значений, периоды, неоднозначные цитаты, неполные основания, Unicode и частичный результат.

Локально подготовлены кандидаты для всех 15 предоставленных статей — по одному выбранному утверждению на статью. Это отдельные входы B4 со статусом `single_annotator_draft`, не полная разметка всех утверждений и не реальный вывод B3. Исходная разметка B1 и тексты не изменены:

```bash
.venv/bin/python -m llm.events.normalization_cli check \
  --inputs data/context/events/b4/development-inputs.json \
  --articles ../alpha-context/articles.json
```

Оба пути можно заменить. Команда проверяет соответствие полного набора ID/хэшей корпусу, затем ожидаемые результаты нормализации. Без внешних файлов по умолчанию проверяются только 22 синтетических случая. Результаты не являются extraction F1 или оценкой обобщения.

## Обработка сохранённого артефакта

Входом служит ID итогового артефакта B3 `extraction_candidates`, а не ID задания или статьи. Его можно получить из `storage_cli show-job <job_id>`. Допускается и итоговый `repaired_candidates` после явного repair. Нельзя передать произвольный промежуточный артефакт: проверяются тип, владелец/процессор, успешность задания, ID его итогового артефакта, source ID, хэши статьи и ProcessingSpec.

```bash
.venv/bin/python -m llm.events.normalization_cli normalize --artifact-id <b3_artifact_id>
.venv/bin/python -m llm.events.normalization_cli show <b4_artifact_id>
.venv/bin/python -m llm.events.normalization_cli batch \
  --artifact-id <artifact_1> --artifact-id <artifact_2> --max-jobs 2
```

Другой путь БД задаётся глобально **перед подкомандой**:

```bash
.venv/bin/python -m llm.events.normalization_cli --db /tmp/demo.sqlite3 normalize --artifact-id <id>
```

Нормализация имеет свой процессор `events.normalize_claims`. Его спецификация содержит входной артефакт, хэш его конфигурации извлечения, версию/хэш правил и словаря и хэш выходной схемы. Точный повтор возвращает `cached`. Изменение правил, словаря или входа создаёт другой ключ. Правила хэшируются вместе с общими проверками B1; ID привязаны к источнику, входному артефакту, хэшу конфигурации и локальным ID. Технические ID — UUIDv5, их строки непрозрачны для потребителей.

Обрабатываются только текущие редакции. Если редакция меняется во время работы, токен B2 не позволит опубликовать результат. Старые статьи можно нормализовать чистой функцией для аудита. Ошибка одного входа в batch возвращается отдельно, остальные обрабатываются до `max_jobs`. Повторные ID в списке пропускаются. Никакого автоматического retry нет.

## Контракт для B5

[JSON Schema b4.1](../../docs/contracts/normalized-article.b4.1.schema.json) генерируется из `NormalizedArticleResult` командой `normalization_cli schema`. Контракты B1/B6 и B3 не изменены.

Результат содержит:

- `source`: ровно метаданные источника B1 из архивного `ArticleRecord`;
- `input_artifact_id`, `article_sha256`, `configuration_sha256` и статус выполненных проверок;
- `accepted`: объекты `{candidate_id, event_type, claim}`, где `claim` — `SourceClaim` B1;
- `evidence`: доказательства B1, используемые принятыми утверждениями;
- `rejected`: исходные локальные ID и `issues=[{code,path,message}]`; оригинальные кандидаты остаются во входном артефакте;
- `excluded`: успешно проверенные исключённые фрагменты с полем, координатами, цитатой и причиной;
- `diagnostics`: предупреждения и ошибки с ID кандидата, если они относятся к нему;
- `transformations`: правило, путь входного поля, исходное/полученное значение, ID доказательств и ссылки на архивные метаданные;
- `limitations` и `quality`.

`complete` означает отсутствие ошибок и неразрешённых предупреждений B4. `partial` — есть пригодная часть вместе с ошибками или предупреждениями. `insufficient` — пригодных утверждений нет при непустом или ошибочном входе. Корректное извлечение без кандидатов допускает `complete`; это не доказательство отсутствия экономических фактов в статье.

`complete/partial` сохраняются как `succeeded` с итоговым артефактом `normalized_claims`. `insufficient` сохраняется как диагностический `normalization_result`, а задание становится `failed`. Не выбирайте просто «последний успешный артефакт статьи»: B5 должен знать нужный upstream и конфигурацию B4. Утверждения разных выпусков B3/B4 не считаются автоматически дубликатами.

```python
from llm.events import EventStore, NormalizationService, NormalizationConfig
from llm.events import normalize_extraction, validate_normalized_result

store = EventStore()
service = NormalizationService(store)
outcome = service.normalize_artifact(b3_artifact_id, NormalizationConfig())
if outcome['status'] in ('succeeded', 'cached'):
    result = store.get_artifact(outcome['artifact_id']).payload
    # Для B5: result['accepted'], result['source'], result['evidence'], ограничения.

# Без БД и сети, в том числе для исторической редакции:
# result = normalize_extraction(extraction_result, article_record, config)
# validate_normalized_result(result, article_record)
```

Общая `validate_claim_collection` в модуле `validation` проверяет утверждения/источники/доказательства без события. Её используют B1 и B4; для прохождения проверок фиктивный EventBundle не создаётся. Существующие `validate_bundle`/`validate_grounding` сохраняют прежнее поведение.

## Проверка цитат и полей

Ищется точное совпадение в объявленном `title` или `text`. Исходник не чистится: регистр, пробелы, NBSP, переносы и пунктуация значимы. Координаты — кодовые точки Unicode, `[start,end)`; JavaScript-индексы UTF-16 не подходят напрямую.

Нет совпадения — `quote_not_found`, несколько — `quote_ambiguous`. Автоматически выбирать первое совпадение или искать похожую строку нельзя. Для неоднозначности нужна более длинная точная цитата. Несколько предложений могут иметь отдельные доказательства. Ошибка доказательства отклоняет все использующие его кандидаты; ошибки неиспользованных доказательств тоже сохраняются в диагностике.

Каждое существенное поле итогового `SourceClaim` должно иметь основания по правилам B1. B4 не заполняет пропуски ссылкой на всю статью. `value_text → value` и `unit_text → unit` переводятся в путях. Производные границы периода наследуют только ссылки исходного выражения времени; использование публикации записывается отдельно в трассе. Строки `Period.text` и `Scenario.text` должны буквально присутствовать в связанных цитатах.

Проблемный кандидат отклоняется целиком: нельзя потерять числовое измерение и опубликовать остаток фразы. Уже пригодные кандидаты сохраняются независимо от соседних ошибок.

## Числа и единицы

Вычисления — `Decimal`, результат — десятичные строки без экспоненты или `{min,max}`. Поддерживаются запятая/точка, разделители тысяч пробелами/NBSP, знак `−`, диапазоны `X–Y`, `X-Y`, `от X до Y`, множители `тыс/млн/млрд/трлн` и явная общая единица в диапазоне/паре «с X до Y».

Проценты, процентные и базисные пункты различаются. Число 14% остаётся `14 percent`, не `0.14`. Множитель из value и unit применяется один раз; конфликт множителей отклоняет кандидат. Копейки переводятся в RUB, млн баррелей в сутки — в barrel_per_day, мощности Мбит/с/Гбит/с/Тбит/с — в bit_per_second. Поддержаны валюты и явно заданные пары, тонны, количество, место в рейтинге, часы и IP-адреса. Неизвестная единица — ошибка, а не выдуманная величина.

Исходные значения и основания единиц должны присутствовать в связанных доказательствах. Обнаруженные противоречия единиц рядом с числом, неподтверждённый масштаб, квалификатор или направление отклоняют кандидат. Парсер не доказывает правильность всех семантических связей в сложном предложении: консервативно отказывает при неоднозначности.

Для `level` снижение инвестпрограммы с 1,1 до 1,096 трлн не делает уровни отрицательными. Для изменений знак восстанавливается по ограниченным конструкциям роста/снижения и сравнений «больше/меньше/выше/ниже». Общий предикат падения применим к явно связанной паре. Улучшение прогноза падения не равно положительному росту. Нет единственного направления — `ambiguous_direction`; явный знак противоречит источнику — `direction_mismatch`. Роли before/after сами по себе направления не задают.

Не вычисляются отсутствующие прежние уровни. Диапазон не заменяется средним. Проценты и пункты не исправляются друг в друга по предположению. Явная приблизительность/порог требуют соответствующего квалификатора и буквального основания.

## Даты: ближайший период относительно публикации

Правила поддерживают ISO/русские даты, месяцы, кварталы, полугодия, годы, диапазоны месяцев, первые N месяцев и относительные сравнения. Исходный текст времени сохраняется. Приоритет: явный год → единственный год в связанном контексте → явные относительные выражения → ближайший календарный период.

Для месяца/даты без года рассматриваются предыдущий, текущий и следующий год относительно календарной даты публикации в её собственном часовом поясе. Выбирается минимальное расстояние в днях до интервала. Например, сентябрь при публикации в октябре 2026 — сентябрь 2026; при публикации в августе 2026 — тоже сентябрь 2026; январь при публикации в конце декабря 2026 может стать январём 2027.

Такой год — предположение `nearest_period_year`, а не сообщённый источником год. Оно обязательно присутствует в диагностике и трассе с `/article/published_at`, качество становится как минимум `partial`. Модальность не переключает поиск на прошлое/будущее: прогноз может получить ближайший прошедший период, оставаясь прогнозом. При одинаковом расстоянии или отсутствии даты публикации границы неизвестны. Дата запуска программы не используется.

«В этом/прошлом/следующем году», «до/на конец года» имеют отдельные правила. Для «год к году» и «к предыдущему месяцу» нужен установленный период наблюдения. Его предположения наследуются сравнением. Нераспознанная фраза сохраняется с неизвестными границами и предупреждением; явно невалидная дата отклоняет кандидат.

Годовой календарный интервал в накопленной статистике не означает, что наблюдения уже есть до 31 декабря; это помечается `calendar_year_not_complete`. Временные поля, модальность и стадия при датировке не подменяются.

## Организации и показатели

[Машинный словарь B4](normalization_vocabulary.json) версионируется отдельно от описательного словаря B1. Его условия — фиксированный набор проверок, а не исполнение свободного `context_rule`. Неизвестное условие — ошибка конфигурации.

Совпадение имени точное после ограниченной обработки регистра, внешних кавычек и пробелов. Исходное имя сохраняется; canonical name/ID и правило записываются в трассе. Нет fuzzy matching, морфологической догадки или внешнего NER. «ЦБ» требует явного российского контекста в доказательствах. Похожие юрлица, группа и головная компания не объединяются по подстроке; SYNTHETIC_U не используется как ID организации. Неизвестный/конфликтный alias оставляет `entity_id=null` и предупреждение.

Небольшой словарь показателей различает РСБУ/МСФО, M2/широкую денежную массу и не объединяет портфели. Стандарт используется только при явном контексте. Неизвестное имя показателя сохраняется с предупреждением, а не заменяется ближайшим известным.

## Явный однократный repair

Нормализация никогда не вызывает модель автоматически. Отдельная команда принимает оригинальный B3 artifact или call ID:

```bash
.venv/bin/python -m llm.events.normalization_cli repair \
  --artifact-id <original_b3_artifact_id> \
  --profile <provider.json> --limits <limits.json>
# Либо --call-id для завершённого stop-ответа B3 с ошибкой JSON/схемы.
```

Для офлайн-теста можно добавить `--offline-responses <scripted_responses.json>` и offline-профиль B3. Все денежные настройки проверяются общим механизмом B3. Реальные вызовы остаются закрыты до подтверждения тарифов, модели, возможностей и NLP-квоты. В реализации и обязательной приёмке B4 генерация не запускалась.

Допустимы исходные кандидаты с ошибками B4 либо единственный HTTP 200/stop ответ неуспешного B3 с непустым content, не прошедший структурный парсер. Timeout, HTTP-ошибки, refusal, tools и length не подходят. Одни предупреждения (неизвестный alias, неподдерживаемый вывод даты) не являются причиной платного repair.

Модель получает ту же статью, исходный ответ, диагностику и замороженную пригодную часть. Она не должна придумывать отсутствующие факты. При структурированном входе набор claim_id должен остаться тем же; уже принятые кандидаты и используемые ими доказательства проверяются на точное равенство JSON-значений. Модель может добавить новое более точное доказательство для отклонённой части, но не переписать общее доказательство пригодного утверждения. Нарушение ограничений отклоняет repair.

Запрос выполняет общий `OneShotRunner`, выделенный из B3 без изменения его старых API/ключей кэша: те же gates, heartbeat, один запрос, бюджет, запись позднего ответа и fencing. Результат repair сохраняется новым `repaired_candidates`; оригиналы не переписываются. Затем весь результат обязательно проходит B4, включая попадание в repair-кэш. Итог нормализации находится в `normalization`; успех генерации сам по себе не означает прохождение B4. CLI вернёт код 1, если последующая нормализация неуспешна.

Guard выполняется внутри той же BEGIN IMMEDIATE, что и резерв денег: ищет уже зарезервированный repair исходной попытки B3 в том же offline/live режиме. Новая конфигурация, конкурентный процесс и ручной retry второй вызов не разрешают. Слот считается использованным уже при резервировании, включая аварию до получения ответа; сверка денег не освобождает repair-слот. Недостаточный бюджет до резервирования слот не расходует. Исправлять результат repair повторно нельзя.

Исходный и поздний ответ, usage, неизвестный расход и смена редакции обрабатываются как в B3. При устаревшем токене деньги учитываются, но текущий результат не публикуется. SQLite остаётся v2: используются существующие jobs/attempts/artifacts/llm_calls, новая миграция для B4 не требуется.

Каталог B5 реализован отдельно: выбор конкретного результата B4, версии событий, ручные решения и ограничения сопоставления описаны в [CATALOG.md](CATALOG.md). B5 требует явную миграцию SQLite до схемы 3; форматы B4 и B6 не менялись.
