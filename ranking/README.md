# Отбор и ранжирование новостей

Работающий первый baseline: профили из CSV → отбор кандидатов → объяснимое ранжирование → лента без повторов. Без LLM/API, GPU и внешних Python-зависимостей. Проверяется на Python 3.13.5; запускать из корня проекта.

[Отчет о реализации и фактических проверках](IMPLEMENTATION_REPORT.md).

## Быстрый запуск

Исходные CSV должны находиться в `data/companies/`, как описано в [данных](../data/README.md).

```bash
python3 -m ranking demo
```

Показывает ленты для трех настоящих обезличенных компаний: `U_3263` (грузоперевозки), `U_44792` (ПО), `U_1941` (оптовая торговля). Выбор фиксирован и объяснен в `data/examples/ranking/selection.json`; правила скоринга не зависят от этих ID.

Все 20 сообщений в примере синтетические. После временных фильтров и объединения версий остаются 16 кластеров. Дата анализа зафиксирована: 20.10.2026, 18:00 МСК. Это воспроизводимый тест, а не живой поток.

Результаты в `data/processed/ranking/` (исключены из Git):

- `demo.md` — читаемые ленты, основания и первичная оценка;
- `profiles.json` — профили с происхождением признаков;
- `feeds.json` — кандидаты, финальная лента, причины исключения и ограничения;
- `evaluation.json` — nDCG, Precision и Recall на черновой разметке.

Для графа можно прочитать весь платежный CSV потоком, сохраняя только связи выбранных компаний:

```bash
python3 -m ranking demo --with-payments --output data/processed/ranking/with_graph
```

Дополнительно сохраняются `graph_stats.json` и `graph_probes.json`. Probes — явно синтетическое сопоставление ID с наблюдаемым контрагентом; оно не входит в метрики ленты и не заменяет отсутствующий справочник реальных названий.

## Использование компонентов

```bash
python3 -m ranking profile --company-id U_3263 --output data/processed/ranking/profile.json
python3 -m ranking rank --company-id U_1941 --events data/examples/ranking/events.json --as-of 2026-10-20T18:00:00+03:00 --output data/processed/ranking/trade.json
```

`--companies-csv` позволяет передать другую таблицу того же формата. `rank` требует явный `--as-of`, поддерживает `--top-k`, `--rules`, `--with-payments`, `--payments-csv`. `demo` дополнительно принимает `--company-ids` и `--labels`. Для компании без полного набора меток оценка качества будет недоступна, а ранжирование продолжит работать.

Новый upstream передает **структурированное событие**. Классификация темы и выделение фактов из произвольного текста в этот этап не входят. Минимальный JSON, Python API и семантика версий описаны в [CONTRACT.md](CONTRACT.md).

## Как работает baseline

- Профили: трехзначные продукты, сохраненные интервалы, неизвестные единицы выручки, quarantine конфликтующих ID. `U_428697` отклоняется. Происхождение включает CSV, хэш, номер записи и поле.
- Кандидаты: точный перебор доступного окна, совпадение ОКВЭД/отрасли, условные продуктовые/географические механизмы, слабый lexical fallback по описанию деятельности, явные entity IDs и платежные связи.
- Lexical fallback требует двух разных специфических нормализованных слов. Это грубые пятисимвольные префиксы русских слов, не эмбеддинги или полноценная морфология. Явно несовпадающий отраслевой/географический охват не перекрывается этим каналом.
- Score: сумма объясненных вкладов с ограничением 100, параметры в [rules.json](config/rules.json). Максимальный активный продукт вместо сложения кредит+лизинг. Приоритет — эвристика, не вероятность и не денежный эффект.
- Время: aware timestamps, исключение будущих публикаций/наблюдений, окно 30 дней, исключение неизвестной даты. Старое объявление с близким вступлением остается доступным.
- Версии: выбирается высшая наблюдаемая версия кластера. Старый прогноз не наследует приоритет, если его новый вариант не подтверждает прежний механизм. Поздняя перепечатка не откатывает версию.
- Лента: порог, ограничение темы, уникальные кластеры, возможность скрыть уже показанные версии. Пустая/короткая лента допустима.
- Граф: неполные узлы сохраняются, самопереводы и все неоднозначные повторяющиеся пары исключаются. Доля — часть наблюдаемого направления платежей, не доля выручки/закупок.

## Проверки

```bash
python3 -m unittest discover -s ranking/tests -v
python3 -m ranking.validate_data
```

Unit/CLI-тесты используют временные синтетические CSV и работают без исходной базы. Вторая команда нормализует всю реальную базу, кроме конфликтных ID, и проверяет инварианты ранжирования на 100 компаниях. Это проверка обработки данных, не измерение полезности для 100 компаний. JSON результата — `data/processed/ranking/data_validation.json`.

Метрики: nDCG@5 с gain `2**grade-1`; Precision@5 с порогом grade>=2 и фиксированным знаменателем 5; Recall кандидатов по релевантным кластерам. Группы без положительных меток получают nDCG=null. Если в доступном пуле есть неразмеченные события, nDCG/Precision не считаются, чтобы не принять их за отрицательные.

**48 меток на 3 компаниях созданы тем же агентом, что и baseline.** Они явно provisional, не являются независимой экспертной оценкой. Нужны проверка аналитиком и отдельные скрытые семейства событий. Высокий результат на этом маленьком наборе не доказывает качество на реальных новостях.

## Состав кода

`profiles.py` — CSV и provenance; `events.py` — валидация/время/версии; `lexical.py` — слабый текстовый канал; `engine.py` — отбор, score и лента; `graph.py` — потоковые платежные агрегаты; `metrics.py` — оценка; `__main__.py` — CLI; `validate_data.py` — интеграционная проверка реальных данных.

Оригинальный аудит остается доступен: `python3 ranking/audit_data.py`. Он в отличие от нового графового модуля читает платежи в память.

Следующее улучшение: независимая разметка и анализ ошибок, затем эмбеддинги/обучаемый ранкер по результатам сравнения. Полный план — [PLAN.md](PLAN.md).
