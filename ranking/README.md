# Отбор и ранжирование новостей

Ответственность ML 1: нормализованные профили компаний, наблюдаемые связи, отбор кандидатов и оценка значимости события для компании.

Вход: данные из `data/companies/` и структурированные события. Выход: упорядоченные события, баллы, причины приоритета, использованные признаки и ограничения данных. Генерация развернутой интерпретации находится в `llm/agent/`.

Формат событий от B6: [EventBundle v0.2](../docs/b6-event-contract.md), с Python-моделями, схемой и готовыми JSON-примерами. `ranking_features` помогает отбирать кандидатов, а `claims`, `conflicts` и `limitations` задают основания и ограничения. Сценарий и роли значений до/после передаются структурно. Версия 0.1 сохранена для совместимости; [проверки и переход](../llm/events/README.md). Оценка значимости для компании в B6 не вычисляется.

Первый этап: три профиля из исходной базы, синтетические события, объяснимый baseline и оценка с аналитиком.
Текущий потребитель принимает **EventBundle v0.1** по [JSON Schema](../docs/contracts/event-bundle.schema.json). Producer команды перешёл на v0.2; миграция потребителя — отдельная задача. v0.2 явно отклоняется: нельзя удалять scenario/value_role или молча менять номер версии.

Точный Python API и контракт результата для backend: [CONTRACT.md](CONTRACT.md).

## Что реализовано

- Строгий приём EventBundle, проверка ссылок/цитат/полей и SQLite-история версий с отзывом события.
- Нормализация CSV компаний: неизвестные значения, происхождение признаков, версии профиля и ограничения историчности.
- Потоковый платёжный граф выбранных компаний с исключением неоднозначных пар и контролем качества долей.
- Объяснимый ранкер без LLM: восемь правил, роли, свежесть, конфликты, подтверждённые entity mappings, ограничение повторов в ленте.
- Общий CLI и интеграционные проверки CLI ↔ Python API.

Этот срез публикует автономный бейслайн для интеграции. RAG, аналитик и изменения backend в него не включены.

## Быстрый запуск на синтетике

Python 3.13+, `uv`, запуск из корня checkout. После установки зависимостей демо и тесты работают без внешних API, GPU и локальных банковских CSV.

```bash
uv sync --frozen
uv run --frozen python -m ranking validate-b6 --input docs/b6-examples/normal.json
uv run --frozen python -m ranking demo --as-of 2026-10-20T18:00:00+03:00 --output-dir data/processed/personalization/demo
uv run --frozen python -m unittest discover -s ranking/tests -v
```

Демо создаёт три файла `DEMO_LOGISTICS.json`, `DEMO_IT.json`, `DEMO_TRADE.json`. Каждый содержит `ranked`, `feed`, `deferred`, `excluded`, причины, ссылки на признаки/claims и версии. Все входные компании и новости демо явно синтетические. Пустая лента допустима, если ни один кандидат не преодолел порог; это видно вместе с причинами и полным scored-пулом.

Одна компания и экспорт релевантности для следующих модулей:

```bash
uv run --frozen python -m ranking rank --events data/examples/personalization/events.jsonl --profiles data/examples/personalization/profiles.json --company-id DEMO_LOGISTICS --role cfo --as-of 2026-10-20T18:00:00+03:00 --mode fixture --fixture-clock 2026-10-20T17:00:00+03:00 --output data/processed/personalization/ranking.json --relevance-event-id synthetic:fuel --relevance-output data/processed/personalization/fuel-relevance.json
```

`--events` разрешён только в fixture-режиме с отдельными часами. В рабочем режиме сначала `ingest`, затем `rank --state-dir`: время получения назначается принимающей системой. Файл хранилища выбирается по mode (`events.sqlite3` / `fixture-events.sqlite3`); режимы изолированы. Поздняя загрузка старой статьи не означает знание о ней в прошлом.

## Профиль из локального датасета

```bash
uv run --frozen python -m ranking profile --company-id U_3263 --companies-csv data/companies/df_Uid_data_hack.csv --payments-csv data/companies/df_Uid_payment_hack.csv --with-payments --output data/processed/personalization/U_3263-with-graph.json
```

Это одиночный CompanyProfile. `rank --profiles` принимает envelope `{"schema_version":"0.1","profiles":[...]}`, как в synthetic примере. API `CompanyRepository` позволяет подготовить несколько профилей за одну загрузку CSV, `attach_payment_graph` — за одно сканирование платежей. Для нового ID переобучение и изменение кода не нужны.

Реальные исходники, нормализованные профили, агрегаты графа и SQLite остаются локальными под игнорируемыми путями. Сохранился прежний исследовательский `python3 ranking/audit_data.py`; он читает платежи в память и не является runtime-графом нового модуля.

## Как трактовать результат

Score — некалиброванный эвристический приоритет внимания, а не вероятность, доказанное изменение прибыли или финансовая рекомендация. Высокая значимость начинается с 0.50, средняя — с 0.25; свежесть по умолчанию убывает с полураспадом 10 дней. `raw_total` сохраняет различия при насыщении score=1. При недостатке оснований пара deferred/unknown, а не автоматически «неважно».

Эмбеддинги и обученный ранкер пока не подключены. Для MVP события перебираются по одной выбранной компании; общей матрицы «все компании × все новости» нет. Векторный и инвертированный поиск можно добавить позднее с измерением recall кандидатов. Текущие тесты проверяют поведение, но не заменяют независимую экспертную оценку качества.

Связь реального названия из новости с обезличенным ID требует доверенного entity mapping. Наблюдаемая платёжная доля не доказывает зависимость бизнеса, валюту и период операций. При потерях в графе сильный бонус за процент запрещён. Прогноз/отрицание сохраняются в объяснениях. Недатированный профиль не объявляется исторически достоверным.

Модуль принимает готовые B6-события. Сбор статей в `news/`, генерация EventBundle, RAG и LLM-интерпретация — отдельные этапы; запуск `ranking demo` их готовность не подтверждает.
